应用在构建机上通过校验，解包后却提示资源损坏。单独检查新换上的 helper，签名又是有效的。遇到这类问题，先确定需要哪一层证据：应用包是否保持签名时的状态，签名是否满足预期发布者的要求，以及 macOS 是否允许用户打开最终分发产物。

本文用一个包含主程序、helper 和文本资源的临时 `.app` 复现三类结果。你可以看到改写一份资源为什么会使整包校验失败，也可以用同一个 identifier 为另一份程序签名，观察嵌套校验和发布者要求如何分别工作。

> 示例环境：macOS 26.7.1（25G241）、Apple Silicon arm64、Apple clang 21.0.0、系统 Bash 3.2.57。九项实验均在此环境实测。本文面向 macOS 本地调试与 CI，分发与公证环节的验证限制见文末。

## 一、适用场景与准备

这套方法适用于检查 CI 打包前后的产物、排查某次构建为何破坏签名，以及确认 helper 或资源在打包过程中是否被替换。需要能读懂基本 Shell 命令、退出状态和应用包路径。C 代码只输出一个字符串，用来生成可区分的 Mach-O 文件。

使用普通用户，在 macOS 终端中运行以下检查。需要已安装 Xcode 或 Xcode Command Line Tools，并且终端用户能在临时目录写文件。实验无需 `sudo`、证书、钥匙串凭据或网络。若 `xcrun` 报找不到工具，先完成开发工具安装，再继续实验。

```bash
sw_vers
uname -m
xcode-select -p
xcrun clang --version
/bin/bash --version
```

示例用本机编译器默认目标架构生成单架构二进制。其他 macOS 版本的诊断文字可能不同。Linux 上的 Clang 可以编译 C，但这套校验依赖 macOS 的应用包结构和系统 `codesign`，Linux 常见的 ELF 或包管理器校验命令有各自的签名模型。跨平台 CI 可以在 macOS runner 上执行本节实验和产物校验。

## 二、签名覆盖了哪些内容

实验的应用包结构如下。签名成功后才会生成 `_CodeSignature/CodeResources`。

```text
SealLab.app/
└── Contents/
    ├── Info.plist
    ├── MacOS/SealLab
    ├── Helpers/SealHelper
    ├── Resources/message.txt
    └── _CodeSignature/CodeResources
```

`Info.plist` 的 `CFBundleExecutable` 指向主程序文件名，`CFBundleIdentifier` 提供应用标识。helper 放在系统约定的嵌套代码目录 `Contents/Helpers`，普通数据放在 `Contents/Resources`。区分路径很重要，外层签名可以按嵌套代码记录 helper，普通资源则按文件内容封印。把数据写进代码目录会让签名工具按该目录的代码规则处理它。参见 [Apple TN2206 的嵌套代码说明](https://developer.apple.com/library/archive/technotes/tn2206/)。

Mach-O 签名的核心结构是 **CodeDirectory**。它包含可执行文件页的哈希，以及用于绑定 `Info.plist`、资源封印等结构的特殊哈希槽。对 CodeDirectory 求哈希得到 **CDHash**，因此 CDHash 和对整个文件运行 `shasum -a 256` 得到的摘要表示不同的对象。通用二进制中的每个架构有独立的签名；查看某个架构的 CDHash 只描述该架构的 CodeDirectory。参见 [Apple TN3126 的 CodeDirectory 与哈希槽说明](https://developer.apple.com/documentation/technotes/tn3126-inside-code-signing-hashes)。

应用包中的 `CodeResources` 将资源相对路径与摘要关联，也可以为标准位置的嵌套代码记录 CDHash 与代码要求。外层在签名时依赖这些记录，所以应先签每个内层组件，再签外层。具体包结构及历史格式有差异，诊断时以目标系统的 `codesign` 结果为准。参见 [Apple TN3126 的资源封印说明](https://developer.apple.com/documentation/technotes/tn3126-inside-code-signing-hashes) 和 [Apple 的分发签名指南](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac)。

### 完整性、身份与分发策略

| 你要确认的事 | 检查入口 | 结果怎么读 |
| --- | --- | --- |
| 当前磁盘上的包是否满足自身签名 | `codesign --verify --deep --strict` | 检查代码、封印及嵌套签名，默认还检查代码自身的指定要求 |
| 是否符合独立提供的代码要求 | 在校验时增加 `-R='…'` | 只有同时通过完整性和该要求才成功，身份结论取决于要求写了什么 |
| 最终分发的应用是否符合系统策略 | 现代 macOS 上对正式产物做分发预检，再走真实下载与首次打开流程 | 涉及 Gatekeeper、公证状态等，包签名有效只是其中一项 |

指定要求（Designated Requirement，DR）用于定义系统如何识别一份代码及其后续版本。本实验用 `--sign -` 创建 ad hoc 签名，不绑定证书身份。当前机器显示的 helper 默认 DR 与它的 CDHash 绑定；改动后重新签名的 helper 可以有同样的 identifier，却具有不同的代码身份。identifier 本身由构建方提供，单独检查它只能证明签名声明了这个标识。参见 [Apple TN3127 的代码要求说明](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) 和 [Apple 平台安全指南的 Gatekeeper 说明](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web)。

## 三、从零运行九项实验

把下面整段保存为 `seal-lab.sh`，在有权写入该文件的目录中执行 `/bin/bash ./seal-lab.sh`。脚本在 `mktemp` 创建的独立目录编译、签名与复制应用包。资源覆写和 helper 替换只发生在临时副本；退出时删除本次临时目录，原始样本可通过重新运行脚本重建。实验不启动生成的可执行文件，也不更改系统安全设置。

```bash
#!/bin/bash
set -euo pipefail
export LC_ALL=C

temp_base="${TMPDIR:-/tmp}"
lab="$(/usr/bin/mktemp -d "${temp_base%/}/worthy-sign.XXXXXXXX")"
readonly lab
trap '/bin/rm -rf -- "$lab"' EXIT

app="$lab/SealLab.app"
helper="$app/Contents/Helpers/SealHelper"
resource="$app/Contents/Resources/message.txt"
app_id=example.worthy.seallab
helper_id=example.worthy.seallab.helper

pass() { printf 'PASS %s\n' "$1"; }

verify() {
    /usr/bin/codesign --verify --deep --strict --verbose=2 "$@"
}

expect_rejected() {
    local label="$1" diagnostic="$2"
    shift 2
    if verify "$@" >"$lab/rejected.log" 2>&1; then
        printf 'FAIL %s: verification unexpectedly succeeded\n' "$label" >&2
        exit 1
    fi
    /bin/cat "$lab/rejected.log"
    if ! /usr/bin/grep -Fq -- "$diagnostic" "$lab/rejected.log"; then
        printf 'FAIL %s: unexpected diagnostic\n' "$label" >&2
        exit 1
    fi
    pass "$label"
}

/bin/mkdir -p "$app/Contents/"{MacOS,Helpers,Resources}
/bin/cat >"$lab/demo.c" <<'C'
#include <stdio.h>

int main(void) {
    puts(DEMO_MESSAGE);
    return 0;
}
C

/bin/cat >"$app/Contents/Info.plist" <<'PLIST'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>CFBundleIdentifier</key><string>example.worthy.seallab</string>
    <key>CFBundleName</key><string>SealLab</string>
    <key>CFBundleExecutable</key><string>SealLab</string>
    <key>CFBundlePackageType</key><string>APPL</string>
    <key>CFBundleVersion</key><string>1</string>
</dict>
</plist>
PLIST

/usr/bin/plutil -lint "$app/Contents/Info.plist"
printf '%s\n' 'original resource' >"$resource"

/usr/bin/xcrun clang -Wall -Wextra -Werror '-DDEMO_MESSAGE="main"' \
    "$lab/demo.c" -o "$app/Contents/MacOS/SealLab"
/usr/bin/xcrun clang -Wall -Wextra -Werror '-DDEMO_MESSAGE="helper v1"' \
    "$lab/demo.c" -o "$helper"

# 先签内层，再签外层。--force 替换实验产物上可能已有的签名。
/usr/bin/codesign --force --sign - --identifier "$helper_id" "$helper"
/usr/bin/codesign --force --sign - "$app"

/usr/bin/codesign --display --verbose=4 "$app"
/usr/bin/codesign --display -r- "$helper"
verify "$app"
pass baseline

verify -R="identifier \"$app_id\"" "$app"
pass identifier_match
expect_rejected missing_apple_anchor 'code failed to satisfy specified code requirement' \
    -R="anchor apple generic and identifier \"$app_id\"" "$app"

# 保留原包；在独立副本中只改变一个资源。
resource_copy="$lab/ResourceEdit.app"
/usr/bin/ditto "$app" "$resource_copy"
printf '%s\n' 'edited resource' >"$resource_copy/Contents/Resources/message.txt"
expect_rejected edited_resource 'a sealed resource is missing or invalid' "$resource_copy"

/bin/cp "$resource" "$resource_copy/Contents/Resources/message.txt"
verify "$resource_copy"
pass restored_resource

# 替换另一个副本的 helper，保留相同 identifier，但改动程序内容。
helper_copy="$lab/HelperEdit.app"
/usr/bin/ditto "$app" "$helper_copy"
replacement="$lab/SealHelperReplacement"
/usr/bin/xcrun clang -Wall -Wextra -Werror '-DDEMO_MESSAGE="helper v2"' \
    "$lab/demo.c" -o "$replacement"
/usr/bin/codesign --force --sign - --identifier "$helper_id" "$replacement"
/bin/mv "$replacement" "$helper_copy/Contents/Helpers/SealHelper"

verify -R="identifier \"$helper_id\"" "$helper_copy/Contents/Helpers/SealHelper"
pass replacement_helper_valid
expect_rejected replaced_helper 'nested code is modified or invalid' "$helper_copy"

# 仅为展示重新封印：外层改为接受当前的 helper。
/usr/bin/codesign --force --sign - "$helper_copy"
verify "$helper_copy"
pass resealed_bundle
expect_rejected resealed_without_apple_anchor 'code failed to satisfy specified code requirement' \
    -R="anchor apple generic and identifier \"$app_id\"" "$helper_copy"

printf '%s\n' 'ALL 9 CASES PASSED'
```

执行流程中，`plutil -lint` 先确认 plist 可以解析。主程序与第一个 helper 使用同一份 C 源码，通过 `-DDEMO_MESSAGE=…` 编译出不同内容。独立签署 helper 时用 `--identifier` 固定标识，签署外层应用时由应用包的元数据提供标识。Apple Silicon 上编译器链接的二进制可能已带链接时签名，因此实验用 `--force` 明确替换临时产物上已有的签名。

| 参数 | 在本实验中的作用 |
| --- | --- |
| `--sign -` | 写入 ad hoc 签名，使用连字符表示签名身份参数 |
| `--force` | 签署时替换已有签名，仅用于实验产物 |
| `--display --verbose=4` | 显示签名摘要、哈希、资源与团队标识等元数据 |
| `--display -r-` | 把代码要求打印到终端 |
| `--verify --deep` | 递归检查已识别的嵌套代码 |
| `--strict` | 启用更严格的静态验证，例如对符号链接施加额外约束 |
| `--verbose=2` | 显示验证结果与嵌套对象路径，便于定位失败 |
| `-R="…"` | 在自身签名校验之外，要求目标还满足这条显式规则 |

脚本对负例同时检查非零退出状态和对应的英文诊断，避免把路径写错之类的故障误报为实验成功。`LC_ALL=C` 用来固定语言。如果其他版本只有诊断措辞差异，先人工对照触发的检查与错误路径，再按实际结果调整负例匹配文本。生产 CI 应以退出状态决定任务是否失败，保留完整日志用于诊断。

## 四、预期结果与本次实测

以下是九项实验的实测摘要，已省略临时路径、哈希值和其他详细日志。外层应用报告 `Signature=adhoc`、`TeamIdentifier=not set`；helper 的要求输出包含 `cdhash`。

```text
PASS baseline
PASS identifier_match
PASS missing_apple_anchor
PASS edited_resource
PASS restored_resource
PASS replacement_helper_valid
PASS replaced_helper
PASS resealed_bundle
PASS resealed_without_apple_anchor
ALL 9 CASES PASSED
```

| 实验 | 观察到的结果 |
| --- | --- |
| 原始应用包 | 递归严格校验通过，显示 `valid on disk` |
| 外层 identifier 匹配 | 仅用 identifier 的显式要求通过 |
| 增加 `anchor apple generic` | 显式要求失败。该 ad hoc 签名没有满足 Apple 锚点的签名身份 |
| 改写文本资源 | 外层报告 `a sealed resource is missing or invalid`，并定位到被改写的 `Resources/message.txt` |
| 复制原始资源回去 | 无需重签，外层校验恢复通过 |
| 单独校验新版 helper | 完整性和 identifier 均通过 |
| 校验换过 helper 的整包 | 外层报告 `nested code is modified or invalid`，定位到 `Helpers/SealHelper` |
| 重新签署实验副本的外层 | 递归严格校验通过，当前 helper 已纳入新的封印 |
| 对重签的副本再查 Apple 锚点 | 显式要求仍失败 |

这里最有辨识度的是资源还原与外层重签的区别。还原字节让文件重新匹配原来的封印；重签则用当前内容生成新封印。正式分发包遇到未知篡改时，应从可信构建产物恢复，或重新走完整构建与发布签名流程。随手用 ad hoc 签名覆盖，虽然可能消除静态校验报错，却会丢失原来的发布者证据。

## 五、排查实际产物

先检查**从交付物解包出来的同一份应用**，再回到构建机找签名后的基准产物。以下两条是只读命令，适合普通用户在能读取目标包的 macOS 环境运行。替换示例路径，保留路径引号；`--display` 主要把签名详情写到标准错误，归档日志时应同时收集两路输出。

```bash
app='/path/to/Your App.app'
/usr/bin/codesign --display --verbose=4 "$app" 2>&1
/usr/bin/codesign --verify --deep --strict --verbose=2 "$app"
```

| 现象 | 先检查什么 | 如何处理 |
| --- | --- | --- |
| 无法找到主程序，或应用包结构有歧义 | `Info.plist` 的 `CFBundleExecutable`、对应文件名和目录层级 | 修复组装步骤，完成包结构后重新构建和签署 |
| 提示资源缺失、无效或多出文件 | 详细输出中的 `file modified:` 等路径，以及签名后执行的资源替换、模板渲染或打包步骤 | 将改写移到签名之前。运行时可变数据放到用户目录，例如应用自己的 Application Support 子目录 |
| 提示嵌套代码无效 | 出错路径或 `In subcomponent:`，再单独对该路径执行 `codesign --verify --strict --verbose=2` | 确认内层是否损坏、被换包或签名顺序有误，修复后从内到外签署并重新检查整包 |
| 仅显式要求失败 | 代码要求来自哪里，预期签名渠道、identifier、Team ID 是否一致 | 从可信发布基线核对要求和产物来源，纠正构建身份或拒收产物 |
| 构建目录通过，解包产物失败 | 对比签名后与解包后的目录、文件和符号链接，核查打包与传输 | 修正打包流程，把解包后的递归严格校验纳入交付检查 |
| 静态签名通过，用户仍无法打开 | 正式发布渠道、分发预检、公证票据与真实首次打开流程 | 在干净的目标系统上测试最终分发产物，按发布渠道的官方流程定位 |

普通静态验证默认检查通用 Mach-O 包含的所有架构。用 `--architecture` 查看或排查某个切片后，交付门禁仍应运行未限定架构的整包验证。查看本机选项可执行 `man codesign`，重点看 `--all-architectures`、`--deep`、`--strict` 和 `--test-requirement`。签署时对每个嵌套组件明确设置所需身份与选项，避免用 `--deep --force` 批量覆盖所有组件。参见 [Apple 的 macOS 分发签名指南](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac)。

## 六、把校验放进交付流程

1. **先组装，再签名。** 生成资源、写入构建信息、处理可执行文件，然后签 helper、框架等内层组件，最后签应用包。
2. **校验用户收到的产物。** CI 中对签名后的包及按最终交付方式解出的包运行递归严格校验。收集签名摘要和完整错误日志，禁止用 `|| true` 吞掉失败。诊断时可以缩小到出错组件，交付前仍须检查整包。
3. **独立管理预期身份。** 需要验证发布者时，将从可信正式样本审定的代码要求纳入受控配置，匹配预期渠道、团队与标识。只从待验证产物读取其自身 DR 再用作预期值，会让来源检查依赖该产物本身。实验中的 Apple 锚点仅用来区分证书要求与 ad hoc 签名，正式渠道还应约束预期发布者。参见 [Apple TN3127 的发布渠道与默认要求](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)。
4. **单独验证分发。** 对 Mac App Store 之外分发的正式 Mac 应用，按 Apple 指南完成 Developer ID 签名与公证，并测试用户实际收到的包。在 macOS 14 及以上，可对解包后的正式应用运行 `/usr/bin/syspolicy_check distribution "$app"` 做只读预检。预检之后仍要按实际下载路径测试首次打开。参见 [Apple 的公证指南](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) 和 [Apple DTS 的可信执行排查指南](https://developer.apple.com/forums/thread/706442)。

本次实测包含编译、签名、资源篡改与恢复、嵌套工具替换和显式要求验证。已在本机核对 `syspolicy_check` 的帮助；Developer ID 证书签名、公证提交、Gatekeeper 首次打开、Intel 与通用二进制均未实测。排查时可以按三个结果逐步收窄范围：先查签名覆盖的内容，再核对独立的发布者要求，最后检查正式分发产物的系统策略结果。
