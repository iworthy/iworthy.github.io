商品目录查询的 P99 突然升高时，监控可以指出异常时段，但要追到代码里，还需要知道慢的是哪个操作、发生在哪个线程、最终成功还是失败。JDK Flight Recorder（JFR）可以把这些业务字段和 JVM 诊断事件写进同一份录制文件，供事后按时间线排查。

本文用一个无外部依赖的程序实现自定义耗时事件。先验证 250 毫秒阈值如何筛选快慢操作，再开启调用栈，最后复现两份录制重叠时的配置影响。

## 一、适用版本与权限

示例以包含 `jdk.jfr` 模块的 **HotSpot JDK 25** 为基线。需要会编译 Java 程序，并能在两个终端中运行命令。使用同一套 JDK 的 `java`、`javac`、`jcmd` 和 `jfr`，避免系统 `PATH` 中的旧版本混入。使用 Java 模块系统时，在应用的 `module-info.java` 中声明 `requires jdk.jfr;`。本文用类路径启动，无需创建模块描述符。[JDK 25 的 jdk.jfr 模块](https://docs.oracle.com/en/java/javase/25/docs/api/jdk.jfr/module-summary.html)

以下命令适用于 Linux 和 macOS 的 Bash 或 Zsh。Linux 上把 `JAVA_HOME` 指向所用 JDK 的根目录。macOS 若已注册 JDK 25，可通过 `export JAVA_HOME="$(/usr/libexec/java_home -v 25)"` 选择它。使用解压版时，手动指向 JDK 包里的 `Contents/Home`。两端都使用同一个普通账号启动 JVM 和执行 `jcmd`。目标 JVM 需在同一台机器上，并与诊断命令使用相同的有效用户和组 ID。容器场景优先在目标容器内用服务账号及可见的 PID 操作。[JDK 25 的 jcmd 命令](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jcmd.html#description)

## 二、确定事件的计时边界

自定义事件继承 `jdk.jfr.Event`。`begin()` 和 `end()` 之间的时长用于阈值判断，包含休眠、阻塞和线程未获调度的时间。它测的是这段代码的经过时间。若还想测量进入方法前的排队时间，需要把计时边界移到入队处，或单独记录排队时长。

| 设置或方法 | 在这个示例中的作用 |
| --- | --- |
| `@Name` | 为录制配置和 `jfr print` 提供稳定标识。重构 Java 类名时可以保留事件名。 |
| `@Enabled(false)` | 默认关闭事件，由录制配置显式启用。 |
| `@Threshold("250 ms")` | 默认过滤短于 250 毫秒的事件。录制配置可覆盖默认值。 |
| `@StackTrace(false)` | 默认不采集栈。开启时记录 `commit()` 处的栈，适合定位调用入口。 |
| `end()` → `shouldCommit()` → `commit()` | 先固定时长，再按启用状态与阈值判断是否值得填充字段，最后提交事件。 |

把 `end()` 放在填充字段之前，可以让时长对应业务操作。调用 `shouldCommit()` 后再构造仅用于诊断的字段，可减少无效工作。若省略 `end()`，`commit()` 可以结束已开始的计时，这时提交前的字段准备也落在计时范围内。[JFR 事件 API](https://docs.oracle.com/en/java/javase/25/docs/api/jdk.jfr/jdk/jfr/Event.html) · [JFR 阈值编程指南](https://docs.oracle.com/en/java/javase/25/jfapi/event-threshold.html) · [事件设置](https://docs.oracle.com/en/java/javase/25/docs/api/jdk.jfr/jdk/jfr/package-summary.html)

## 三、编译并启动实验

在终端 A 创建独立的临时目录。用接下来的 Java 代码新建其中的 `CatalogJfrDemo.java`。

```bash
umask 077
work="$(mktemp -d /tmp/worthy-jfr.XXXXXXXX)" && cd "$work"
printf 'work=%s\n' "$work"
"$JAVA_HOME/bin/java" -version
"$JAVA_HOME/bin/javac" -version
```

```java
import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.nio.charset.StandardCharsets;
import jdk.jfr.Category;
import jdk.jfr.Enabled;
import jdk.jfr.Event;
import jdk.jfr.FlightRecorder;
import jdk.jfr.Label;
import jdk.jfr.Name;
import jdk.jfr.StackTrace;
import jdk.jfr.Threshold;

public final class CatalogJfrDemo {
    @Name("cc.worthy.CatalogLookup")
    @Label("Catalog Lookup")
    @Category({"Worthy", "Catalog"})
    @Enabled(false)
    @Threshold("250 ms")
    @StackTrace(false)
    static final class CatalogLookup extends Event {
        @Label("Operation")
        String operation;

        @Label("Outcome")
        String outcome;
    }

    private static void lookup(String operation, long delayMillis, boolean fail)
            throws IOException, InterruptedException {
        CatalogLookup event = new CatalogLookup();
        String outcome = "error";
        event.begin();
        try {
            if (delayMillis > 0) {
                Thread.sleep(delayMillis);
            }
            if (fail) {
                throw new IOException("simulated timeout");
            }
            outcome = "ok";
        } catch (InterruptedException interrupted) {
            outcome = "interrupted";
            throw interrupted;
        } finally {
            event.end();
            if (event.shouldCommit()) {
                event.operation = operation;
                event.outcome = outcome;
                event.commit();
            }
        }
    }

    public static void main(String[] args) throws IOException, InterruptedException {
        FlightRecorder.register(CatalogLookup.class);
        var input = new BufferedReader(
                new InputStreamReader(System.in, StandardCharsets.UTF_8));
        System.out.printf("READY pid=%d (run or quit)%n", ProcessHandle.current().pid());

        String command;
        while ((command = input.readLine()) != null && !command.equals("quit")) {
            if (!command.equals("run")) {
                System.out.println("Type run or quit");
                continue;
            }
            lookup("cache-hit", 0, false);
            lookup("backend-read", 650, false);
            try {
                lookup("backend-timeout", 800, true);
            } catch (IOException expected) {
                System.out.println(expected.getMessage());
            }
            System.out.println("ROUND DONE");
        }
    }
}
```

```bash
"$JAVA_HOME/bin/javac" -Xlint:all CatalogJfrDemo.java &&
  "$JAVA_HOME/bin/java" -cp . CatalogJfrDemo
```

看到 `READY pid=...` 后保留这个终端。程序启动时显式注册事件类型，便于第一次执行操作前就用 `JFR.check verbose=true` 检查配置。每输入一次 `run` 就产生一组操作，最后显示 `ROUND DONE`。快操作没有模拟等待，两次慢操作分别休眠 650 和 800 毫秒。第二次慢操作抛出模拟超时，`finally` 仍记录结果。休眠时长只用于把三类样本拉开，实际事件时长会随调度而变化。

## 四、启动录制、导出并检查事件

在终端 B 使用同一套 JDK。把下面的目录和 PID 换成终端 A 输出的值。先确认 `VM.command_line` 指向实验程序，并用 `JFR.check` 确认没有正在运行的录制。

```bash
umask 077
work='/tmp/worthy-jfr.实际目录后缀'
pid=12345
bin="$JAVA_HOME/bin"

"$bin/jcmd" "$pid" VM.command_line
"$bin/jcmd" "$pid" JFR.check

"$bin/jfr" configure --input none --output "$work/slow.jfc" \
  '+cc.worthy.CatalogLookup#enabled=true' \
  '+cc.worthy.CatalogLookup#threshold=250ms' \
  '+cc.worthy.CatalogLookup#stackTrace=false'

"$bin/jcmd" "$pid" JFR.start name=catalog-slow settings="$work/slow.jfc" \
  disk=true duration=5m maxsize=32m
"$bin/jcmd" "$pid" JFR.check name=catalog-slow verbose=true
```

`--input none` 从空配置创建 JFC，便于观察指定事件。新增设置要在事件名前加 `+`，并用引号将整项设置作为同一个参数。录制使用五分钟作为实验上限，`maxsize=32m` 是该录制的磁盘历史保留设置。若录制自动到期，检查启动时显示的输出路径，并重新启动录制后再运行一轮。目标 JVM 读取 `settings` 路径并写入导出文件，因此路径要对它可见，目录也要允许它写入。[jfr configure](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jfr.html#jfr-configure-subcommand) · [JFR.start 参数](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jcmd.html#commands-for-jcmd)

在终端 A 输入一次 `run`，等到 `ROUND DONE`。在终端 B 导出快照，然后检查录制仍在运行，最后停止它。本文只分析显式命名的输出文件。有时限的录制在停止时还可能写入启动时提示的默认文件。

```bash
"$bin/jcmd" "$pid" JFR.dump name=catalog-slow filename="$work/slow-only.jfr"
"$bin/jcmd" "$pid" JFR.check name=catalog-slow
"$bin/jcmd" "$pid" JFR.stop name=catalog-slow

"$bin/jfr" summary "$work/slow-only.jfr"
"$bin/jfr" print --events cc.worthy.CatalogLookup "$work/slow-only.jfr"
```

预期有两条 `cc.worthy.CatalogLookup` 记录。用 `operation` 和 `outcome` 核对 `backend-read / ok` 与 `backend-timeout / error`，并确认没有调用栈。快速的 `cache-hit` 通常会被阈值过滤。若机器停顿使它实际超过 250 毫秒，应以记录时长为准。导出前已经完成的操作才有机会出现在这份快照里。

接着用同一份 JFC 启动第二次录制，覆盖两个已有设置。将阈值改为 `0ms`，并启用调用栈。

```bash
"$bin/jcmd" "$pid" JFR.start name=catalog-detail settings="$work/slow.jfc" \
  disk=true duration=5m maxsize=32m \
  'cc.worthy.CatalogLookup#threshold=0ms' 'cc.worthy.CatalogLookup#stackTrace=true'
"$bin/jcmd" "$pid" JFR.check name=catalog-detail verbose=true
```

在终端 A 再输入一次 `run`。看到 `ROUND DONE` 后，在终端 B 停止录制并直接保存文件。

```bash
"$bin/jcmd" "$pid" JFR.stop name=catalog-detail filename="$work/all-with-stack.jfr"
"$bin/jfr" print --events cc.worthy.CatalogLookup --stack-depth 8 "$work/all-with-stack.jfr"
```

这次应出现三条事件，包括 `cache-hit / ok`。栈应指向 `CatalogJfrDemo.lookup` 及调用它的 `main`。`--stack-depth` 调整的是打印深度，只有录制时启用了栈采集才有栈可看。需要交给程序读取时，可用 `jfr print --json --events cc.worthy.CatalogLookup 文件名` 导出结构化内容。[JDK 25 的 jfr print](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jfr.html#jfr-print-subcommand)

## 五、复现重叠录制的影响

在终端 B 启动两份重叠录制。第一份使用 250 毫秒阈值且关闭栈，第二份接受所有时长并开启栈。两份都启动后，在终端 A 输入一次 `run` 并等待完成。

```bash
"$bin/jcmd" "$pid" JFR.start name=catalog-overlap-slow settings="$work/slow.jfc" \
  disk=true duration=5m maxsize=32m
"$bin/jcmd" "$pid" JFR.start name=catalog-overlap-detail settings="$work/slow.jfc" \
  disk=true duration=5m maxsize=32m \
  'cc.worthy.CatalogLookup#threshold=0ms' 'cc.worthy.CatalogLookup#stackTrace=true'
```

在终端 B 只导出第一份录制的快照，然后结束两份录制。

```bash
"$bin/jcmd" "$pid" JFR.dump name=catalog-overlap-slow filename="$work/overlap.jfr"
"$bin/jcmd" "$pid" JFR.stop name=catalog-overlap-detail
"$bin/jcmd" "$pid" JFR.stop name=catalog-overlap-slow
"$bin/jfr" print --events cc.worthy.CatalogLookup "$work/overlap.jfr"
"$bin/jcmd" "$pid" JFR.check
```

重叠时，即使只导出配置为高阈值的那一份，快操作和调用栈也可能出现在结果里。JVM 会综合并行录制对事件的要求，导出指定录制名不会按该录制的配置重新筛选事件。这也解释了为什么打开一份临时详细录制可能抬高同一进程的采集成本。复核阈值时，先查看全部活动录制，再选没有其他录制重叠的时间段。[JDK 25 FlightRecorderMXBean#getRecordingSettings](https://docs.oracle.com/en/java/javase/25/docs/api/jdk.management.jfr/jdk/management/jfr/FlightRecorderMXBean.html#getRecordingSettings(long))

实验结束后在终端 A 输入 `quit`，只退出这个实验进程。录制和源文件都留在 `mktemp` 返回的目录。确认已经保留需要的录制后，可删除该目录；删除会移除实验文件，需要重新运行才能生成新录制。

## 六、迁移到服务时怎么排查

| 现象 | 检查方法 |
| --- | --- |
| `jcmd` 无法附加 | 核对有效用户和组、进程是否仍在运行、容器内可见的 PID、Attach 机制是否被禁用。以 `jcmd <PID> help JFR.start` 核对目标 JVM 实际支持的参数。 |
| 文件能打开，但没有业务事件 | 核对 `@Name`、录制配置中的 `enabled`、`threshold` 和操作完成时间。用 `jfr summary` 看事件计数，用 `jfr metadata --events cc.worthy.CatalogLookup 文件名` 检查文件中的事件元数据。 |
| 有错误日志，录制里缺少失败事件 | 检查失败路径是否走到 `finally`，以及异常是否在阈值以下就抛出了。若必须覆盖全部失败，可单设低频失败事件，或用现有错误计数验证完整性。 |
| 时长异常高，栈只显示业务入口 | 栈记录提交事件时的调用位置。用同一时间窗口的 JVM 事件和服务指标验证假设，例如观察 `jdk.SocketRead` 的阻塞时间、GC 暂停和上下游的请求时延。是否有这些 JVM 事件取决于实际录制配置。 |
| 导出路径报错或录制很快丢失旧数据 | 确认目标 JVM 对绝对路径有写权限，检查可用磁盘、录制的 `disk`、`maxage` 和 `maxsize`。JFR 以数据块保留历史，另外导出的快照也要单独管理。 |

接入服务时，选定少量有诊断价值的同步业务边界，例如一次缓存加载或一次后端调用。示例在同一线程开始并提交事件。若调用只负责发起异步工作，埋点需覆盖实际完成位置，并明确定义计时和栈分别代表哪个阶段。事件字段优先使用操作名、结果等有限集合。避免写入令牌、用户标识、查询原文或异常消息。限制录制文件的权限和留存时间，核对模板是否还会收集系统属性、线程名等数据再决定如何分享。

生产诊断可以从较高阈值、关闭业务事件栈和有时间上限的录制开始。在代表性负载下观察应用延迟、事件频率和文件增长，再按需缩短窗口、降低阈值或开启栈。需要结束诊断时，用 `JFR.stop name=<本次录制名>` 停止本次录制。要计算整体请求量、错误率或 P99，仍应使用覆盖全部请求的指标。带阈值的 JFR 录制提供的是一组满足采集条件的样本。[Oracle 的 JFR 性能排查指南](https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshoot-performance-issues-using-jfr.html)
