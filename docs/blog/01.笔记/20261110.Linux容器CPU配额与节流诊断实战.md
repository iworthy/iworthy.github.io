一个容器的请求尾延迟突然变高，宿主机还有不少空闲 CPU。先查容器的 CPU 配额和节流计数，再决定是调整并发度、修改配额，还是继续排查宿主机竞争。仅凭整机 CPU 利用率，很难区分这些情况。

本文用三组短实验验证配额生效的条件，并给出从容器到宿主机逐级检查的命令。读完可以从两份 `cpu.stat` 快照算出窗口 CPU 用量和节流周期比例，并判断下一步该检查哪一层。

## 一、实验环境与权限

需要会运行 Docker 容器，并能区分 CPU 时间和墙钟时间。实验使用 Linux cgroup v2 的统一层级、支持 CPU 带宽限制的内核及 Docker Engine 20.10 或更新版本。以实际的 `docker info` 和容器接口检查为准。下文只讨论普通公平调度类的工作负载。[Docker 的 cgroup v2 支持条件](https://docs.docker.com/engine/containers/runmetrics/#running-docker-on-cgroup-v2)

在 Linux Docker 客户端或 macOS 的 Bash/Zsh 中都可以运行实验。macOS 上的 Docker 后端需要提供 Linux 虚拟机，`/proc` 和 `/sys/fs/cgroup` 由容器里的 Linux 读取。第五节按宿主机 PID 定位 cgroup 的命令只在 Linux Docker daemon 所在主机及对应命名空间中运行。远程 Docker context 也遵循这一规则。

外层命令需要已有的 Docker daemon 访问权限，容器内以 UID/GID 65534 运行。实验容器无网络、无宿主目录挂载、根文件系统只读，仅在自己的 `/tmp` 写入采样文件。先确认当前 context 指向测试环境。示例依赖本地的 `almalinux:8` 镜像，缺少镜像时，可通过环境批准的镜像源取得。允许访问 Docker Hub 的环境可运行 `docker pull almalinux:8`。实验命令本身使用 `--pull=never`，因此不会临时拉取镜像。

## 二、配额、权重和 CPU 集合各管什么

`cpu.max` 的两列分别是配额和周期，单位都是微秒。若值为 `50000 100000`，同一 cgroup 的普通任务每 100 毫秒合计最多消耗 50 毫秒 CPU 时间，长期上限约为 0.5 个逻辑 CPU 的计算时间。它们仍可在允许的多个 CPU 上并行。比如两个线程同时运行，在简化模型中约 25 毫秒就能用完当期配额，然后等下次补充。实际调度还受配额切片、周期边界和突发配置影响。[Linux 内核 cgroup v2 CPU 接口](https://docs.kernel.org/admin-guide/cgroup-v2.html#cpu-interface-files) · [内核 CPU 带宽控制](https://docs.kernel.org/scheduler/sched-bwc.html)

| 接口 | 读数或设定的含义 |
| --- | --- |
| `cpu.max` | 本级带宽上限。第一列 `max` 表示本级不设配额，父级上限仍有效。 |
| `cpu.max.burst` | 支持此接口的内核可允许有限的额外突发额度，默认值为 0。 |
| `cpu.weight` | 同一父级下发生竞争时的相对权重，不能解除自己或祖先的配额。 |
| `cpuset.cpus.effective` | 本组实际允许使用的逻辑 CPU 编号。还可通过目标进程的 `Cpus_allowed_list` 检查进程亲和性。 |

父级和子级可以分别耗尽配额。若两个子组共用父级的 1 CPU 带宽，即使每个子组的配置都允许用到 1 CPU，两组并发时仍需共享父级的总预算。容器内部在私有 cgroup 命名空间里看到的根，通常是宿主机层级中的一个子目录。[Linux 内核带宽控制的层级规则](https://docs.kernel.org/scheduler/sched-bwc.html#hierarchical-considerations) · [Docker 的 cgroup 命名空间默认值](https://docs.docker.com/engine/containers/runmetrics/#running-docker-on-cgroup-v2)

## 三、复现实验

把下面整段复制到测试终端。实验顺序为 `idle-half`（0.5 CPU、休眠）、`busy-half`（0.5 CPU、单工作进程忙循环）、`busy-unlimited`（无本级配额、同样的单工作进程）。每次采样约四秒，第三组最多占用约一个逻辑 CPU。容器在主进程退出后由 `--rm` 清理。若需提前终止，在前台按 Ctrl-C 并检查 `docker ps --filter ancestor=almalinux:8`。如实验容器仍在运行，按启动时间和命令确认其 ID 后执行 `docker stop <容器ID>`，这会终止该容器内的进程并触发自动清理。

```bash
(
  set -eu
  docker context show
  docker info --format 'engine={{.ServerVersion}} cgroup={{.CgroupVersion}} driver={{.CgroupDriver}}'
  test "$(docker info --format '{{.CgroupVersion}}')" = 2 || {
    echo 'This experiment requires cgroup v2.' >&2
    exit 1
  }

  run_case() {
    label=$1
    mode=$2
    shift 2
    printf '\n[%s]\n' "$label"
    docker run --rm -i --pull=never --network none --read-only \
      --tmpfs /tmp:rw,nosuid,nodev,noexec,mode=1777,size=4m \
      --user 65534:65534 --cap-drop ALL --security-opt no-new-privileges \
      --cgroupns=private "$@" almalinux:8 sh -se -- "$mode" <<'CONTAINER'
mode=$1
cg=/sys/fs/cgroup
test "$(cat /proc/self/cgroup)" = '0::/' && test -r "$cg/cpu.max" || {
  echo 'Expected a readable CPU controller at the private cgroup root.' >&2
  exit 1
}
printf 'kernel=%s arch=%s cpu.max=' "$(uname -r)" "$(uname -m)"
cat "$cg/cpu.max"

LC_ALL=C
export LC_ALL
read -r start _ < /proc/uptime
cat "$cg/cpu.stat" > /tmp/cpu.before
case "$mode" in
  idle) sleep 4 ;;
  busy)
    result=0
    timeout -k 1s 4s sh -c 'while :; do :; done' || result=$?
    test "$result" -eq 124 || {
      printf 'unexpected timeout status: %s\n' "$result" >&2
      exit 1
    }
    ;;
  *) exit 2 ;;
esac
cat "$cg/cpu.stat" > /tmp/cpu.after
read -r stop _ < /proc/uptime

awk -v elapsed_us="$(awk -v start="$start" -v stop="$stop" \
  'BEGIN { printf "%.0f", (stop - start) * 1000000 }')" '
  FNR == NR { before[$1] = $2; next }
  { after[$1] = $2 }
  END {
    count = split("usage_usec nr_periods nr_throttled throttled_usec", keys)
    for (i = 1; i <= count; i++) {
      key = keys[i]
      if (!(key in before) || !(key in after) || after[key] < before[key]) {
        print "missing or reset counter: " key > "/dev/stderr"
        exit 1
      }
      delta[key] = after[key] - before[key]
      printf "delta_%-16s %.0f\n", key, delta[key]
    }
    if (elapsed_us <= 0) exit 1
    printf "elapsed_s             %.2f\n", elapsed_us / 1000000
    printf "avg_cpu_cores         %.3f\n", delta["usage_usec"] / elapsed_us
    if (delta["nr_periods"] > 0)
      printf "throttled_period_pct  %.1f\n",
        100 * delta["nr_throttled"] / delta["nr_periods"]
    else
      print "throttled_period_pct  n/a"
  }
' /tmp/cpu.before /tmp/cpu.after
CONTAINER
  }

  run_case idle-half idle --cpu-period=100000 --cpu-quota=50000
  run_case busy-half busy --cpu-period=100000 --cpu-quota=50000
  run_case busy-unlimited busy
)
```

`--cpu-period` 和 `--cpu-quota` 分别指定周期和配额。Docker 的 `--cpus=0.5` 在使用默认 100 毫秒周期时表达相同的额度，选一套参数传递即可。`timeout` 正常触发超时后返回 124。脚本在发出 TERM 一秒后可用 KILL 终止仍未退出的实验进程。[Docker CPU 资源参数](https://docs.docker.com/engine/containers/resource_constraints/#configure-the-default-cfs-scheduler) · [GNU Coreutils timeout](https://www.gnu.org/software/coreutils/manual/html_node/timeout-invocation.html)

## 四、判读实验结果

对比两次快照时，应确认来自同一个仍在运行的 cgroup。容器重建后重新取基线。在稳定采样窗口内，以 `Δusage_usec / 窗口微秒数` 估算平均用掉多少个逻辑 CPU。计数包含该组和后代的进程，实验中的采样命令也有少量开销。

| 增量 | 怎么看 |
| --- | --- |
| `nr_periods` | 带宽控制经过的周期计数。空闲时可能没有增量，不能用墙钟时间除以周期来替换实测计数。 |
| `nr_throttled` | 节流计数。用它和周期计数的增量估算发生节流的周期比例，周期增量为零时记为不可计算。 |
| `throttled_usec` | 内核累计的节流时间。不同 CPU 的节流时间可以叠加，除以墙钟时间不能得到请求受影响的比例。 |

上表的带宽计数来自 `cpu.stat`，反映该级自身的带宽限制。父级引起的节流需要查看父级的计数。即使这里的节流周期比例是 100%，它也只表示每个计入的周期都发生了节流。每个周期中等待了多久，要结合其他数据判断。[Linux 内核对 `cpu.stat` 的定义](https://docs.kernel.org/admin-guide/cgroup-v2.html#cpu-interface-files)

三组实验可按以下条件核对。前两组都应显示 `50000 100000`。空闲组用量很低，节流计数通常不增长。忙循环组会持续产生可运行任务，在 CPU 供应足够且无更紧父级限额时，平均用量应接近 0.5，节流计数应增长。对照组的第一列应是 `max`，有足够 CPU 时，单工作进程的平均用量接近 1。这个对照仍可能受到虚拟机调度、父组配额及宿主机竞争的影响。

## 五、在宿主机追查父级配额

当容器内显示 `max`，或者用量持续低于本级额度，先检查祖先目录。在 daemon 所在的 Linux 主机上，将 `app-container` 替换为正在运行的目标容器名。命令需要已有的 Docker 查询权限和目标 PID、cgroup 文件的读取权限。它适用于完整的统一层级挂载在 `/sys/fs/cgroup` 的宿主环境。如果 daemon 位于虚拟机或独立 PID 命名空间，请在能解释其 PID 的环境执行。

```bash
(
  set -eu
  container=app-container
  pid=$(docker inspect --format '{{.State.Pid}}' "$container")
  test "$pid" -gt 0 || {
    echo 'The container is not running.' >&2
    exit 1
  }
  root=/sys/fs/cgroup
  test "$(stat -f -c %T "$root")" = cgroup2fs
  relative=$(awk '/^0::/ { sub(/^0::/, ""); print; exit }' "/proc/$pid/cgroup")
  case "$relative" in
    /../*|/..) echo 'Run in the daemon host cgroup namespace.' >&2; exit 1 ;;
    /*) ;;
    *) echo 'No unified cgroup path for this PID.' >&2; exit 1 ;;
  esac
  group=$root${relative%/}
  test -d "$group"
  awk '/^Cpus_allowed_list:/ { print }' "/proc/$pid/status"
  while :; do
    printf '\n[%s]\n' "$group"
    for name in cpu.max cpu.stat cpu.weight cpuset.cpus.effective cpu.pressure; do
      if [ -r "$group/$name" ]; then
        printf '%s\n' "$name"
        cat "$group/$name"
      fi
    done
    test "$group" != "$root" || break
    group=${group%/*}
  done
  test "$(docker inspect --format '{{.State.Pid}}' "$container")" = "$pid" || {
    echo 'Container PID changed. Discard this sample and retry.' >&2
    exit 1
  }
)
```

隔几秒再运行一次，逐级比较同一目录的计数增量。对父级读数要考虑同级容器的影响。父级节流增长可以说明共享上限被触发，但要结合目标容器的可运行负载和业务时间线判断它是否因此受影响。根 cgroup 没有 `cpu.max` 属于正常现象。[Docker：查找容器的 cgroup 目录](https://docs.docker.com/engine/containers/runmetrics/#find-the-cgroup-for-a-given-container)

## 六、排障与调整顺序

| 观察 | 下一步 |
| --- | --- |
| `cpu.max` 缺失，或者 `cpu.stat` 只有用量字段 | 确认是否在 v2、是否处于真正的层级根，以及上级是否通过 `cgroup.subtree_control` 启用了 CPU 控制器。rootless 环境还需核对控制器是否由父级委派。 |
| 本级节流和请求 p99 同时上升 | 对齐负载、排队长度、吞吐量和延迟的时间窗。固定其他配置，分别小幅调整 CPU 密集型并发度和配额，比较单项改动的影响。 |
| 本级用量低且计数不增长，父级节流在增长 | 核对父级限额、同级负载与目标进程的运行状态。只提高子容器额度无法解除父级限制。 |
| 各层节流均未增长，CPU 压力却升高 | 检查 `cpuset.cpus.effective`、进程亲和性和所在 CPU 的竞争。若 CPU 压力也低，再结合应用剖析或线程栈检查 I/O、锁与下游等待。 |
| 计数变小或目录在采样之间消失 | 核对容器 ID、PID 和 cgroup 路径是否变化，丢弃跨实例的增量并重新采样。 |

`cpu.pressure` 的 `some` 行可以辅助判断有任务等待 CPU 的程度。它是等待压力指标，配额耗尽则要用带宽计数定位。生产采集应同时记录配置、采样间隔和容器实例标识。不要为读取这些数据向业务容器挂载可写的宿主机 cgroup 层级，也不要把 Docker socket 暴露给应用。[Linux 内核 PSI 文档](https://docs.kernel.org/accounting/psi.html)

生产配置应通过管理该容器的部署入口修改。调高额度会扩大容器可争用的 CPU 时间，调低额度或缩短周期可能改变服务的延迟与吞吐。变更前保留原始配置，先在单个副本试运行，观察该副本和同级服务的指标。回退时还原部署配置，通过同一入口重新应用，再复查 `cpu.max` 和业务指标。

## 七、实际验证与结论

从正文提取第三节完整脚本，在 macOS 26.7.1（Apple Silicon）上的 OrbStack Linux 7.2.12 aarch64、Docker Engine 29.8.2（cgroup v2，`cgroupfs` 驱动）和 AlmaLinux 8.10 容器中执行。容器内为 GNU Coreutils 8.30 和 GNU Awk 4.2.1。两段 Bash 示例均通过 Bash、Zsh 语法检查和 ShellCheck。

| 实验 | `cpu.max` | 采样秒数 | 平均 CPU 数 | 节流计数增量 / 周期计数增量 | 节流时间增量（微秒） |
| --- | --- | ---: | ---: | ---: | ---: |
| `idle-half` | `50000 100000` | 4.01 | 0.001 | 0 / 1 | 0 |
| `busy-half` | `50000 100000` | 4.01 | 0.505 | 40 / 40 | 1,981,477 |
| `busy-unlimited` | `max 100000` | 4.00 | 1.001 | 0 / 0 | 0 |

这是一轮短采样。周期边界、`/proc/uptime` 的显示精度以及采样进程自身的开销都会影响小数位。第五节的宿主机巡检命令未在独立 Linux 宿主机上运行。本次也未注入父级配额、测试 rootless、修改生产配置或测量请求延迟。

诊断时先读 `cpu.max` 确认规则，再算 `cpu.stat` 的窗口增量确认节流。若本级规则无法解释观察结果，就沿宿主机层级检查父组、同级负载和可用 CPU。把这些数据与应用延迟对齐，才有依据选择该调整的配置。
