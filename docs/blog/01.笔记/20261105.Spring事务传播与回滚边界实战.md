## 一、适用场景与学习目标

适合已经会写简单 SQL、理解 Java 异常和 Spring Bean 注入的开发人员，以及需要定位事务回滚、数据库连接占用问题的运维人员。运行实验只需 JDK 8、curl 和可写的临时目录，不需要安装数据库服务器、Maven 或启动 Web 服务。

完成后应能够：

- 画出一次业务调用经过的代理边界，识别自调用造成的事务属性失效。
- 区分异常被 Java 代码捕获与数据库事务仍可提交这两件事。
- 依据最终业务要求选择 REQUIRED、REQUIRES_NEW 或 JDBC 保存点。
- 用最终表数据验证事务行为，避免只凭日志中的“方法执行完成”判断提交成功。

适用范围限定为：同一 JVM、同一线程、一个 DataSource、`DataSourceTransactionManager`、Spring 默认代理事务模式。本文不覆盖分布式事务、响应式事务或 JPA 持久化上下文的回滚语义。

## 二、先分清三个边界

### 2.1 方法调用不一定经过事务代理

在本例中，容器为 Service 创建代理。外部调用先进入代理，事务拦截器根据注解安排开始或加入事务，再执行目标方法，最后根据返回或异常完成事务。

```text
调用者
  -> Spring 代理
     -> 事务拦截器：获取事务
        -> 目标 Service 方法
     -> 正常返回或异常：提交、回滚或标记 rollback-only
  <- 调用者获得返回值或异常
```

如果目标对象在方法体中调用自己的另一个方法，这次调用没有重新进入代理。内部方法即使标了注解，也不会建立新的事务拦截边界。这个限制见 [Spring 5.3.31 代理事务说明](https://docs.spring.io/spring-framework/docs/5.3.31/reference/html/data-access.html#transaction-declarative-annotations)。

因此，自调用要分两种情况判断：

- 外层没有事务：内部注解被绕过，本例 SQL 会使用普通自动提交连接。
- 外层已有事务：内部 SQL 仍可加入外层事务，但内部声明的 REQUIRES_NEW 不会因此生效。

后文分别实测这两条路径。修复时优先把需要独立边界的行为放入另一个 Spring Bean，再通过注入的代理调用；手工 `new Service()` 不会获得容器创建的事务代理。

### 2.2 逻辑事务边界与物理事务不是同一件事

以两个 Service 在同一线程调用为例：

| 内层传播方式 | 外层已有事务时 | 本例数据库资源 | 内层失败后的关键影响 |
| --- | --- | --- | --- |
| REQUIRED | 加入外层事务 | 共用一个物理事务及连接 | 符合回滚规则的失败可将共享事务标记为 rollback-only |
| REQUIRES_NEW | 挂起外层，启动独立事务 | 外层连接保留，内层另取连接 | 内层独立回滚；异常若继续传出，仍可能触发外层回滚 |
| NESTED | 在现有事务上建立保存点 | 同一物理事务及连接 | 可回滚到保存点；没有独立的持久提交 |

没有外层事务时，REQUIRED 会开启事务，REQUIRES_NEW 也会开启事务；NESTED 在该条件下按 REQUIRED 处理。传播定义可查 [Propagation API](https://docs.spring.io/spring-framework/docs/5.3.39/javadoc-api/org/springframework/transaction/annotation/Propagation.html)。本文只实测“已有外层事务”时的传播差异。

### 2.3 Spring JDBC 必须使用同一套事务资源

[DataSourceTransactionManager](https://docs.spring.io/spring-framework/docs/5.3.31/javadoc-api/org/springframework/jdbc/datasource/DataSourceTransactionManager.html) 负责管理单个 DataSource 的 JDBC 事务，并把连接资源与当前线程关联。`JdbcTemplate` 会通过 Spring 的连接获取机制参与事务。

本例将同一个 DataSource 同时交给 JdbcTemplate 和事务管理器。若业务访问另一个 DataSource，或者直接获取了一条不受当前事务管理的连接，不能因为方法上有注解就认定那部分 SQL 会一起回滚。

这也是排查时必须记录“实际使用哪个事务管理器、哪个数据源”的原因。

### 3.3 理解数据源配置

程序使用以下 JDBC URL：

```text
jdbc:h2:mem:txlab;DB_CLOSE_DELAY=-1
```

- `mem:txlab`：同一 JVM 中有名称的内存数据库，让不同 JDBC 连接访问同一个实验库。
- `DB_CLOSE_DELAY=-1`：最后一个连接关闭后仍保留该内存库，便于跨连接验证。程序结束前执行 `SHUTDOWN`；JVM 退出后数据不会保留。
- `sa` 与空密码：仅用于不启动网络服务的本地内存实验，不能照搬到远程或持久化数据库。

命名内存库与关闭行为参见 [H2 官方文档](https://h2database.com/html/features.html#in_memory_databases)。该页面随 H2 主线更新；本次数据行为另由 H2 2.1.214 实际执行确认。

本例的 [DriverManagerDataSource](https://docs.spring.io/spring-framework/docs/5.3.31/javadoc-api/org/springframework/jdbc/datasource/DriverManagerDataSource.html) 每次请求创建连接，**不是连接池**，适合小型验证。它可以提供 REQUIRES_NEW 需要的独立连接，但不能用来验证生产连接池容量或等待时间。

## 四、完整代码：九个场景与最终数据断言

保存为 `src/lab/TxBoundaryLab.java`。这是完整源文件，包含配置、两个 Service 和可执行入口。

```java
package lab;

import java.io.IOException;
import javax.sql.DataSource;
import org.springframework.aop.support.AopUtils;
import org.springframework.context.annotation.*;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;
import org.springframework.jdbc.datasource.DriverManagerDataSource;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.UnexpectedRollbackException;
import org.springframework.transaction.annotation.*;
import org.springframework.transaction.support.TransactionSynchronizationManager;

public class TxBoundaryLab {
    @Configuration
    @EnableTransactionManagement(proxyTargetClass = true)
    public static class Config {
        @Bean
        public DataSource dataSource() {
            return new DriverManagerDataSource(
                    "jdbc:h2:mem:txlab;DB_CLOSE_DELAY=-1", "sa", "");
        }

        @Bean
        public JdbcTemplate jdbc(DataSource ds) {
            return new JdbcTemplate(ds);
        }

        @Bean
        public PlatformTransactionManager transactionManager(DataSource ds) {
            return new DataSourceTransactionManager(ds);
        }

        @Bean
        public InnerService inner(JdbcTemplate jdbc) {
            return new InnerService(jdbc);
        }

        @Bean
        public OuterService outer(JdbcTemplate jdbc, InnerService inner) {
            return new OuterService(jdbc, inner);
        }
    }

    public static class InnerService {
        private final JdbcTemplate jdbc;

        public InnerService(JdbcTemplate jdbc) { this.jdbc = jdbc; }

        private void audit(boolean fail) {
            jdbc.update("insert into audit_log(id) values (?)", 1);
            if (fail) { throw new IllegalStateException("inner failure"); }
        }

        @Transactional
        public void requiredFail() { audit(true); }

        @Transactional(propagation = Propagation.REQUIRES_NEW)
        public void newFail() { audit(true); }

        @Transactional(propagation = Propagation.REQUIRES_NEW)
        public void newSuccess() { audit(false); }

        @Transactional(propagation = Propagation.NESTED)
        public void nestedFail() { audit(true); }
    }

    public static class OuterService {
        private final JdbcTemplate jdbc;
        private final InnerService inner;

        public OuterService(JdbcTemplate jdbc, InnerService inner) {
            this.jdbc = jdbc;
            this.inner = inner;
        }

        private void order() {
            jdbc.update("insert into orders(id) values (?)", 1);
        }

        public void selfCallWithoutTransaction() { runtimeFail(); }

        @Transactional
        public void runtimeFail() {
            order();
            System.out.println("runtimeFail active="
                    + TransactionSynchronizationManager.isActualTransactionActive());
            throw new IllegalStateException("outer failure");
        }

        @Transactional
        public void checkedDefault() throws IOException {
            order();
            throw new IOException("checked failure");
        }

        @Transactional(rollbackFor = IOException.class)
        public void checkedRollback() throws IOException {
            order();
            throw new IOException("checked failure");
        }

        @Transactional
        public void requiredCatch() {
            order();
            try { inner.requiredFail(); }
            catch (IllegalStateException expected) { /* lab: continue */ }
        }

        @Transactional
        public void newFailCatch() {
            order();
            try { inner.newFail(); }
            catch (IllegalStateException expected) { /* lab: continue */ }
        }

        @Transactional
        public void newSuccessThenOuterFail() {
            order();
            inner.newSuccess();
            throw new IllegalStateException("outer failure");
        }

        @Transactional
        public void nestedFailCatch() {
            order();
            try { inner.nestedFail(); }
            catch (IllegalStateException expected) { /* lab: continue */ }
        }

        @Transactional(propagation = Propagation.REQUIRES_NEW)
        public void selfNewSuccess() {
            jdbc.update("insert into audit_log(id) values (?)", 1);
        }

        @Transactional
        public void selfNewThenOuterFail() {
            order();
            selfNewSuccess();
            throw new IllegalStateException("outer failure");
        }
    }

    @FunctionalInterface
    interface Action { void run() throws Exception; }

    private static void verify(JdbcTemplate jdbc, String name, Action action,
            Class<? extends Exception> expected, int orders, int audits)
            throws Exception {
        jdbc.update("delete from audit_log");
        jdbc.update("delete from orders");
        Exception actual = null;
        try { action.run(); }
        catch (Exception e) { actual = e; }

        if ((expected == null && actual != null)
                || (expected != null
                    && (actual == null || actual.getClass() != expected))) {
            throw new AssertionError(name + ": unexpected exception", actual);
        }
        int actualOrders = jdbc.queryForObject(
                "select count(*) from orders", Integer.class);
        int actualAudits = jdbc.queryForObject(
                "select count(*) from audit_log", Integer.class);
        if (actualOrders != orders || actualAudits != audits) {
            throw new AssertionError(name + ": orders=" + actualOrders
                    + ", audit=" + actualAudits);
        }
        System.out.println("PASS " + name + " orders=" + actualOrders
                + " audit=" + actualAudits + " exception="
                + (actual == null ? "none" : actual.getClass().getSimpleName()));
    }

    public static void main(String[] args) throws Exception {
        try (AnnotationConfigApplicationContext ctx =
                new AnnotationConfigApplicationContext(Config.class)) {
            JdbcTemplate jdbc = ctx.getBean(JdbcTemplate.class);
            OuterService outer = ctx.getBean(OuterService.class);
            if (!AopUtils.isAopProxy(outer)
                    || !AopUtils.isAopProxy(ctx.getBean(InnerService.class))) {
                throw new AssertionError("expected Spring proxies");
            }
            jdbc.execute("create table orders(id int primary key)");
            jdbc.execute("create table audit_log(id int primary key)");
            verify(jdbc, "self-no-tx", outer::selfCallWithoutTransaction,
                    IllegalStateException.class, 1, 0);
            verify(jdbc, "runtime", outer::runtimeFail,
                    IllegalStateException.class, 0, 0);
            verify(jdbc, "checked-default", outer::checkedDefault,
                    IOException.class, 1, 0);
            verify(jdbc, "checked-rollback", outer::checkedRollback,
                    IOException.class, 0, 0);
            verify(jdbc, "required-catch", outer::requiredCatch,
                    UnexpectedRollbackException.class, 0, 0);
            verify(jdbc, "new-fail-catch", outer::newFailCatch, null, 1, 0);
            verify(jdbc, "new-success-outer-fail", outer::newSuccessThenOuterFail,
                    IllegalStateException.class, 0, 1);
            verify(jdbc, "nested-fail-catch", outer::nestedFailCatch, null, 1, 0);
            verify(jdbc, "self-new-outer-fail", outer::selfNewThenOuterFail,
                    IllegalStateException.class, 0, 0);
            jdbc.execute("shutdown");
        }
        System.out.println("ALL 9 CASES PASSED");
    }
}
```

代码中有几项专门用于排除干扰的设计：

1. `@EnableTransactionManagement(proxyTargetClass = true)` 显式启用类代理；Service 类和需要拦截的方法都为 public，且没有 final 修饰。
2. Service 由容器中的 `@Bean` 创建；启动后同时断言两个对象确实是 Spring AOP 代理。
3. 表在所有业务事务开始之前创建，避免把数据库 DDL 行为混入 DML 回滚实验。审计表没有引用订单表的外键，使独立内层事务不依赖尚未提交的订单行。
4. 每个场景之前，在业务事务之外删除上个场景的数据。**这些 DELETE 是清空实验表的操作**，不应改为生产连接执行。
5. 验证代码位于所有代理调用之外，检查异常类型和最终行数；没有给入口加一层测试事务。
6. 内层失败是应用主动抛出 IllegalStateException，不是数据库连接中断或严重 SQL 错误。不要将保存点实验结果外推到所有数据库故障。

示例中的空 catch 是为了观察“捕获之后能否提交”，只捕获预期异常类型。生产代码需要记录失败、更新业务状态或安排补偿，不能照搬为静默吞掉异常。

## 六、逐个解释回滚边界

### 6.1 自调用：有注解，但没有新拦截边界

`self-no-tx` 通过代理进入一个未标事务的方法，再在目标对象内部调用 `runtimeFail()`。后者输出 active=false，订单最终为 1 行：异常产生之前，INSERT 已在该实验连接的自动提交模式下完成。

`runtime` 则由入口直接调用代理上的同一个方法，输出 active=true。异常经过事务拦截器后触发回滚，订单为 0 行。两组使用相同的 SQL 和异常，区别是调用路径。

`self-new-outer-fail` 验证另一种情况：外层事务有效，但内部 `selfNewSuccess()` 的 REQUIRES_NEW 被自调用绕过。审计写入参与外层事务，最终随订单一起回滚。

因此，仅打印 active=true 不能证明“新的独立事务已经建立”。应结合代理路径与最终提交结果判断。

### 6.2 受检异常：调用失败不一定意味着数据库回滚

在固定的 Spring 5.3.31 默认规则中，运行时异常和 Error 触发回滚；受检异常不默认触发。规则依据 [Transactional API](https://docs.spring.io/spring-framework/docs/5.3.31/javadoc-api/org/springframework/transaction/annotation/Transactional.html)。

实验中的 IOException 确实传回调用者，但 checked-default 仍保留订单。checked-rollback 则通过 `rollbackFor = IOException.class` 明确要求回滚，订单为 0。

业务异常应按实际语义制定规则。例如“校验未通过，先前写入必须撤销”，就要保证该异常类型命中回滚规则。优先使用异常类表达规则，避免宽泛字符串匹配导致意外命中其他异常。

此外，异常需要穿过对应事务拦截边界。若在同一个事务方法体内抛出又捕获，拦截器最终只看到正常返回；没有其他 rollback-only 原因时，不能期待它自动依据那次已捕获异常回滚。

### 6.3 REQUIRED：catch 不能清除已标记的 rollback-only

required-catch 的实际顺序是：

```text
外层代理开启事务 A
  外层写订单
  内层代理加入事务 A
    内层写审计并抛出运行时异常
  内层拦截器将共享事务标记为 rollback-only
  外层方法捕获异常，正常返回
外层代理尝试完成事务，发现不能提交
回滚事务 A，向入口抛出 UnexpectedRollbackException
```

捕获动作发生在内层代理已经处理异常之后。它能改变 Java 控制流，却不能把共享事务恢复成可提交状态。最终两张表都为 0。

本例保持事务管理器默认设置，包括参与事务失败后的回滚标记行为，相关配置见 [AbstractPlatformTransactionManager API](https://docs.spring.io/spring-framework/docs/5.3.31/javadoc-api/org/springframework/transaction/support/AbstractPlatformTransactionManager.html)。

出现 UnexpectedRollbackException 时，要沿调用链查找**先前的失败或 rollback-only 设置来源**。最后的异常是整体提交没有发生的通知，不能简单归因于外层 catch “没写对”。也不应为了消除异常直接修改全局回滚行为；数据库资源是否还能继续使用，需要单独判断。

### 6.4 REQUIRES_NEW：独立结果，也意味着独立业务事实

new-fail-catch 中，内层事务 B 写审计后回滚，外层事务 A 捕获失败后提交订单。结果是订单 1、审计 0。

new-success-outer-fail 中，内层 B 已经提交审计，外层随后抛异常并回滚。结果是订单 0、审计 1。这条审计在语义上应表达“曾尝试下单”，不能错误地表达“订单已成功创建”。

独立提交适合允许与主业务结果脱钩的记录。但若审计行必须与订单同时存在，REQUIRES_NEW 就不能满足这个约束。本实验没有外键，正是为了避免把未提交订单的可见性和锁等待混入传播演示。

内层独立回滚也不等于外层必然提交：如果不捕获内层异常，它继续穿过外层代理时，仍会按照外层规则导致外层回滚。

### 6.5 NESTED：局部撤销依赖保存点

nested-fail-catch 中，内层失败后回滚到保存点，移除审计写入；外层继续完成，留下订单。

这与 new-fail-catch 的最终行数相同，但使用的资源和提交关系不同。NESTED 没有为内层建立可脱离外层独立持久化的提交；若外层最终回滚，整个物理事务中的相关改动仍受其影响。

本次仅在 H2 与 DataSourceTransactionManager 下验证。迁移到其他 JDBC 驱动、事务管理器或 ORM 时，应先确认保存点支持，并重新运行针对最终数据库结果的测试。

## 七、进阶实践：连接、锁与超时一起考虑

### 7.1 REQUIRES_NEW 会增加同时占用的连接

在本例这种外层已持有连接的 JDBC 事务中，挂起外层不会释放其连接和锁。内层启动独立事务时还需要另一条连接。该风险在 [Spring 6.2 官方事务传播说明](https://docs.spring.io/spring-framework/reference/6.2/data-access/transaction/declarative/tx-propagation.html) 中也有明确说明。

假设有 N 个并发业务线程，每个都先持有一条外层连接，再等待内层连接，而池只有 N 条连接，就可能出现所有线程都无法继续推进的局面。实际系统可能最终因获取连接超时而失败；不能把这种停滞都当成数据库检测到的死锁。

官方文档要求为这种调用关系保留额外连接，但“比线程数多 1”不应直接当作生产容量结论。它没有覆盖多层嵌套、其他业务共享连接、数据库连接上限或突发负载。应从同时活跃的事务层数和入口并发推导需求，再通过测量确定上限与限流策略。

本文没有使用连接池，也没有进行压力测试，不提供池大小、吞吐或延迟的实测建议。

### 7.2 挂起的外层事务仍可能阻塞内层

即使池中有空闲连接，内层若更新外层已锁定的同一行，仍可能等待。此时外层又同步等待内层返回，形成业务层面的进度依赖。

审计功能应尽量避免依赖外层未提交数据；它若必须读取或更新这类数据，应重新设计边界。观察连接等待、数据库会话和锁等待时，要使用同一请求标识关联内外事务，单看线程数无法定位原因。

### 7.3 事务超时不是任意代码的强制终止器

对本例的事务管理器，事务 timeout 会结合支持该机制的 JDBC 操作施加到 statement 等环节，具体取决于驱动及调用方式。不要认为给注解加 timeout 就能中断所有业务计算或外部 HTTP 调用。

连接获取超时、SQL 执行超时、锁等待超时和请求总期限应分别检查，并确保失败后的事务与连接得到清理。本文没有运行超时故障注入，因此不声称验证了某种驱动的超时或取消行为。

## 八、迁入 Spring Boot 项目时的核对步骤

本文显式配置是为了固定实验条件。已有 Boot 项目通常由自动配置与项目配置共同决定事务管理器，不能直接复制整个 Config，制造多个管理器或覆盖既有 DataSource。

建议按以下顺序迁入相同业务实验：

1. 保持项目现有的依赖管理，确认实际 Spring Framework 与 JDBC 驱动版本；不要单独把本文旧版 JAR 加进 Boot 项目。
2. 查明业务实际使用的 DataSource、JdbcTemplate 或 ORM，以及与其匹配的事务管理器。多个管理器时，通过注解中的 transactionManager 明确选择。
3. 将业务方法放入容器管理的 Bean，通过注入对象从代理外调用；先保留 public、可代理的方法形态。
4. 把验证入口放在被测事务之外，使用独立测试库，并在代理调用彻底返回后检查表数据。
5. 在真实数据库上补充驱动错误、锁等待、连接池耗尽等故障验证，记录异常类型与最终数据，避免仅断言方法返回值。

版本差异也必须显式核对。[Spring 6.2 的注解事务文档](https://docs.spring.io/spring/reference/6.2/data-access/transaction/declarative/annotations.html) 说明：从 6.0 起，类代理支持的事务方法可见性范围有所扩展；6.2 还提供全局默认回滚行为配置。若项目采用这些配置，本文默认受检异常用例的预期可能需要调整。本文未在这些新版本上运行，不把文档核对表述为实测通过。

命令式事务上下文也不会自动传播到新线程；异步方法若需要事务，必须在实际执行线程上建立合适的边界。响应式事务则依赖不同的上下文机制，不能套用本实验的线程模型。

## 九、常见错误与排查顺序

| 现象 | 优先核对 | 验证办法 |
| --- | --- | --- |
| 抛异常后数据仍存在 | 是否经过代理、异常是否命中规则 | 对照 self-no-tx 与 checked-default，检查事务状态与最终行数 |
| 捕获异常后仍全部回滚 | 内层是否 REQUIRED，是否已标记 rollback-only | 保留首次异常，沿内层代理出口追踪 |
| REQUIRES_NEW 看似不起作用 | 是否自调用、是否手工 new 对象 | 对照 self-new-outer-fail，确认独立数据是否真的提交 |
| 主业务失败，审计却保留 | 是否已经独立提交 | 核对审计含义，区分尝试记录与成功事实 |
| 并发后卡在获取连接 | 外层连接占用、池上限、嵌套层数 | 同时查看活动连接、等待连接的线程和入口并发 |
| 有连接但 SQL 一直等待 | 内层是否依赖外层持有的锁 | 对齐数据库会话、锁等待和同一请求调用链 |
| NESTED 报不支持 | 管理器与驱动是否支持保存点 | 在同版本测试库执行最小保存点实验 |
| 测试总是回滚，看不出差异 | 测试框架是否额外包了一层事务 | 先采用本文 main 入口，再迁入项目测试 |

排查日志应记录请求标识、Service 方法、异常类型、数据源标识和事务管理器类型；避免输出口令、完整业务载荷或敏感 SQL 参数。只在短期诊断中提高日志级别，并测量额外日志对系统的影响。

不要把生产数据库接到本实验上。程序含建表、全表 DELETE 和 SHUTDOWN，且使用为隔离复现准备的弱认证配置。其恢复方式是重新运行程序重建内存实验数据；它不能为生产误操作提供恢复能力。

## 十一、实践总结

判断事务行为时，先确认调用是否真正进入代理，再确认异常经过了哪个拦截边界，最后确认 SQL 属于哪个物理事务。REQUIRED 中捕获异常不代表清除了回滚标记；REQUIRES_NEW 的独立提交会形成独立业务事实；NESTED 的局部回滚依赖保存点，仍受外层最终结果约束。

落地时以最终数据与明确的失败语义作为验收条件，同时检查连接占用、锁依赖和版本配置。只有把这些边界记录清楚，才能从“注解看起来正确”走到“故障时结果符合预期”。
