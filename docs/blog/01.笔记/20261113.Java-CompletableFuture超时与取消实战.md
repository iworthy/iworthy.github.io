接口已经返回超时，线程池里的数据库查询却仍在执行；调用方收到降级结果，后台任务稍后又完成了写入。这些现象往往来自同一个误解：把“停止等待”“Future 完成”和“任务停止”当成了一件事。

## 二、先区分三个观察对象

排障时应分别回答：调用线程是否还在等待？Future 对外暴露什么结果？工作线程是否已经退出业务代码？

| 操作 | 等待方 / Future 的变化 | 对已经开始的后台任务 |
| --- | --- | --- |
| `f.get(30, MILLISECONDS)` 等待超时 | 本次等待抛 TimeoutException，未因此完成 f | 不发出取消请求 |
| `f.orTimeout(30, MILLISECONDS)` 的定时器获胜 | f 异常完成，结果是超时 | 不负责中断任务 |
| `f.completeOnTimeout(value, ...)` 的定时器获胜 | f 正常完成，结果是降级值 | 不负责中断任务 |
| `f.cancel(true)`，f 是 CompletableFuture | 未完成的 f 进入取消状态 | 参数 true 在此实现中不触发中断 |
| `task.cancel(true)`，task 是已运行的 FutureTask | 尝试取消，并尝试中断执行线程 | 是否及时退出取决于任务响应 |

前两类超时的异常位置也不同：`get(timeout)` 自己等不及，直接抛 `TimeoutException`；若 f 已被 `orTimeout` 异常完成，`get()` 取得的是 `ExecutionException`，其原因才是 `TimeoutException`。使用 `join()` 读取这种异常完成时，通常看到 `CompletionException`。[Future 的等待与取消契约](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/Future.html)

正常结果、异常和超时会竞争完成同一个 CompletableFuture。除专门用于强制改写状态的恢复 API 外，后到的完成尝试不会覆盖已确定结果。因此“返回了降级值”也不意味着“后台操作尚未发生”。下面用门闩控制任务完成顺序，避免凭线程休眠猜测时序。

## 三、完整可运行实验

程序只创建一个有界、单工作线程的执行器。每个 Work 通过三个门闩暴露开始、放行和退出节点；`started` 确保测试的是已经开始的任务，`release` 阻止任务提前正常返回，`exited` 用于单独观察业务代码退出。[CountDownLatch API 与内存可见性](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/CountDownLatch.html)

30 毫秒仅用于触发超时，不是性能目标。读取测试结果和等待同步事件时设置 5 秒保护上限；极端繁忙的环境仍可能使保护断言失败，应先检查机器负载和线程状态，不能把它解释成调度器承诺失效。

```java
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicBoolean;

public final class TimeoutLab {
    private static final TimeUnit MS = TimeUnit.MILLISECONDS;
    private static final TimeUnit SEC = TimeUnit.SECONDS;

    static void check(boolean condition, String message) {
        if (!condition) throw new AssertionError(message);
    }

    static void await(CountDownLatch latch) throws InterruptedException {
        check(latch.await(5, SEC), "latch did not open within 5s");
    }

    static final class Work implements Callable<String>, AutoCloseable {
        final CountDownLatch started = new CountDownLatch(1);
        final CountDownLatch release = new CountDownLatch(1);
        final CountDownLatch exited = new CountDownLatch(1);
        final AtomicBoolean interrupted = new AtomicBoolean();

        public String call() throws InterruptedException {
            started.countDown();
            try {
                release.await();
                return "real";
            } catch (InterruptedException e) {
                interrupted.set(true);
                throw e;
            } finally {
                exited.countDown();
            }
        }

        String supply() {
            try {
                return call();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                throw new CompletionException(e);
            }
        }

        void stillRunning() {
            check(exited.getCount() == 1, "work unexpectedly exited");
            check(!interrupted.get(), "work unexpectedly interrupted");
        }

        public void close() {
            release.countDown();
        }
    }

    static void expectTimeout(CompletableFuture<?> future) throws Exception {
        try {
            future.get(5, SEC);
            throw new AssertionError("expected exceptional completion");
        } catch (ExecutionException e) {
            check(e.getCause() instanceof TimeoutException, "wrong cause");
        }
    }

    // Only use this method when this caller owns the submitted task.
    static <T> T awaitOwned(Future<T> task, long timeout, TimeUnit unit)
            throws InterruptedException, ExecutionException, TimeoutException {
        try {
            return task.get(timeout, unit);
        } catch (TimeoutException | InterruptedException e) {
            task.cancel(true);
            throw e;
        }
    }

    static void getTimeout(ExecutorService pool) throws Exception {
        try (Work w = new Work()) {
            CompletableFuture<String> f = CompletableFuture.supplyAsync(w::supply, pool);
            await(w.started);
            try {
                f.get(30, MS);
                throw new AssertionError("expected wait timeout");
            } catch (TimeoutException expected) {
                check(!f.isDone(), "get changed future state");
                w.stillRunning();
            }
            w.release.countDown();
            check(f.get(5, SEC).equals("real"), "real result lost");
        }
        System.out.println("PASS 1 get: wait timed out, real result retained");
    }

    static void orTimeout(ExecutorService pool) throws Exception {
        try (Work w = new Work()) {
            CompletableFuture<String> f = CompletableFuture.supplyAsync(w::supply, pool);
            await(w.started);
            check(f.orTimeout(30, MS) == f, "orTimeout returned a different object");
            expectTimeout(f);
            check(!f.isCancelled(), "timeout is not cancellation");
            w.stillRunning();
            w.release.countDown();
            await(w.exited);
            expectTimeout(f);
        }
        System.out.println("PASS 2 orTimeout: same object, worker continued");
    }

    static void fallback(ExecutorService pool) throws Exception {
        try (Work w = new Work()) {
            CompletableFuture<String> f = CompletableFuture.supplyAsync(w::supply, pool);
            await(w.started);
            check(f.completeOnTimeout("fallback", 30, MS) == f, "different object");
            check(f.get(5, SEC).equals("fallback"), "wrong fallback");
            check(!f.isCompletedExceptionally(), "fallback should be normal");
            w.stillRunning();
            w.release.countDown();
            await(w.exited);
            check(f.join().equals("fallback"), "late result overwrote fallback");
        }
        System.out.println("PASS 3 completeOnTimeout: fallback persisted, worker continued");
    }

    static void isolatedView(ExecutorService pool) throws Exception {
        try (Work w = new Work()) {
            CompletableFuture<String> source = CompletableFuture.supplyAsync(w::supply, pool);
            await(w.started);
            CompletableFuture<String> view = source.copy().orTimeout(30, MS);
            expectTimeout(view);
            check(!source.isDone(), "view timeout changed source");
            w.stillRunning();
            w.release.countDown();
            check(source.get(5, SEC).equals("real"), "source result lost");
            expectTimeout(view);
        }
        System.out.println("PASS 4 copy: caller view timed out, source succeeded");
    }

    static void cancelCompletable(ExecutorService pool) throws Exception {
        try (Work w = new Work()) {
            CompletableFuture<String> f = CompletableFuture.supplyAsync(w::supply, pool);
            await(w.started);
            CompletableFuture<Integer> child = f.thenApply(String::length);
            check(f.cancel(true), "cancel failed");
            check(f.isCancelled(), "source not cancelled");
            try {
                f.join();
                throw new AssertionError("expected CancellationException");
            } catch (CancellationException expected) {
                w.stillRunning();
            }
            try {
                child.join();
                throw new AssertionError("expected wrapped cancellation");
            } catch (CompletionException e) {
                check(e.getCause() instanceof CancellationException, "wrong child cause");
                check(!child.isCancelled(), "child cancelled directly");
            }
            w.release.countDown();
            await(w.exited);
            check(!w.interrupted.get(), "cancel(true) interrupted supplier");
        }
        System.out.println("PASS 5 cancel CF: supplier not interrupted, child failed");
    }

    static void cancelOwned(ExecutorService pool) throws Exception {
        try (Work w = new Work()) {
            FutureTask<String> task = new FutureTask<>(w);
            pool.execute(task);
            await(w.started);
            try {
                awaitOwned(task, 30, MS);
                throw new AssertionError("expected wait timeout");
            } catch (TimeoutException expected) {
                check(task.isCancelled(), "task not cancelled");
                await(w.exited);
                check(w.interrupted.get(), "worker did not observe interrupt");
            }
        }
        System.out.println("PASS 6 owned FutureTask: timeout requested interrupt, worker exited");
    }

    public static void main(String[] args) throws Exception {
        ExecutorService pool = new ThreadPoolExecutor(
                1, 1, 0, SEC, new ArrayBlockingQueue<>(8),
                r -> new Thread(r, "timeout-lab-worker"),
                new ThreadPoolExecutor.AbortPolicy());
        try {
            getTimeout(pool);
            orTimeout(pool);
            fallback(pool);
            isolatedView(pool);
            cancelCompletable(pool);
            cancelOwned(pool);
            System.out.println("ALL 6 CASES PASSED");
        } finally {
            pool.shutdownNow();
            check(pool.awaitTermination(5, SEC), "pool did not terminate");
        }
    }
}
```

## 四、逐步解释实验结果

### 1. 限制本次等待：get(timeout)

第一组先确认 supplier 已经开始，再执行限时等待。主线程收到 `TimeoutException` 后，f 仍未完成，工作线程还停在门闩上。显式放行后，f 能正常得到 `real`。

这适用于“调用方只等一小段时间，任务完成后仍有价值”的情况，例如一个由多个请求共享的缓存加载。若重复调用 `get(30, MS)`，每次都是新的等待预算，并不会自动变成从第一次调用起累计 30 毫秒的总截止时间。

### 2. 改变结果状态：orTimeout

第二组显式检查 `f.orTimeout(...) == f`。它返回原对象，给同一结果增加超时完成竞争，并没有创建独立包装 Future。超时后 `isCancelled()` 为 false，因为这里是超时异常完成，不是调用了取消。

此时后台 Work 仍等待放行。即使放行并执行到退出节点，f 的超时结果也保留。程序中并未发生业务写入；如果将 Work 替换成写库、发消息等动作，Future 的结果状态本身无法阻止这些副作用。

### 3. 降级是正常结果：completeOnTimeout

第三组返回字符串 `fallback`，`isCompletedExceptionally()` 为 false。后续只处理正常结果的阶段可以继续执行，监控若只统计 Future 异常，就可能遗漏这次降级。

业务上应让降级结果带有明确来源，例如区分“真实查询为空”和“上游超时后使用旧缓存”。不能用正常结果隐藏资金、库存等写操作的执行状态；超时后重试前仍需查询状态或使用幂等键。

### 4. 独立结果视图：copy

第四组给 `source.copy()` 增加超时：视图失败，source 仍未完成；放行后 source 正常得到结果，而视图保留自己的超时结果。

这里隔离的是结果状态，source 与视图仍依赖同一个后台计算。它适合共享加载时为每个调用方设不同等待期限。若直接在共享 source 上调用 `orTimeout`，最短期限可能改变所有持有者看到的结果。

`copy()` 也不是深拷贝：成功时传递同一个结果值，可变对象仍需要线程安全设计。source 异常时复制视图的异常包装也有差异，不能仅靠包装层数判断是否为业务错误。

### 5. 取消 CompletableFuture 与取消执行任务

第五组先建立依赖阶段 child，再取消 f。f 的 `join()` 直接抛 `CancellationException`；child 的 `join()` 抛 `CompletionException`，原因为取消异常，但 child 的 `isCancelled()` 为 false。只检查依赖阶段的取消标志可能漏掉上游取消。

更关键的是，`cancel(true)` 后 supplier 并未收到中断。CompletableFuture 的取消主要描述结果状态，它不拥有一个通用的“杀掉 supplier”操作。非 Async 的后续动作还可能在完成该阶段的线程中执行，不能在其中放置长时间阻塞的日志、查询或清理。[CompletableFuture 的取消、copy 与执行策略](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/CompletableFuture.html)

## 五、需要停止独占任务时，保存真正的取消句柄

第六组把 Work 包装成 `FutureTask` 后交给执行器。主线程在等待超时后调用 `task.cancel(true)`。本次任务阻塞在支持中断的 `CountDownLatch.await()`，因此它收到 `InterruptedException`、执行 finally 并退出。FutureTask 与 CompletableFuture 的角色不同，不能仅凭它们都实现 Future 就推断取消行为相同。[FutureTask API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/FutureTask.html)

代码中的 `awaitOwned` 演示两条路径：等待超时或等待线程被中断，都向独占任务发出取消请求，再把原异常向上传递。调用者仍能区分 `TimeoutException`、`InterruptedException` 和任务失败对应的 `ExecutionException`。如果上层无法继续抛出 `InterruptedException`，需要恢复当前线程中断标志，并结束当前操作，不能捕获后继续无限重试。

这里的“独占”是必要前提：一个请求退出，不应取消其他请求仍需要的共享任务。异步接口可以同时持有“结果阶段”和“底层任务 / 客户端调用的取消句柄”，由明确的所有者协调；仅对依赖阶段调用 `cancel` 不会自动沿调用链取消整个计算图。

### 中断是协作协议

`cancel(true)` 是取消尝试，返回后不能据此断言资源已释放。本例额外等待 `exited`，再检查任务确实观察到了中断。实际业务应在 finally 或 try-with-resources 中关闭自己拥有的资源，并通过任务退出、连接归还等指标确认清理。

CPU 循环需要周期性检查中断并主动退出；阻塞 I/O 是否支持中断取决于具体 API。数据库、HTTP 客户端和驱动应分别配置其支持的执行超时与取消机制，不要把线程中断当作远端事务回滚保证。[Thread.interrupt 的 API 语义](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Thread.html#interrupt())

本文的取消对照只验证门闩这种可中断等待，不验证 JDBC、网络请求或不可中断的原生调用。不要使用强制停止线程的方法代替协作取消。

## 六、生产实践：总预算、排队和负载治理

### 1. 明确预算从哪里开始

实验为了固定时序，等到任务开始后才设置超时。生产请求通常需要从入口计算总预算，包含提交、线程池排队、连接池等待、网络和下游执行。

`awaitOwned` 只限制进入 `get` 后的等待，不是完整请求截止时间实现。生产代码可在入口记录 `System.nanoTime()`，在每次等待前从总预算减去已耗时；预算耗尽就不再发起下一步。进程内耗时使用该单调时间源的差值，不应使用可受校时影响的墙钟时间，也不能把原始 nanoTime 值当作跨进程时间戳。[System.nanoTime 文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html#nanoTime())

重试、退避和多个依赖调用都消耗同一总预算。调用方视图的定时器也不是实时中断装置，超时处理可能受线程调度和执行环境影响，不能承诺精确在第 30 毫秒完成所有清理。

### 2. 控制实际工作量

实验显式使用 1 个工作线程、容量 8 的队列和 AbortPolicy。容量仅为了实验，不能作为生产推荐值。实际系统应记录队列长度、排队耗时、执行耗时、拒绝量与超时后仍运行的任务数，再按资源容量设置并发上限。

超时后立刻重试，而旧任务未停止，可能使同一业务同时占用更多线程和连接。应结合重试上限、幂等、退避、限流和熔断治理。不要仅把外层 Future 的超时时间调小，就认定线程池负载已经下降。

取消排队中的 FutureTask 不一定马上把其对象从执行器队列中移除；大量取消时还要观察队列容量及对象滞留，并评估 ThreadPoolExecutor 提供的 `remove` / `purge` 等维护方式。拒绝必须成为调用方能观察到的失败，静默丢弃可能让等结果的一方一直挂起。[ThreadPoolExecutor 的队列、拒绝与维护](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)

### 3. 避免执行器依赖死锁

若某个单线程池的工作任务又向同一池提交子任务，并调用 `get` 等待它，子任务只能排队，父任务却占着唯一线程。外层增加超时最多让故障晚一些暴露，不能修复依赖关系。

应梳理执行器的使用边界，避免工作线程同步等待同池排队任务，或使用组合式阶段衔接。耗时阻塞任务显式选择执行器；使用 Async 后缀也仍需考虑所选执行器是否有能力运行后续动作。

程序末尾的 `shutdownNow()` 和有界 `awaitTermination` 是独立实验进程的清理手段，会尝试中断任务。线上共享池应由应用生命周期统一关闭，不能在每次请求结束时关闭。中断无法迫使不响应的任务退出，关闭策略也要有超时和诊断。[ExecutorService 生命周期](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/ExecutorService.html)

## 七、常见错误与排查顺序

| 现象 | 优先检查 | 验证方法 |
| --- | --- | --- |
| 请求已超时，线程仍繁忙 | 是否只改变了结果状态 | 分别记录请求返回时间和任务 finally 退出时间 |
| 一位调用者设超时，其他调用者也失败 | 是否共享同一个 f 并直接调用 orTimeout | 检查引用身份，对每个调用方建立复制视图 |
| cancel(true) 后没有中断 | 取消的是 CompletableFuture 还是底层任务句柄 | 记录句柄类型、取消结果与任务中断处理 |
| isCancelled 为 false 却因取消失败 | 是否只是依赖阶段异常完成 | 查看异常原因链，不只判断当前阶段标志 |
| 监控显示成功，但大量用户拿到旧值 | 降级是否被统计为普通成功 | 给结果来源与超时降级建立独立计数 |
| 超时越来越多，队列仍增长 | 旧任务未退出、重试放大或排队不在预算内 | 对齐排队、执行、下游等待和任务退出指标 |
| 示例报 wrong cause 或保护超时 | 是否发生拒绝、人工中断或机器过载 | 保留完整异常链与线程信息，先定位前一失败 |
| cannot find symbol: orTimeout/copy | 编译器版本或 --release 过旧 | 对照 java、javac 路径和版本 |

排查时先找负责实际工作的线程及资源所有者，再追踪谁能取消它；单看 Future 的 `isDone()` 无法证明业务代码已经结束。日志只记录必要的任务标识和状态，避免把凭据、完整请求体或敏感查询参数写进超时异常。

恢复配置时应通过可控发布回退并发、预算或降级策略；已经提交的业务副作用必须按业务恢复流程处理，不能靠把 Future 重新设为成功来“恢复”。
