两个 worker 同时查询待处理任务，如果都先用普通 `SELECT` 读出第一条，再按主键更新，就可能先后处理同一个任务。这里有两个独立的问题：怎样让两个事务领取不同的行，以及怎样在领取后释放数据库锁，同时保留谁领到了任务的证据。

本文用两个 SQL*Plus 会话先复现读一致性、快速失败和限时等待，再用一个 PL/SQL 游标实现每次领取一条任务。最后通过提交和回滚区分游标、数据库事务和任务状态的生命周期。

## 二、先区分一致性读和行锁

普通 `SELECT` 在 `READ COMMITTED` 下读的是语句开始时的一致性视图。若另一会话有尚未提交的修改，Oracle 可借助 undo 返回此前提交的版本。`SELECT ... FOR UPDATE` 还要拿到可供当前事务更新的行锁，因此会与另一事务对同一行的写入或加锁冲突。

Oracle 用 TX 事务锁协调这类等待，也会为 DML 和锁定读取得 TM 表锁。常见的 DML 表锁模式允许另一个事务修改同表的其他行，并阻止不兼容的 DDL。锁住一行的事务在提交或完整回滚时释放该行锁。只关闭结果集、游标或语句，事务仍可能保持打开。[Oracle Database 19c Concepts：Data Concurrency and Consistency](https://docs.oracle.com/en/database/oracle/oracle-database/19/cncpt/data-concurrency-and-consistency.html)

### 1. A 锁住第一行

A 先锁住 `id = 1`，再更改 `note`，保留其 `READY` 状态。执行完留在提示符，暂时不要提交或回滚。

```sql
SELECT id, status, note FROM lock_claim_lab WHERE id = 1 FOR UPDATE;
UPDATE lock_claim_lab SET note = 'uncommitted-A' WHERE id = 1;
```

### 2. B 读旧值，随后试图加锁

在 B 运行下面三个查询。先看到 `1 / READY / first`。第二条应快速返回锁冲突。第三条在 A 持锁期间等到超时后报错。`WAIT 2` 为该行的锁冲突给出两秒等待窗口，SQL*Plus 显示的语句总耗时还包含客户端和数据库执行开销。错误码要结合数据库版本和执行路径解读。Oracle 将 `ORA-30006` 列为一种等待到期错误，本实验的 26ai Free 对两条查询均返回 `ORA-00054`，并附 `ORA-40097`，可以通过计时和等待视图区分。

```sql
SELECT id, status, note FROM lock_claim_lab WHERE id = 1;
SELECT id FROM lock_claim_lab WHERE id = 1 FOR UPDATE NOWAIT;
SELECT id FROM lock_claim_lab WHERE id = 1 FOR UPDATE WAIT 2;
ROLLBACK;
```

`ROLLBACK` 结束 B 的当前事务，不会撤销 A 的修改。应用收到某条语句的锁错误后，应按业务边界显式决定整笔事务是否回滚。此前在同一事务中成功的语句可能仍然有效。实验也可在此处让 B 发起无修饰的 `FOR UPDATE`，通过第六节观察等待，再从 B 取消当前语句并回滚。保持 A 的锁，继续下一节。[Oracle 错误说明 ORA-00054](https://docs.oracle.com/en/error-help/db/ora-00054/)，[ORA-30006](https://docs.oracle.com/en/error-help/db/ora-30006/)，[ORA-40097](https://docs.oracle.com/en/error-help/db/ora-40097/)

| 写法 | 遇到本实验中的行锁冲突 | 典型用途 |
| --- | --- | --- |
| `FOR UPDATE` | 等锁释放 | 单一操作允许等待，并另有调用超时控制 |
| `FOR UPDATE NOWAIT` | 立即返回锁冲突 | 交互式操作需要快速提示，或上层统一调度重试 |
| `FOR UPDATE WAIT 2` | 行锁等待到期后返回错误 | 允许短暂排队的交互操作 |
| `FOR UPDATE SKIP LOCKED` | 跳过被其他事务锁住的候选行 | 多消费者领取任务 |

`WAIT` 和 `SKIP LOCKED` 对排他表锁有不同于行锁的行为。若表被排他锁定，两者都可能阻塞到表锁释放，`WAIT 2` 也不能把这种等待限制在两秒内。应用的请求预算应同时覆盖数据库调用、驱动取消后的事务清理和网络超时。[Oracle Database 19c SQL Language Reference：SELECT](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/SELECT.html)

## 三、用 SKIP LOCKED 每次领取一条

把以下块保存为 `claim_one.sql`，在 B 执行 `@claim_one.sql`，也可把整块连同 `/` 粘贴进 B。脚本每次只取一行，在同一事务中把这行从 `READY` 改为 `RUNNING`，写入领取方和数据库时间。脚本结束后由调用方决定提交或回滚。

```sql
DECLARE
    CURSOR ready_jobs IS
        SELECT id
        FROM lock_claim_lab
        WHERE status = 'READY'
        ORDER BY id
        FOR UPDATE SKIP LOCKED;
    l_id lock_claim_lab.id%TYPE;
BEGIN
    OPEN ready_jobs;
    FETCH ready_jobs INTO l_id;

    IF ready_jobs%NOTFOUND THEN
        DBMS_OUTPUT.PUT_LINE('NO_CLAIM');
    ELSE
        UPDATE lock_claim_lab
        SET status = 'RUNNING',
            claimed_by = 'worker-B',
            claimed_at = SYSTIMESTAMP
        WHERE CURRENT OF ready_jobs;
        DBMS_OUTPUT.PUT_LINE('CLAIMED_ID=' || l_id);
    END IF;

    CLOSE ready_jobs;
END;
/
```

`ORDER BY id` 确定本次扫描候选行的顺序。`SKIP LOCKED` 允许越过头部被锁住的行，因此领取次序不保证全局 FIFO。普通 `FOR UPDATE` 游标在打开时锁定结果集，而带 `SKIP LOCKED` 的游标在 `FETCH` 时锁定取到的行。这里显式取一行，再用 `WHERE CURRENT OF` 更新游标定位的行。`worker-B` 是示例标识，实际应用应传入能区分 worker 的值。`claimed_at` 便于检查卡住的任务，示例尚未实现租约。仅看到 `CLAIMED_ID` 代表事务已执行更新，领取结果在成功提交后才对其他会话可见。[Oracle Database 19c PL/SQL Language Reference：Transaction Processing and Control](https://docs.oracle.com/en/database/oracle/oracle-database/19/lnpls/transaction-processing-and-control.html)

Oracle Database 19c 的 `row_limiting_clause` 不能与 `FOR UPDATE` 同用，所以这里在 PL/SQL 中只取一行。26ai 在线 SQL 参考列出了部分支持组合，应按部署的具体更新版本核对。若先把候选范围硬截为最前一条，再跳过该行，后面明明有空闲任务也可能领不到。用 JDBC 改写时，还应验证驱动的预取行为及真实加锁范围。[Oracle Database 19c SELECT](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/SELECT.html)，[Oracle AI Database 26ai SELECT](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/SELECT.html)

## 四、验证关闭游标、提交和回滚

1. **B 领取第二行。** A 仍持有第一行的锁。B 运行领取脚本后预期显示 `CLAIMED_ID=2`，暂不提交。
2. **A 探测第二行。** 以下第一条普通查询仍看到 `2 / READY`，第二条返回 `ORA-00054`。此时 B 的游标已经关闭，但 B 的事务还持有第二行的锁。

```sql
SELECT id, status FROM lock_claim_lab WHERE id = 2;
SELECT id FROM lock_claim_lab WHERE id = 2 FOR UPDATE NOWAIT;
```

3. **B 提交并再次尝试。** 在 B 执行 `COMMIT`，再运行领取脚本。第一行仍被 A 锁住，第二行已经是 `RUNNING`，结果为 `NO_CLAIM`。执行 `ROLLBACK` 结束这次尝试。`NO_CLAIM` 表示本次没有拿到可领取的行，队列里可能仍有被锁住的任务。
4. **A 回滚。** 在 A 执行 `ROLLBACK`，第一行恢复 `note = 'first'` 并释放锁。随后在 B 再运行领取脚本，预期 `CLAIMED_ID=1`。这次在 B 执行 `ROLLBACK`，验证未提交的领取可以撤销。
5. **任一会话核对最终状态。** 运行下面的查询。第一行应为 `READY / first`，领取者和领取时间均为空。第二行应为 `RUNNING / second / worker-B`，领取时间非空。

```sql
SELECT id, status, note, claimed_by,
       CASE WHEN claimed_at IS NULL THEN 'NO' ELSE 'YES' END AS has_claim_time
FROM lock_claim_lab
ORDER BY id;
```

这个过程包含两个恢复边界。提交前失败可用回滚撤销领取，提交后 worker 退出则会留下 `RUNNING` 记录。处理后者需要应用定义任务超时与重新领取规则。

## 五、把领取放进真实的 worker

- **缩短事务。** 在同一个连接中完成加锁、状态变更和提交，再执行外部 I/O。若先在一个连接里锁定，再借另一个连接更新，后者会和前者竞争同一把锁。使用连接池时，每次归还连接前都要结束事务。
- **补齐状态机。** 可为任务增加完成状态、尝试次数、到期时间和每次领取唯一的 token。回收方通过带旧状态和到期条件的更新回收，完成方用 `WHERE id = :id AND status = 'RUNNING' AND claim_token = :token` 限定本轮领取，并检查更新行数。这样旧 worker 在租约过期后返回时，无法覆盖新一轮领取的状态。外部请求仍应使用幂等键，避免重复执行副作用。
- **处理结果不明确。** 若数据库已提交，但网络在响应到达前断开，客户端可能无法立刻判断领取是否成功。保留可查询的领取 token 或请求标识，重连后按标识核对，再决定是否重试。
- **控制扫描与重试。** 如果 `READY` 在大表中只占小部分，可评估 `(status, id)` 索引是否减少扫描，同时测量高频状态切换带来的索引写入成本。没有可领记录时做有上限的退避和抖动，监控最老待领任务的年龄、领取失败率和锁等待。批量领取时同时限制批量大小与事务时长。
- **有序加锁。** 若一个事务需要锁定多行或跨多个表，给同类操作制定一致的加锁顺序。收到 `ORA-00060` 时收集死锁信息并结束受影响的业务事务，具备幂等性时再有限重试。成熟的消息投递、保留和消费需求可评估数据库自带的 Advanced Queuing。[Oracle Database 19c Advanced Queuing User’s Guide](https://docs.oracle.com/en/database/oracle/oracle-database/19/adque/index.html)

## 六、诊断等待与清理实验

对于正在等待的会话，可由 DBA 在同一测试 PDB 用下面的只读查询识别阻塞者。把 `123` 换成 B 的 SID，`DEFINE` 是 SQL*Plus 的文本替换命令，此处只填写数值。在 B 被阻塞时采样，`blocking_session_status = 'VALID'` 才表示阻塞实例和会话字段有效。RAC 中要用 `GV$SESSION` 的 `INST_ID` 和 `SID` 共同定位。`SQL_ID` 指当前语句，若持锁方空闲，往往还需结合应用事务日志和连接池记录找到早先执行的 DML。[Oracle Database 19c Reference：V$SESSION](https://docs.oracle.com/en/database/oracle/oracle-database/19/refrn/V-SESSION.html)

```sql
SET LINESIZE 220
COLUMN username FORMAT A18
COLUMN module FORMAT A20
COLUMN event FORMAT A36
COLUMN state FORMAT A12
DEFINE waiter_sid = 123
SELECT sid, serial#, username, module, sql_id, event, state,
       blocking_session_status, blocking_instance, blocking_session
FROM v$session
WHERE sid = &waiter_sid;
UNDEFINE waiter_sid
```

| 现象 | 排查方向 |
| --- | --- |
| `ORA-00054` 或 `ORA-30006` | 先检查谁持锁、锁等多久、事务在哪里结束。短时间内已返回的失败可能无法用视图复现，可使用两会话重现并在等待期间采样。 |
| `SKIP LOCKED` 仍卡住 | 检查是否有人持有排他表锁或执行与 DML 冲突的操作。区分 TX、TM 等等待后再选择处理方式。 |
| 第二个 worker 也领到了第一行 | 检查两次领取是否在独立会话，以及锁定读、状态更新和提交是否在同一个事务内。重点排查自动提交及连接切换。 |
| 长期存在 `RUNNING` | 检查 worker 是否在提交领取后退出，回收策略是否按租约处理，以及完成操作是否校验本轮领取标识。 |

实验结束后，在 A、B 各执行 `ROLLBACK`，再由 A 执行下列命令。`DROP TABLE` 删除实验表和样本，执行后不能靠 `ROLLBACK` 恢复。先确认当前用户、PDB 和表归属，且没有未提交的其他工作。若需恢复这两条样本，重新执行第一节的建表与插入脚本。

```sql
DROP TABLE lock_claim_lab;
```

当任务允许任意 worker 领取时，使用 `SKIP LOCKED` 处理行竞争，在同一短事务内记录领取结果。把提交当作进入任务执行阶段的边界，再用幂等、租约和可核对的领取标识应对进程中断与重试。
