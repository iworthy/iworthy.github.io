三个订单各分摊一笔 10.00 元的费用，每单保留两位小数，结果都是 3.33 元，合计却只有 9.99 元。另一个系统虽然全程使用 BigDecimal，逐项计算税额后再汇总，仍然和按总额计算的结果差一分钱。

BigDecimal 能表达十进制数，但金额正确性还需要明确输入、计算、结算和分摊规则。本文围绕“如何让舍入可解释、分摊可复现、总额可核对”展开，并提供不依赖第三方库的完整程序。

## 一、适用场景、版本与实验约定

适合处理费用分摊、账单核对、金额接口校验的 Java 开发人员，以及需要复现“一分钱差异”的运维人员。读者应了解 Java 集合、异常和整数除法。

## 二、先分清数值、表示和精度

### 2.1 十进制输入必须保留到构造边界

`new BigDecimal("0.1")` 与 `new BigDecimal(0.1)` 的来源不同：后者接收已经形成的二进制浮点值。`BigDecimal.valueOf(double)` 使用 double 的规范字符串，也不能恢复先前浮点计算丢失的信息。完整程序会验证 `valueOf(0.1 + 0.2)` 不等于十进制 0.3。[BigDecimal 构造与 valueOf](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/math/BigDecimal.html)

因此接口应保留原始十进制文本或直接映射为 BigDecimal，不要先转成 double 再转换回来。金额与币种需要一起传递；两个数字都叫 10.00，并不说明它们可以相加。

### 2.2 scale 和 precision 回答不同问题

可以用 `unscaledValue × 10^(-scale)` 理解表示。程序中 `123.450` 的 unscaledValue 是 123450、scale 是 3、precision 是 6；`1.0` 与 `1.00` 数值相同，但表示不同。

数值比较使用 `compareTo`；`equals` 还检查 scale。程序用两个集合复现差别：HashSet 保留 `1.0` 和 `1.00` 两个元素，TreeSet 按自然顺序只保留一个。业务键应先定义规范形式，不能指望更换集合实现后语义保持一致。[BigDecimal 比较规则](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/math/BigDecimal.html#equals(java.lang.Object))

`setScale(2, mode)` 约束小数位；`new MathContext(2, mode)` 约束有效数字总数。对 1234.567，前者得到 1234.57，后者得到数值 1200。`MathContext.DECIMAL128` 也不是“金额自动正确”开关。[JDK MathContext](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/math/MathContext.html)

BigDecimal 不可变，`setScale`、`add` 等返回新值。调用后必须接收结果；忽略返回值不会修改原对象。

## 三、舍入规则必须同时定义时点和方向

### 3.1 同一 HALF_UP，换个时点也会改变结果

假设两条明细的精确税额都是 `0.05 × 0.10 = 0.005`：

| 策略 | 计算过程 | 结果 |
| --- | --- | --- |
| 明细结算，再求和 | 0.005 → 0.01，各算两次 | 0.02 |
| 先汇总精确值，再结算 | 0.005 + 0.005 → 0.01 | 0.01 |

两种结果都符合各自规则。系统必须明确法定或合同上的结算对象是明细还是整单，记录计算规则版本，并让展示、入账和对账沿用同一规则。不要只在公共工具里写一个 `round()`，却让不同调用方决定何时调用。

对不能整除的比例还要定义中间精度。完整程序验证 `1 ÷ 3` 的精确除法会报错；指定两位后是 0.33。另一个易漏点是 `divide(divisor, roundingMode)` 使用被除数的 scale：`1 ÷ 8` 在这个重载下会得到 0。金额除法应明确写出目标 scale，而不是依赖输入碰巧带了几位小数。[BigDecimal divide](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/math/BigDecimal.html#divide(java.math.BigDecimal,int,java.math.RoundingMode))

连续两次舍入也可能改变结果。程序中的 1.2449 先舍入到三位再到两位得到 1.25，直接舍入到两位得到 1.24。因此“多保留一位最后再舍入”不构成通用正确性证明；应为具体公式规定精度，并覆盖边界值。

### 3.2 退款场景不能把 DOWN 当作向下取整

下面结果由完整程序验证，目标 scale 均为 2：

| 输入 | HALF_UP | HALF_EVEN | DOWN | FLOOR |
| --- | --- | --- | --- | --- |
| 1.225 | 1.23 | 1.22 | 1.22 | 1.22 |
| -1.225 | -1.23 | -1.22 | -1.22 | -1.23 |

DOWN 朝零截断，FLOOR 朝负无穷；HALF_UP 遇到中点远离零，HALF_EVEN 遇到中点使保留末位为偶数。选择哪一种需要业务决定，不能仅凭“四舍五入”四个字推导负数行为。[JDK RoundingMode](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/math/RoundingMode.html)

`UNNECESSARY` 适合表达“此处必须已经精确”：需要丢弃非零数位就抛异常。它用于验证边界，不用于替调用方挑选舍入政策。

## 四、从整数最小单位推导守恒分摊

本文采用最大余数法。设总额的绝对值是 T 分，各权重为 wᵢ，权重和为 W：

1. 对每项计算整数商 qᵢ 和余数 rᵢ，使 `T × wᵢ = qᵢ × W + rᵢ`，且 `0 ≤ rᵢ < W`。
2. 先分配 qᵢ 分，剩下 `L = T - Σqᵢ` 分。
3. 按 rᵢ 从大到小排列，前 L 项各加一分；余数相同按输入顺序。
4. 如果原总额为负，每一项再取负，最后把整数分转换成固定两位小数。

例如 T=1000、权重为 1/1/1，每项商为333，余数为1，剩余一分交给第一项，结果为 3.34/3.33/3.33。

这个算法不需要把比例近似成小数。因为各精确份额之和为 T，L 等于各小数部分之和，所以 L 是非负整数且小于项数。补上 L 分后总额严格守恒；每项与精确份额的误差小于一分。零权重项余数为零，也不会抢到应分给正余数项的尾差。

乘积 `T × wᵢ` 和 W 可能超过 long，代码使用 BigInteger 保存中间整数，通过 `divideAndRemainder` 一次取得商与余数。[JDK BigInteger](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/math/BigInteger.html#divideAndRemainder(java.math.BigInteger))

**顺序也是业务输入。** 数据库查询如果没有稳定排序，同一账单重算可能把那一分钱交给不同明细。生产实现应按持久化明细 ID 确定顺序，并保存总额、权重、顺序和算法版本。相同输入下本文结果确定，不代表每个参与者长期累计获得尾差的机会均等。

本算法还不处理“折扣不能超过商品可抵扣金额”等逐项上限；有上限时需要另外设计受约束的分配规则。退款若是冲销已入账交易，优先反向使用原分摊记录，而不是用当前权重重新计算。

## 五、完整可运行程序

保存下面内容为临时实验目录中的 `MoneyLab.java`。`parseMoney` 是文本入口；`allocate` 只接受已经规范为 scale=2 的金额、最多10000项权重，并限制金额 precision 不超过18。负 scale、超长指数文本和科学记数法不在本文接口合同内。

```java
import java.math.BigDecimal;
import java.math.BigInteger;
import java.math.MathContext;
import java.math.RoundingMode;
import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.TreeSet;

public final class MoneyLab {
    private static final int SCALE = 2;
    private static final int MAX_ITEMS = 10_000;

    public static BigDecimal parseMoney(String text) {
        if (text == null || text.length() > 20
                || !text.matches("-?[0-9]{1,16}(?:\\.[0-9]{1,2})?")) {
            throw new IllegalArgumentException("Invalid money text");
        }
        return new BigDecimal(text).setScale(SCALE, RoundingMode.UNNECESSARY);
    }

    public static List<BigDecimal> allocate(BigDecimal total, long... weights) {
        if (total == null || total.scale() != SCALE || total.precision() > 18) {
            throw new IllegalArgumentException("Expected bounded scale-2 total");
        }
        if (weights == null || weights.length == 0 || weights.length > MAX_ITEMS) {
            throw new IllegalArgumentException("Invalid item count");
        }
        BigInteger weightSum = BigInteger.ZERO;
        for (long weight : weights) {
            if (weight < 0) throw new IllegalArgumentException("Negative weight");
            weightSum = weightSum.add(BigInteger.valueOf(weight));
        }
        if (weightSum.signum() == 0) {
            throw new IllegalArgumentException("Zero weight sum");
        }

        BigInteger units = total.unscaledValue().abs();
        BigInteger[] parts = new BigInteger[weights.length];
        BigInteger[] remainders = new BigInteger[weights.length];
        List<Integer> order = new ArrayList<>(weights.length);
        BigInteger assigned = BigInteger.ZERO;
        for (int i = 0; i < weights.length; i++) {
            BigInteger[] qr = units.multiply(BigInteger.valueOf(weights[i]))
                    .divideAndRemainder(weightSum);
            parts[i] = qr[0];
            remainders[i] = qr[1];
            assigned = assigned.add(qr[0]);
            order.add(i);
        }
        order.sort((i, j) -> {
            int byRemainder = remainders[j].compareTo(remainders[i]);
            return byRemainder != 0 ? byRemainder : Integer.compare(i, j);
        });
        int left = units.subtract(assigned).intValueExact();
        if (left < 0 || left >= weights.length) {
            throw new IllegalStateException("Remainder invariant failed");
        }
        for (int k = 0; k < left; k++) {
            int i = order.get(k);
            parts[i] = parts[i].add(BigInteger.ONE);
        }

        List<BigDecimal> result = new ArrayList<>(weights.length);
        BigDecimal sum = new BigDecimal(BigInteger.ZERO, SCALE);
        for (BigInteger part : parts) {
            BigDecimal amount = new BigDecimal(
                    total.signum() < 0 ? part.negate() : part, SCALE);
            result.add(amount);
            sum = sum.add(amount);
        }
        require(sum.equals(total), "Allocation must preserve total and scale");
        return List.copyOf(result);
    }

    private static BigDecimal d(String text) {
        return new BigDecimal(text);
    }

    private static void require(boolean condition, String message) {
        if (!condition) throw new AssertionError(message);
    }

    private static void exact(BigDecimal actual, String expected) {
        require(actual.equals(d(expected)), "Unexpected decimal: " + actual);
    }

    private static void fails(Class<? extends RuntimeException> type, Runnable r) {
        try {
            r.run();
        } catch (RuntimeException e) {
            if (type.isInstance(e)) return;
            throw e;
        }
        throw new AssertionError("Expected " + type.getSimpleName());
    }

    public static void main(String[] args) {
        require(new BigDecimal(0.1).compareTo(d("0.1")) != 0, "double source");
        exact(BigDecimal.valueOf(0.1), "0.1");
        require(BigDecimal.valueOf(0.1 + 0.2).compareTo(d("0.3")) != 0,
                "valueOf cannot repair previous arithmetic");
        System.out.println("PASS 01 decimal input boundary");

        exact(parseMoney("12.3"), "12.30");
        fails(IllegalArgumentException.class, () -> parseMoney("12.345"));
        fails(IllegalArgumentException.class, () -> parseMoney("1e9"));
        fails(ArithmeticException.class,
                () -> d("12.345").setScale(2, RoundingMode.UNNECESSARY));
        System.out.println("PASS 02 strict money input");

        BigDecimal a = d("1.0"), b = d("1.00");
        require(a.compareTo(b) == 0 && !a.equals(b), "comparison");
        require(new HashSet<>(List.of(a, b)).size() == 2, "hash equality");
        require(new TreeSet<>(List.of(a, b)).size() == 1, "natural order");
        BigDecimal representation = d("123.450");
        require(representation.unscaledValue().equals(BigInteger.valueOf(123450))
                && representation.scale() == 3 && representation.precision() == 6,
                "representation");
        System.out.println("PASS 03 scale and equality");

        fails(ArithmeticException.class, () -> d("1").divide(d("3")));
        exact(d("1").divide(d("3"), 2, RoundingMode.HALF_UP), "0.33");
        exact(d("1").divide(d("8"), RoundingMode.HALF_UP), "0");
        exact(d("1").divide(d("8"), 2, RoundingMode.HALF_UP), "0.13");
        System.out.println("PASS 04 explicit division scale");

        exact(d("1234.567").setScale(2, RoundingMode.HALF_UP), "1234.57");
        require(d("1234.567").round(new MathContext(2, RoundingMode.HALF_UP))
                .compareTo(d("1200")) == 0, "significant digits");
        BigDecimal immutable = d("1.234");
        immutable.setScale(2, RoundingMode.HALF_UP);
        exact(immutable, "1.234");
        System.out.println("PASS 05 precision is not scale");

        BigDecimal tax = d("0.05").multiply(d("0.10"));
        exact(tax.setScale(2, RoundingMode.HALF_UP).multiply(d("2")), "0.02");
        exact(tax.multiply(d("2")).setScale(2, RoundingMode.HALF_UP), "0.01");
        exact(d("1.2449").setScale(3, RoundingMode.HALF_UP)
                .setScale(2, RoundingMode.HALF_UP), "1.25");
        exact(d("1.2449").setScale(2, RoundingMode.HALF_UP), "1.24");
        System.out.println("PASS 06 rounding boundaries");

        RoundingMode[] modes = {RoundingMode.HALF_UP, RoundingMode.HALF_EVEN,
                RoundingMode.DOWN, RoundingMode.FLOOR};
        String[] positive = {"1.23", "1.22", "1.22", "1.22"};
        String[] negative = {"-1.23", "-1.22", "-1.22", "-1.23"};
        for (int i = 0; i < modes.length; i++) {
            exact(d("1.225").setScale(2, modes[i]), positive[i]);
            exact(d("-1.225").setScale(2, modes[i]), negative[i]);
        }
        System.out.println("PASS 07 signed rounding modes");

        List<BigDecimal> thirds = allocate(parseMoney("10.00"), 1, 1, 1);
        require(thirds.equals(List.of(d("3.34"), d("3.33"), d("3.33"))), "thirds");
        System.out.println("PASS 08 thirds = " + thirds);

        List<BigDecimal> weighted = allocate(parseMoney("0.05"), 0, 1, 2);
        require(weighted.equals(List.of(d("0.00"), d("0.02"), d("0.03"))), "weights");
        System.out.println("PASS 09 weighted = " + weighted);

        List<BigDecimal> refund = allocate(parseMoney("-0.01"), 1, 1, 1);
        require(refund.equals(List.of(d("-0.01"), d("0.00"), d("0.00"))), "refund");
        fails(IllegalArgumentException.class, () -> allocate(parseMoney("1"), 0, 0));
        fails(IllegalArgumentException.class, () -> allocate(parseMoney("1"), -1, 2));
        System.out.println("PASS 10 refund = " + refund);
        System.out.println("ALL 10 CASES PASSED");
    }
}
```

`fails` 只接受预期异常类型，错误类型不同或完全没有报错都会令程序失败。检查使用显式 AssertionError，不依赖可能被关闭的 Java `assert`。运行失败时进程返回非零，适合接入 CI。

`parseMoney` 允许 `12`、`12.3`、`12.30`，统一输出两位；拒绝空白、加号、千分位、指数及三位小数，包括 `12.300`。这是文本格式约束，严格程度比“数值能否无损转换为分”更高。`allocate` 拒绝直接传入 `new BigDecimal("10")`，调用者须先通过入口规范化。

## 七、常见错误与排查路径

| 症状 | 优先检查 | 处理方向 |
| --- | --- | --- |
| Non-terminating decimal expansion | 是否执行了精确的 1/3 等除法 | 明确除法 scale 与舍入政策；不要无条件改为 double |
| Rounding necessary | UNNECESSARY 边界是否收到非整分值 | 检查上游合同，不要吞掉异常后静默截断 |
| 除法结果突然变成整数 | 是否选了只传 RoundingMode 的重载 | 显式指定 scale |
| 金额相等却命中不了 Map 键 | equals 与输入 scale 是否一致 | 建立统一的金额键表示，并包含币种 |
| 合计差一分钱 | 明细与整单的舍入点是否一致 | 对照原始十进制值、规则版本和每个结算点 |
| 重算时尾差换了明细 | 权重、输入顺序是否稳定 | 使用持久化 ID 排序并保存原分摊记录 |
| Invalid money text | 是否带空白、指数、千分位或超出长度 | 检查序列化与接口格式，不先做有损数值转换 |
| Expected bounded scale-2 total | 直接 API 调用绕过了 parseMoney | 检查总额 scale、precision 与规范化位置 |
| invalid flag: --release | javac 是否仍来自 JDK 8 | 切换 PATH 后重新核对 java/javac 版本 |

排查时应采集币种、原始输入文本、scale、舍入规则、计算阶段、总额及排序键。含账号、订单和付款信息的日志应按系统规则脱敏，并限制访问；不要为了查一分钱差异输出整份敏感请求。

## 八、性能、安全与接入实践

分摊需要 O(n) 存储与 O(n log n) 次排序比较，另外还有与整数位数相关的大整数计算成本；本文没有测量吞吐或延迟。对每单大量明细，先确认10000项上限是否合理，再用真实分布压测，不能把算法复杂度当成 SLA。

代码在构造 BigDecimal 前限制输入长度和数字格式，在分摊前限制 scale、precision 和项数。这些限制同时用于控制资源开销。若允许不受约束的指数、位数和明细数量，即使数值对象能创建，后续缩放、乘法或格式化仍可能耗尽资源。不要将 arbitrary precision 理解为无成本、无容量边界。[BigDecimal 复杂度说明](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/math/BigDecimal.html)

接入服务时建议明确以下责任：

1. **输入层保留十进制。** 请求契约、序列化配置和客户端约定保持一致；若浏览器端使用浮点 Number 处理超大整数或金额，后端转换已无法找回原值。
2. **领域层保存规则。** 金额对象携带币种、结算单位与规则版本；禁止跨币种直接加总，精确中间值与已结算金额分开命名。
3. **分摊层核对不变量。** 检查逐项 scale、总和、零权重、符号和确定性。本文返回不可变列表，调用方也应避免并发修改输入权重数组。
4. **存储层验证端到端结果。** 数据库列的精度和 scale 应匹配合同；驱动绑定、JSON 输出与下游系统再次舍入都需要集成测试。不能把 Java 层通过视为整个账务链路通过。
5. **退款沿用原记录。** 对原分摊逐项冲销，核对累计退款上限；规则调整必须留版本和迁移策略。

本文算法只计算金额，不提供并发扣款、幂等支付、双重记账或数据库事务保证。生产写入还需要在对应系统中验证这些责任。

## 十、总结

金额计算应先定义什么位置允许舍入，再定义如何舍入；字符串输入、BigDecimal 和固定小数位只是实现这些规则的工具。发生对账差异时，重建每一个结算点比寻找一个万能精度参数更有效。

分摊时把已经结算的总额转为整数最小单位，用商与余数分配，并固定尾差顺序，可以同时获得总额守恒与确定性。最终应将规则、输入顺序及分摊结果作为可审计的数据保存。
