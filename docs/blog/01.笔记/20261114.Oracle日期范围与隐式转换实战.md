“查询 11 月 14 日的订单”看起来只是一个条件，实际可能出现三种故障：只返回零点的数据，把第二天零点算进来，或者更换连接池配置后报日期格式错误。给日期列套上格式化函数后，结果正确了，查询又可能开始扫描大量数据。

本文用同一组边界数据复现这些问题，建立不依赖日期显示格式的查询方式，再通过实际游标计划检查索引访问。适用于按日对账、日志检索、批处理时间窗口和接口筛选。目标是同时把结果边界和访问路径解释清楚。

## 一、适用版本、权限与实验边界

SQL 以 **Oracle Database 19c 的语法及日期语义**为基线，同时在本文末尾注明实际执行版本。需要了解 SELECT、索引和基本 PL/SQL；客户端采用 SQL*Plus，SQLcl 也可按脚本方式执行。SQL Developer 应使用“运行脚本”，以识别 `/`、`VARIABLE` 和 `EXEC` 等客户端命令。

本实验只在专用测试用户下创建 `W_DATE_EDGE`、`W_DATE_LOAD` 两张表及相关索引，写入约十万行合成数据。不连接生产库，不需要修改数据库实例参数。创建表需要 `CREATE TABLE` 和表空间配额；诊断运行时计划需要额外只读权限，下面单独授权。普通查询不需要 DBA 账号。

由测试库管理员连接**目标 PDB**后执行以下一次性准备。要求 USERS 是已存在、可写的普通数据表空间；如名称不同，替换下面两处 users。用户名必须尚不存在；不要删除、复用同名业务账号。示例密码仅供隔离实验，请自行替换，不要沿用到共享环境。

```sql
CREATE USER worthy_date_lab IDENTIFIED BY "WorthyLab_20261114"
  DEFAULT TABLESPACE users QUOTA 100M ON users;
GRANT CREATE SESSION, CREATE TABLE TO worthy_date_lab;

-- 仅第七节 DISPLAY_CURSOR 需要，由管理员授予最小诊断权限。
GRANT SELECT ON sys.v_$session TO worthy_date_lab;
GRANT SELECT ON sys.v_$sql TO worthy_date_lab;
GRANT SELECT ON sys.v_$sql_plan TO worthy_date_lab;
GRANT SELECT ON sys.v_$sql_plan_statistics_all TO worthy_date_lab;
```

本文使用的 Free Lite 镜像没有预建 USERS，首次准备出现 ORA-00959。实测先由管理员在临时 PDB 创建如下表空间，然后重试上面的账号准备。**仅当 USERS 尚不存在时执行**，路径是本次 Linux 容器内的数据库文件路径，不能直接复制到其他数据库；其他环境由管理员选择已有表空间或按本库存储方式创建。该命令会分配 128 MiB 数据文件，关闭自动扩展，所需权限为 CREATE TABLESPACE，语法见 [CREATE TABLESPACE](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/CREATE-TABLESPACE.html)。本次容器销毁时一起清理文件；持久测试库应按管理员的表空间回收流程处理。

```sql
CREATE TABLESPACE users
  DATAFILE '/opt/oracle/oradata/FREE/FREEPDB1/users01.dbf'
  SIZE 128M AUTOEXTEND OFF;
```

Linux 与 macOS 都可以在已安装 Oracle 客户端的终端执行以下命令，替换主机、端口、服务名；在提示中输入密码，不把密码写进命令行、脚本或 shell 历史。连接远端数据库不要求操作系统 root 或 sudo。

```bash

```

这条命令要求监听器确实能从当前主机访问。本文实测使用隔离容器内的本地连接，没有把数据库端口开放到宿主机。后文 SQL 与客户端主机是 Linux 还是 macOS 无关。

## 二、先分清类型、显示格式和业务时区

| 类型或表达式 | 包含什么 | 对查询的影响 |
| --- | --- | --- |
| `DATE` 列 | 年、月、日、时、分、秒 | 列名叫“日期”也可能有非零时间 |
| `TIMESTAMP(6)` 列 | 日期时间及六位小数秒 | `23:59:59` 不是当天最后一个可能值 |
| `DATE '2026-11-14'` | 当天 `00:00:00`，DATE 类型 | 使用固定 ANSI 语法，不依赖 `NLS_DATE_FORMAT` |
| `'2026-11-14'` | 字符串 | 与 DATE 比较时可能触发会话相关转换 |
| `TO_CHAR(date_col, ...)` | 格式化后的字符串 | 改变表达式类型，适合展示，筛选时需审视计划 |

Oracle DATE 的精度到秒；DATE 和普通 TIMESTAMP 都不保存时区。不要因为客户端只显示年月日，就认定数据库没有保存时间。类型及时间字段见 [Oracle 日期时间类型](https://docs.oracle.com/en/database/oracle/oracle-database/19/nlspg/datetime-data-types-and-time-zone-support.html)，ANSI 日期字面量及默认零点规则见 [Datetime Literals](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Literals.html)。

本文统一约定：测试数据已经是同一业务时区下的本地日期时间，不进行时区转换。如果生产库保存 UTC 时间，先明确“某日”属于哪个业务时区，再把该日开始和次日开始分别换算成 UTC，绑定到查询边界。存在夏令时的地区，一天可能不是 24 小时；不要直接用开始时刻加 24 小时替代“下一本地日零点”。带时区类型及夏令时规则另见上述日期时间类型文档，本实验不覆盖这部分行为。

## 三、建立能暴露错误的边界数据

以下各节按顺序在同一个测试用户会话执行。本例将独立实验会话明确设为公历；显式格式模型并不意味着所有 NLS 选项都与转换无关。`WHENEVER SQLERROR` 使意外 SQL 错误终止脚本，避免错误后仍把后续输出当成成功；交互客户端会因此退出，重新登录后应检查已经创建的对象。

```sql
WHENEVER SQLERROR EXIT SQL.SQLCODE ROLLBACK
SET LINESIZE 180
SET PAGESIZE 100
SET SERVEROUTPUT ON
ALTER SESSION SET NLS_CALENDAR = 'GREGORIAN';

CREATE TABLE w_date_edge (
  id NUMBER PRIMARY KEY,
  created_at DATE,
  event_at TIMESTAMP(6)
);

INSERT INTO w_date_edge VALUES (
  1, TO_DATE('2026-11-13 23:59:59', 'YYYY-MM-DD HH24:MI:SS'),
  TIMESTAMP '2026-11-13 23:59:59');
INSERT INTO w_date_edge VALUES (
  2, DATE '2026-11-14', TIMESTAMP '2026-11-14 00:00:00');
INSERT INTO w_date_edge VALUES (
  3, TO_DATE('2026-11-14 12:00:00', 'YYYY-MM-DD HH24:MI:SS'),
  TIMESTAMP '2026-11-14 12:00:00');
INSERT INTO w_date_edge VALUES (
  4, TO_DATE('2026-11-14 23:59:59', 'YYYY-MM-DD HH24:MI:SS'),
  TIMESTAMP '2026-11-14 23:59:59.999999');
INSERT INTO w_date_edge VALUES (
  5, DATE '2026-11-15', TIMESTAMP '2026-11-15 00:00:00');
INSERT INTO w_date_edge VALUES (6, NULL, NULL);
COMMIT;

SELECT id, TO_CHAR(created_at, 'YYYY-MM-DD HH24:MI:SS') AS date_text,
       TO_CHAR(event_at, 'YYYY-MM-DD HH24:MI:SS.FF6') AS ts_text
FROM w_date_edge ORDER BY id;
```

预期 id=4 的两列分别显示 `2026-11-14 23:59:59` 和 `2026-11-14 23:59:59.999999`。id=6 两列为空。显式 TO_CHAR 只用于输出，避免客户端显示格式掩盖边界。

### 1. 等号只匹配一个时刻

```sql
SELECT id FROM w_date_edge
WHERE created_at = DATE '2026-11-14' ORDER BY id;
```

预期只有 **2**。等号比较的是完整 DATE 值，其他时间不等于零点。

### 2. BETWEEN 同时包含两端

```sql
SELECT id FROM w_date_edge
WHERE created_at BETWEEN DATE '2026-11-14' AND DATE '2026-11-15'
ORDER BY id;
```

预期 **2、3、4、5**，多算了次日零点。BETWEEN 等价于下界小于等于该值、该值小于等于上界，见 [BETWEEN Condition](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/BETWEEN-Condition.html)。连续两天都用这样的闭区间，会重复统计交界时刻。

### 3. 写死当天 23:59:59 会漏掉小数秒

```sql
SELECT id FROM w_date_edge
WHERE event_at BETWEEN TIMESTAMP '2026-11-14 00:00:00'
                   AND TIMESTAMP '2026-11-14 23:59:59'
ORDER BY id;
```

预期 **2、3**，漏掉 id=4。为上界不断补 9 会把代码绑定到列精度，将来精度变化又要检查。

## 四、使用左闭右开的完整时间窗口

推荐将窗口定义为 `[start, end)`：包含开始，不包含结束。查一天就使用当天零点到次日零点；查月份就使用当月第一天到下月第一天。不要把“结束日期”同时当作包含的日期和排除的时刻。

```sql
SELECT id FROM w_date_edge
WHERE created_at >= DATE '2026-11-14'
  AND created_at <  DATE '2026-11-15'
ORDER BY id;

SELECT id FROM w_date_edge
WHERE event_at >= TIMESTAMP '2026-11-14 00:00:00'
  AND event_at <  TIMESTAMP '2026-11-15 00:00:00'
ORDER BY id;
```

两条都应返回 **2、3、4**。区间自然衔接，不需要猜测一天最后一秒；DATE 与 TIMESTAMP 示例分别使用匹配类型的边界。NULL 不满足普通范围比较，因此 id=6 不返回；需要处理缺失时间时，应单独定义业务规则。

分页、导出和批处理应记录同一对窗口边界，并对重试结果做幂等处理。半开区间解决时间交界的重复，但不解决运行期间发生的新写入、补录和时间字段修改；增量同步仍需要明确迟到数据策略和一致性要求。

## 五、复现 NLS 引发的“同一句 SQL，不同日期”

隐式转换不一定报错，更难发现的是它把输入解释成了另一个合法日期。以下只修改**当前测试会话**的显示及解析参数：

```sql
ALTER SESSION SET NLS_DATE_FORMAT = 'DD-MM-YYYY';
SELECT TO_CHAR(TO_DATE('01-02-2026'), 'YYYY-MM-DD') AS parsed FROM dual;

ALTER SESSION SET NLS_DATE_FORMAT = 'MM-DD-YYYY';
SELECT TO_CHAR(TO_DATE('01-02-2026'), 'YYYY-MM-DD') AS parsed FROM dual;

SELECT COUNT(*) AS safe_count FROM w_date_edge
WHERE created_at >= DATE '2026-11-14'
  AND created_at <  DATE '2026-11-15';
```

两个 `parsed` 预期分别是 **2026-02-01** 和 **2026-01-02**，`safe_count` 是 **3**。省略格式模型的 TO_DATE 使用默认格式；直接用字符与 DATE 比较也可能走会话相关转换。连接池中不同连接的会话设置、客户端初始化和登录触发器都值得检查。[Oracle 类型转换规则](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Data-Type-Comparison-Rules.html)

### 1. 输入是字符串，就在参数侧显式解析

下面是可在 SQL*Plus 中运行的字符串绑定实验：

```sql
VARIABLE start_text VARCHAR2(10)
VARIABLE end_text VARCHAR2(10)
EXEC :start_text := '2026-11-14';
EXEC :end_text := '2026-11-15';

SELECT id FROM w_date_edge
WHERE created_at >= TO_DATE(:start_text, 'FXYYYY-MM-DD')
  AND created_at <  TO_DATE(:end_text, 'FXYYYY-MM-DD')
ORDER BY id;
```

预期 **2、3、4**。`YYYY` 是四位年，`MM` 是月份，`DD` 是日；`HH24` 表示 24 小时制，分钟是 `MI`。`FX` 启用严格格式匹配，避免宽松的分隔符匹配；完整规则见 [Format Models](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Format-Models.html)。参数仍需检查非空、合法日期及 `start < end`；合法格式不等于合法业务窗口。

解析放在参数侧，列保持原类型。若包含英文月份，除了格式模型还应明确 `NLS_DATE_LANGUAGE`；纯数字格式可以避开月份名称语言差异。业务接口尽量约定四位年份，避免两位年 `RR` 的世纪推断。

### 2. 参数已经是 DATE，就直接绑定

下面用 PL/SQL 的 DATE 变量构造类型明确的动态 SQL。SQL 文本固定，值通过 USING 传递，不进行字符串拼接：

```sql
DECLARE
  l_start DATE := DATE '2026-11-14';
  l_end   DATE := DATE '2026-11-15';
  l_count NUMBER;
BEGIN
  EXECUTE IMMEDIATE
    'SELECT COUNT(*) FROM w_date_edge WHERE created_at >= :a AND created_at < :b'
    INTO l_count USING l_start, l_end;
  IF l_count <> 3 THEN
    RAISE_APPLICATION_ERROR(-20001, 'Unexpected typed-bind result');
  END IF;
  DBMS_OUTPUT.PUT_LINE('TYPED_BIND_COUNT=' || l_count);
END;
/
```

预期 `TYPED_BIND_COUNT=3`。应用也应让驱动绑定合适的日期时间类型，并核对驱动、ORM、列定义和时区配置。本节验证的是数据库 DATE 绑定，不代表已经验证任何 JDBC/ORM 的映射行为。

不要对 DATE 参数或 DATE 列再调用 `TO_DATE(..., 'YYYY-MM-DD')`。TO_DATE 以字符为输入，对 DATE 再调用会先发生 DATE 到字符的转换，可能丢失时分秒或因格式不匹配报错。官方也明确不建议这样使用，见 [TO_DATE](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/TO_DATE.html)。下面可观察实际信息丢失：

```sql
ALTER SESSION SET NLS_DATE_FORMAT = 'YYYY-MM-DD';
SELECT TO_CHAR(created_at, 'YYYY-MM-DD HH24:MI:SS') AS original_value,
       TO_CHAR(TO_DATE(created_at, 'YYYY-MM-DD'),
               'YYYY-MM-DD HH24:MI:SS') AS converted_value
FROM w_date_edge WHERE id = 3;
```

预期原值为 `2026-11-14 12:00:00`，转换后为 `2026-11-14 00:00:00`。这是用于复现问题的反例，不应写入业务代码。

## 六、结果正确之后，检查谓词是否适合现有索引

`TRUNC(created_at) = DATE '2026-11-14'` 可以表达本例“同一天”的需求。TRUNC 默认截断到当天零点，返回 DATE；其规则见 [TRUNC(date)](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/TRUNC-date.html)。但普通 `created_at` 索引与 `TRUNC(created_at)` 表达式不是同一个索引定义。

不要把“列上有函数”概括成“索引一定失效”：优化器可能进行转换，也可能选择索引全扫描；函数索引又是另一种设计。我们要检查的是：日期边界是否成为索引的 **access predicate**，实际读取多少行，回表和过滤发生在哪一步。

建立一张每分钟一行的合成表。它只用于观察访问路径，不能用于推算真实订单系统的吞吐或时延。

```sql
CREATE TABLE w_date_load AS
SELECT level AS id,
       DATE '2026-10-01' + (level - 1) / 1440 AS created_at,
       CAST(RPAD('x', 100, 'x') AS VARCHAR2(100)) AS payload
FROM dual CONNECT BY level <= 100000;

CREATE INDEX w_date_load_ix ON w_date_load(created_at);
BEGIN
  DBMS_STATS.GATHER_TABLE_STATS(USER, 'W_DATE_LOAD', cascade => TRUE);
END;
/
```

Oracle DATE 加数字时，数字按天计算，这里 `1/1440` 是一分钟。100000 行覆盖 2026-10-01 起约 69 天；11 月 14 日应有 1440 行。收集统计信息只针对本实验表，不要把这样的操作未经评估扩展到生产库。

## 七、查看真实执行计划和行数

下面每条业务查询后紧跟 DISPLAY_CURSOR，中间不要运行其他业务 SQL。使用 SQL*Plus，先执行 `SET SERVEROUTPUT OFF`：此前为了观察 PL/SQL 输出开启了 SERVEROUTPUT，客户端自动执行的 `DBMS_OUTPUT.GET_LINES` 会占用“上一条游标”，导致拿不到目标查询计划。也要关闭其他客户端自动补充查询的功能。`gather_plan_statistics` 只对示例查询收集统计信息；不需要全局开启 `STATISTICS_LEVEL=ALL`。

```sql
SET SERVEROUTPUT OFF

SELECT /*+ gather_plan_statistics */ /* worthy_date_range */
       SUM(LENGTH(payload)) AS total_chars
FROM w_date_load
WHERE created_at >= DATE '2026-11-14'
  AND created_at <  DATE '2026-11-15';

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(
  NULL, NULL, 'ALLSTATS LAST +PREDICATE'));

SELECT /*+ gather_plan_statistics */ /* worthy_date_trunc */
       SUM(LENGTH(payload)) AS total_chars
FROM w_date_load
WHERE TRUNC(created_at) = DATE '2026-11-14';

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(
  NULL, NULL, 'ALLSTATS LAST +PREDICATE'));
```

两次 `total_chars` 都应是 **144000**。读取 payload 是为了让查询需要表内数据，避免仅统计索引条目时产生另一种成本比较。关注：

- 范围查询是否出现 `INDEX RANGE SCAN`，日期上下界是否出现在 access 中。
- TRUNC 查询实际选择什么路径，函数是否出现在 filter 中；不要只凭 SQL 外观判定。
- `A-Rows` 是实际输出行数，不是读取的所有数据行数。全表扫描节点即使输出 1440 行，也可能已经检查整张表；结合操作类型、Buffers 和过滤条件理解。
- `E-Rows` 是估算；估算与实际偏差明显时，进一步检查统计信息和数据分布。

`ALLSTATS LAST` 需要执行时收集过统计信息；只运行 EXPLAIN PLAN 得到的是估算计划，不能据此声称真实运行使用了多少逻辑读。DISPLAY_CURSOR 的权限及格式见 [DBMS_XPLAN 官方文档](https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_XPLAN.html)。实际游标可能因绑定值、子游标、数据量和版本不同而变化，本文不强制某一种计划。

如果业务长期以 `TRUNC(created_at)` 检索，可以评估相同表达式的函数索引及其维护成本；如果是普通时间段筛选，优先保留原列范围谓词。索引范围扫描并不总是最佳：当范围覆盖大部分数据，顺序全表扫描可能更合适。也不要仅为让计划“出现索引”而加入强制索引提示。

## 八、常见故障排查与安全注意事项

| 现象 | 优先检查 | 修复方向 |
| --- | --- | --- |
| 查一天只返回极少数据 | 是否写成日期等号；显示是否隐藏时间 | 显式显示时间，再改为完整范围 |
| 每日批处理重复交界记录 | 是否用 BETWEEN 连接相邻窗口 | 统一使用排除上界，并保证重试幂等 |
| TIMESTAMP 漏掉当天最后一些记录 | 上界是否写死 23:59:59 | 使用次日零点的排除上界 |
| ORA-01843、ORA-01861 等转换错误 | 输入、格式模型、绑定类型和会话 NLS | 按实际类型解析，拒绝不合法输入 |
| 没报错却查错月份或日期 | 是否依赖省略格式的 TO_DATE、两位年 | 固定输入协议和四位年份，显式转换 |
| 结果正确但扫描大幅增加 | 列上函数、实际 access/filter、统计信息 | 检查实际游标，评估范围谓词和索引 |
| A-Rows/Buffers 缺失 | 是否收集运行统计；是否看错游标 | 在受控查询上收集并查看正确 SQL_ID/子游标 |
| 时间偏移若干小时 | 存储语义、会话时区、驱动映射 | 明确业务日与存储时区后计算两个边界 |

会话配置可以这样核对：

```sql
SELECT parameter, value FROM nls_session_parameters
WHERE parameter IN ('NLS_DATE_FORMAT', 'NLS_TIMESTAMP_FORMAT',
                    'NLS_DATE_LANGUAGE', 'NLS_CALENDAR')
ORDER BY parameter;

SELECT sessiontimezone, dbtimezone FROM dual;
```

日期格式影响转换和输出，不会给 DATE 列补上时区语义。也不要通过拼接日期字符串构造动态 SQL：会话格式依赖可能引入错误，某些动态 SQL 还会受到基于 NLS 设置的注入影响。固定 SQL 文本并绑定值；类型转换的安全边界见前文 [Oracle 类型转换规则](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Data-Type-Comparison-Rules.html)。

排查生产慢查询时先拿到有代表性的窗口、绑定类型、SQL_ID 和子游标，再比较实际计划。不要把测试库某次运行的缓存命中率、Buffers 或耗时直接当成生产性能承诺。本例没有做压力测试，也没有对应用连接池、分区表或函数索引进行实测。

## 九、清理、回退与实际验证

实验中的 DDL 会隐式提交；ROLLBACK 不能撤销 CREATE TABLE、CREATE INDEX 或 DROP TABLE，具体提交边界见 [COMMIT](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/COMMIT.html)。只有确认处于专用测试账号且对象没有业务数据时，才执行：

```sql
DROP TABLE w_date_load PURGE;
DROP TABLE w_date_edge PURGE;
```

这会删除两张实验表、表内合成数据及依附索引，PURGE 跳过回收站，不能靠闪回表恢复；需要重做实验就重新运行第三、六节。共享环境应先导出仍需保留的数据，或去掉 PURGE 并按本库恢复策略处理。不要删除其他用户的表，也不要使用通配式清理。

本文修改的 NLS 参数仅在当前会话有效。实验使用独立连接，完成后退出该连接即可；若在连接池里试验，则应恢复进入实验前记录的设置，再把连接交还池中。管理员可在确认专用账号不再使用、没有其他对象后删除该账号；本文不提供自动删除账号的命令。

## 十、实践要点

先约定时间列的业务语义，再把查询窗口表达为类型明确的 `[start, end)`。字符串只在输入边界按明确格式转换；已经是日期时间的值直接绑定。输出时可以格式化，筛选时保留原列范围，并通过实际游标确认优化器选择。这样既能解释边界记录为什么出现，也能给性能排查留下可验证的依据。
