## 一、适用版本、权限与实验准备

语义及语法以 **Oracle Database 19c** 官方文档为基线，使用普通堆表，不涉及临时表、自治事务、分布式事务或在线重定义。实际执行版本、结果与限制见第九节。读者应了解 INSERT、UPDATE、主键和 PL/SQL 匿名块。

客户端采用 SQL*Plus；SQLcl 可按脚本方式运行，SQL Developer 应使用“运行脚本”模式，识别 EXEC、SHOW 和独立的 `/` 行。连接之前关闭 GUI 自动提交，并确认没有其他业务工作复用该连接。

由测试库管理员在**目标 PDB**建立全新的测试用户。以下 `users` 必须是已有且可写的普通数据表空间；不同环境请替换为管理员指定名称。不要删除或复用同名业务用户。密码仅作隔离实验示意，共享环境应替换。

本文实测在隔离 Linux 容器内部连接，没有向宿主机公开数据库端口。SQL 的事务语义不因客户端运行在 Linux 或 macOS 而改变。

先核对身份与容器，再在同一个实验会话按顺序执行第二至七节。表名与过程名必须尚未使用，遇到对象重名应停止并检查来源，不能直接 DROP。

```sql
SHOW USER
SHOW CON_NAME
SET AUTOCOMMIT OFF
SET EXITCOMMIT OFF
WHENEVER OSERROR EXIT FAILURE ROLLBACK
WHENEVER SQLERROR EXIT FAILURE ROLLBACK
SET SERVEROUTPUT ON
SET LINESIZE 160
SET PAGESIZE 100
SELECT banner_full FROM v$version;

CREATE TABLE w_tx_data (id NUMBER PRIMARY KEY, val NUMBER NOT NULL);
CREATE TABLE w_tx_marker (id NUMBER PRIMARY KEY);

CREATE OR REPLACE PROCEDURE w_tx_check (
  p_query IN VARCHAR2, p_expected IN NUMBER, p_label IN VARCHAR2
) AUTHID CURRENT_USER AS
  n NUMBER;
BEGIN
  EXECUTE IMMEDIATE p_query INTO n;
  IF n IS NULL OR n <> p_expected THEN
    RAISE_APPLICATION_ERROR(-20001, p_label || ': unexpected value');
  END IF;
  DBMS_OUTPUT.PUT_LINE('PASS ' || p_label || ' = ' || n);
END;
/

INSERT INTO w_tx_data VALUES (1, 100);
COMMIT;
```

`p_query` 只接受下文固定的单值 SELECT，`p_expected` 是期望值，`p_label` 用于定位失败。这个辅助过程没有 COMMIT、ROLLBACK 或自治事务，不改变被观察的事务边界；不能把它开放为接受用户 SQL 的接口。

`SET AUTOCOMMIT OFF` 关闭客户端自动提交，**不能关闭数据库的 DDL 隐式提交**。`EXITCOMMIT OFF` 与显式退出参数用于控制离开客户端时的行为。`WHENEVER SQLERROR` 遇到未处理的 SQL/PLSQL 错误就失败退出并回滚当前未提交事务；它不捕获所有 SQL*Plus 命令错误，应同时检查日志中的 SP2 信息。[SQL*Plus SET](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqpug/SET-system-variable-summary.html)、[WHENEVER SQLERROR](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqpug/WHENEVER-SQLERROR.html)、[EXIT](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqpug/EXIT.html)

## 二、先建立准确的事务模型

对本文普通表操作，区分三种边界：

| 操作 | 当前 DML 的结果 | 保存点 |
| --- | --- | --- |
| COMMIT | 提交此前修改，结束事务 | 全部清除 |
| ROLLBACK | 撤销当前未提交事务，结束事务 | 全部清除 |
| ROLLBACK TO s | 撤销 s 之后的修改，事务继续 | 保留 s 及更早标记，清除后续标记 |
| 语法有效的 DDL | 执行前提交；成功执行后再次提交 | 原事务保存点失效 |

DDL 有两个需要分别理解的阶段：先提交调用会话此前的事务，再尝试改变对象定义。DDL 执行阶段失败，并不意味着第一阶段提交会逆转。官方规则明确包括“语法有效但执行报错”的 DDL，不能把语法拼写错误当成失败 DDL 的通用实验。[Oracle 19c COMMIT](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/COMMIT.html)

同一会话的普通 SELECT 可以看到自己的未提交修改，因此“查得到”本身不是提交证明。下文用完整 ROLLBACK 后的数据、数据字典和第二个会话复核提交结果。本文观察会话使用默认 READ COMMITTED；其他事务模式需另行分析。

## 三、保存点可以局部回退，但不能形成独立事务

先把 100 更新成 110，记录保存点，再改成 120。局部回退恢复到 110；再次回退到同一保存点依然有效，最后完整回滚恢复到已提交的 100。

```sql
UPDATE w_tx_data SET val = 110 WHERE id = 1;
SAVEPOINT before_second;
UPDATE w_tx_data SET val = 120 WHERE id = 1;
ROLLBACK TO before_second;
EXEC w_tx_check('SELECT val FROM w_tx_data WHERE id=1', 110, '01_partial');
ROLLBACK TO before_second;
ROLLBACK;
EXEC w_tx_check('SELECT val FROM w_tx_data WHERE id=1', 100, '02_full');
```

保存点重名会把标记移动到当前位置，不会产生一组同名栈帧。下面回退到最近一次 `s` 后保留 120，随后完整回滚恢复 100。

```sql
UPDATE w_tx_data SET val = 110 WHERE id = 1;
SAVEPOINT s;
UPDATE w_tx_data SET val = 120 WHERE id = 1;
SAVEPOINT s;
UPDATE w_tx_data SET val = 130 WHERE id = 1;
ROLLBACK TO s;
EXEC w_tx_check('SELECT val FROM w_tx_data WHERE id=1', 120, '03_reused');
ROLLBACK;
```

此处最近一次标记时值已经是 **120**，所以断言为 120。保存点不是嵌套事务，调用链中的 COMMIT 会提交当前事务全部修改。复用通用保存点名也可能覆盖调用者的标记，应在组件之间明确事务控制责任。[SAVEPOINT](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/SAVEPOINT.html)、[ROLLBACK](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/ROLLBACK.html)

## 四、普通 DML 报错不等于整个事务自动回滚

以下先完成一次 UPDATE，再在独立 INSERT 中制造主键重复。我们在 PL/SQL 内只捕获预期错误；此前成功 UPDATE 仍为 140，随后由调用者显式回滚。

```sql
UPDATE w_tx_data SET val = 140 WHERE id = 1;
BEGIN
  BEGIN
    INSERT INTO w_tx_data VALUES (1, 999);
    RAISE_APPLICATION_ERROR(-20002, 'Expected duplicate key');
  EXCEPTION
    WHEN DUP_VAL_ON_INDEX THEN
      DBMS_OUTPUT.PUT_LINE('EXPECTED ORA-00001');
  END;
END;
/
EXEC w_tx_check('SELECT val FROM w_tx_data WHERE id=1', 140, '04_dml_error');
ROLLBACK;
```

这是语句级原子性与事务级原子性的区别：失败 INSERT 自身没有部分写入，但前一条 UPDATE 还属于打开的事务。示例明确捕获了 INSERT 错误；不要将它直接推广为所有未捕获 PL/SQL 异常、驱动批处理或框架事务的最终行为。[Oracle Concepts：Transactions](https://docs.oracle.com/en/database/oracle/oracle-database/19/cncpt/transactions.html)

生产代码可以在失败时选择整体回滚或回到保存点，但必须由事务拥有者执行确定的策略；仅打印异常并继续 COMMIT，可能把业务上应一同失败的前序修改提交。

## 五、成功 DDL 会切断此前事务

```sql
INSERT INTO w_tx_data VALUES (2, 200);
ALTER TABLE w_tx_data ADD note VARCHAR2(30);
ROLLBACK;
EXEC w_tx_check('SELECT COUNT(*) FROM w_tx_data WHERE id=2', 1, '05_ddl_dml');
EXEC w_tx_check('SELECT COUNT(*) FROM user_tab_columns WHERE table_name=''W_TX_DATA'' AND column_name=''NOTE''', 1, '06_ddl_column');
```

回滚之后 id=2 仍在，NOTE 列也仍在。第一条 INSERT 在 ALTER 执行前已经提交，列定义由成功的 DDL 提交。后面的 ROLLBACK 没有能够撤销这两项操作的未提交事务。

在另一个新连接的实验账号会话 B 中执行以下只读查询，也应返回一行 `2, 200`。B 不要运行初始化或清理脚本；查询完成后以 `EXIT SUCCESS ROLLBACK` 退出。

```sql
SELECT id, val FROM w_tx_data WHERE id = 2;
```

## 六、失败 DDL 也可能已经提交前序 DML

W_TX_DATA 已存在，再执行同名 CREATE TABLE。该 SQL 语法有效，但因对象名称冲突返回 ORA-00955。动态 SQL 让我们捕获这个**预期**错误并继续验证。

```sql
INSERT INTO w_tx_data(id, val) VALUES (3, 300);
SAVEPOINT before_bad_ddl;
BEGIN
  BEGIN
    EXECUTE IMMEDIATE 'CREATE TABLE w_tx_data (dummy NUMBER)';
    RAISE_APPLICATION_ERROR(-20003, 'Expected ORA-00955');
  EXCEPTION
    WHEN OTHERS THEN
      IF SQLCODE <> -955 THEN RAISE; END IF;
      DBMS_OUTPUT.PUT_LINE('EXPECTED ORA-00955');
  END;
END;
/

BEGIN
  BEGIN
    ROLLBACK TO before_bad_ddl;
    RAISE_APPLICATION_ERROR(-20004, 'Expected ORA-01086');
  EXCEPTION
    WHEN OTHERS THEN
      IF SQLCODE <> -1086 THEN RAISE; END IF;
      DBMS_OUTPUT.PUT_LINE('EXPECTED ORA-01086');
  END;
END;
/
ROLLBACK;
EXEC w_tx_check('SELECT COUNT(*) FROM w_tx_data WHERE id=3', 1, '07_failed_ddl');
```

预期同时出现 ORA-00955、ORA-01086 的标记以及 `PASS 07_failed_ddl = 1`。同名 CREATE 没有改掉原表；此前 id=3 的插入已提交，原保存点也被清除。会话 B 此时查询 id=3，同样应看到 300。

`EXECUTE IMMEDIATE` 不会取消 DDL 的提交规则。这里没有使用自治事务，动态 DDL 就在调用会话中执行。例外处理器只允许预期错误通过，其他错误继续向外抛出；把 `WHEN OTHERS THEN NULL` 放进迁移脚本会掩盖真实失败。

## 七、DELETE 可回滚，TRUNCATE 会改变恢复边界

本节会清空**实验表**。运行前确认账号为 WORTHY_TX_LAB，表中只有前三条合成数据。不要替换为业务表。

```sql
DELETE FROM w_tx_data;
ROLLBACK;
EXEC w_tx_check('SELECT COUNT(*) FROM w_tx_data', 3, '08_delete_rollback');

INSERT INTO w_tx_marker VALUES (1);
TRUNCATE TABLE w_tx_data;
ROLLBACK;
EXEC w_tx_check('SELECT COUNT(*) FROM w_tx_data', 0, '09_truncate_empty');
EXEC w_tx_check('SELECT COUNT(*) FROM w_tx_marker WHERE id=1', 1, '10_other_table_commit');
```

DELETE 回滚后恢复三行。TRUNCATE 成功后仍为零行，另一张表 W_TX_MARKER 的插入也保留下来：隐式提交作用于**该会话的整个当前事务**，不限于被截断的表。[TRUNCATE TABLE](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/TRUNCATE-TABLE.html)

不要把 TRUNCATE 当成“大批量 DELETE 的等价快写法”。普通表 TRUNCATE 不能用 ROLLBACK 撤销，也不能用 FLASHBACK TABLE 找回截断前内容。若误操作涉及真实数据，应停止后续写入并由 DBA 根据已有备份、日志和恢复方案评估；本文没有提供或验证生产恢复流程。保存点、关闭自动提交、在 PL/SQL 中包一层都不能充当备份。

DELETE 会产生与删除数据相关的 undo/redo，也可能长时间持锁；TRUNCATE 有不同的存储、约束和锁语义。本文仅验证恢复边界，没有吞吐量、耗时或空间收益基准，不能从三行实验推出生产性能结论。

## 八、把迁移拆成可验证的阶段

迁移若包含“调整结构→回填数据→验证→约束收紧”，不要在文件最前面写 SAVEPOINT 就声称能整体回滚。建议明确每个阶段的输入、完成标记与失败恢复办法：

1. **预检。** 核对 schema、对象定义、空间和权限，评估 DDL 锁等待；预先保存定义、制定备份和恢复方案。预检不能保证实际执行时没有竞争或空间变化。
2. **结构准备。** 在专用迁移连接执行建表、加列等 DDL。每条成功后检查数据字典，记录已完成阶段；失败就停止，重新确认实际对象状态。
3. **纯 DML 回填。** 使用另一明确边界的事务处理数据，断言受影响行数、空值与约束条件；验证通过后显式 COMMIT。大批次若分段提交，需要幂等条件、进度记录及独立补偿策略。
4. **结构收尾。** 再执行索引、约束等 DDL；失败时前序已提交数据仍可能存在，应设计可重入的修复或前向补丁。

“迁移连接独立”只能避免业务连接中其他未提交 DML 被顺带提交，不能让整个迁移变成一个可回滚事务。不要依靠框架事务注解或 `autoCommit=false` 改写 Oracle 的规则。

DDL 回退通常是另一项变更：例如删掉新列会连同该列数据一起移除，恢复旧结构也不等于恢复旧数据。实际发布前应在与生产版本、对象依赖和数据规模接近的环境演练。需要恢复保证时，应先验证备份可恢复性和应用兼容性。

| 症状 | 检查与处理 |
| --- | --- |
| ORA-01086 保存点无效 | 追溯同连接上的 COMMIT、完整 ROLLBACK 和 DDL；检查保存点是否因回退到更早标记被清除 |
| DDL 报错后 DML 留存 | 核对 DDL 是否语法有效；在新会话查提交结果，不以异常等同整体回滚 |
| 关闭自动提交仍无法回退 | 区分客户端提交、数据库隐式提交和连接池事务管理 |
| 日志报错但进程成功 | 检查 WHENEVER 设置及 SP2 错误；脚本返回成功也不能代替结果断言 |
| 反复重跑出现 ORA-00955 | 检查上次已完成的阶段，不盲目删除对象或把所有重名错误都当成功 |

不要在异常处理中执行“建表记录错误”或“TRUNCATE 临时工作表”来清理：它们可能提交尚待回滚的数据。持久工作表应预先创建，日志策略及自治事务应单独设计，避免引入意外提交或锁依赖。

## 十、总结

保存点只在当前尚未结束的事务内提供局部回退。普通 DML 失败、DDL 执行失败和整笔事务回滚是三个不同事件。排查“回滚为什么没有恢复”时，先重建同一连接上完整的提交边界，再用新连接验证可见数据。

对于包含 DDL 的发布，可靠性来自阶段检查、幂等执行和已经验证的恢复方案。事务控制命令可以保护仍未提交的 DML，却不能撤销已经发生的隐式提交。
