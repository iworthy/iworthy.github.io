给 Java 应用记录 PID、在线上查找某个 JAR 对应的进程、获取 `ProcessBuilder` 启动的子进程编号，看起来都叫“获取 Java 进程 ID”，实际却需要不同的方法。再加上 Java 8 与新版本 API 的差异、容器中的 PID 命名空间，以及进程退出后的编号复用，一行代码背后有不少需要明确的边界。

本文从“要获取哪个进程的 PID”开始，依次介绍 Java API、兼容方案、JDK 工具、操作系统命令和容器排查，最后给出可以复现的交叉验证步骤。所有示例都会说明适用版本与运行环境。

## 一、先选方法：你要找的是哪个进程

| 目标与条件 | 首选方式 | 需要注意 |
| --- | --- | --- |
| 当前 Java 进程，Java 9+ | `ProcessHandle.current().pid()` | 返回 `long`，不需要额外 import |
| 当前 Java 进程，Java 10+，已有管理代码 | `ManagementFactory.getRuntimeMXBean().getPid()` | 方法从 Java 10 开始提供 |
| 当前 Java 进程，Java 8 | 在已验证的 JVM 上解析 `RuntimeMXBean.getName()` | `pid@hostname` 是实现惯例，不能当作规范保证 |
| 当前程序创建的子进程，Java 9+ | 对返回的 `Process` 调用 `pid()` | 返回直接启动的进程编号，可能是 Shell |
| 查找正在运行的 Java 应用 | `jcmd -l`、`jps -l`，再结合系统进程信息 | 受权限、JVM 实现和容器边界影响 |
| Linux/macOS 上按应用定位 | `ps`、`pgrep` | 按名称或字符串匹配得到的是候选结果 |
| Windows 上按应用定位 | PowerShell `Get-CimInstance Win32_Process` | 用命令行区分多个 `java.exe` |
| 应用由 systemd 管理 | 查询服务的 `MainPID` | 前提是服务的主进程配置正确 |
| 容器中的 Java 应用 | 先明确容器内还是宿主机视角 | 两个视角的 PID 可以不同 |

最常见的需求可以直接写成：

```java
// Java 9+
long pid = ProcessHandle.current().pid();
```

但不能直接把这段代码放进 Java 8 项目，也不能拿容器内打印出来的 PID，在宿主机上不加核对地操作同号进程。

## 二、理解 PID：编号的范围比数字本身更重要

### 2.1 PID、PPID、Java 线程 ID 是不同概念

PID 是操作系统分配的进程编号，PPID 是父进程编号。一个 Java 进程通常包含多个线程，这些线程在操作系统和 JVM 中还可能有各自的标识。

例如，线程转储里可能出现 `tid`、`nid`，Java 代码也有线程 ID。它们不能直接替代进程 PID。尤其不能用下面的代码获取 Java 进程编号：

```java
// Java 8 中获取 Java 线程 ID 的写法；不是进程 PID
long threadId = Thread.currentThread().getId();
```

Linux 的线程组编号、原生线程编号与 JVM 线程编号还涉及不同层次，排查 CPU 热点时应单独建立对应关系。

### 2.2 PID 不是永久身份

进程退出之后，PID 可能被操作系统重新分配。因此，昨天记录的 `24680`，今天可能已经属于另一个程序。

实际记录时可以同时保存：

```text
application=orders-service
instance=orders-service-7b8d9f-abcde
pid=24680
processStartTime=2026-11-04T01:58:00Z
```

这里的应用名、实例标识与启动时间共同提供上下文。即使额外核对了这些字段，从“检查”到“执行操作”之间仍然可能发生状态变化，不能把它当作原子身份验证。

[ProcessHandle 官方文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ProcessHandle.html)明确提醒了 PID 复用、进程状态异步变化以及检查和操作之间的竞态问题。

### 2.3 使用 long 保存 PID

Java 的 `ProcessHandle.pid()`、`Process.pid()` 和 `RuntimeMXBean.getPid()` 都返回 `long`。应用接口、日志字段和工具类也应保持一致，不要为了适配某台机器的编号范围而强制转成 `int`。

## 三、Java 9+：使用 ProcessHandle 获取当前 PID

### 3.1 完整的最小示例

保存为 `CurrentPidDemo.java`：

```java
public class CurrentPidDemo {
    public static void main(String[] args) {
        long pid = ProcessHandle.current().pid();
        System.out.println("pid=" + pid);
    }
}
```

使用 JDK 9 或更新版本编译运行：

```bash
javac CurrentPidDemo.java
java CurrentPidDemo
```

输出形如：

```text
pid=24680
```

数字仅为示意，每次运行都可能变化。`ProcessHandle` 位于 `java.lang`，因此无需 import；模块化项目使用它也不需要额外声明 `requires java.management`。

这组 API 由 [JEP 102：Process API Updates](https://openjdk.org/jeps/102)引入，用来改善 Java 对原生进程的识别、查询和管理能力。

### 3.2 顺便获取启动时间与父进程

```java
// Java 9+；放在方法体中执行
ProcessHandle current = ProcessHandle.current();
ProcessHandle.Info info = current.info();

System.out.println("pid=" + current.pid());
System.out.println("start=" + info.startInstant()
        .map(Object::toString).orElse("unknown"));
System.out.println("user=" + info.user().orElse("unknown"));

current.parent().ifPresent(parent ->
        System.out.println("ppid=" + parent.pid()));
```

`startInstant()`、`user()` 等返回 `Optional`，原因是这些信息不一定能从当前平台或权限环境中获得。父进程查询也可能没有结果，不应直接调用 `.get()`。

[ProcessHandle.Info 文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ProcessHandle.Info.html)还说明，命令和参数信息可能受平台限制而截断。代码应明确处理“信息不可用”，不能把空值等同于进程不存在。

### 3.3 查询已有 PID 对应的进程

```java
// Java 9+；放在方法体中执行
long candidatePid = 24680L; // 替换成刚刚核对过的 PID

ProcessHandle.of(candidatePid).ifPresent(handle -> {
    System.out.println("pid=" + handle.pid());
    System.out.println("alive=" + handle.isAlive());
    System.out.println("command=" + handle.info().command()
            .orElse("unknown"));
});
```

这里有两个边界：

1. `ProcessHandle.of()` 找的是本地可访问的原生进程，不会按 PID 连接另一台服务器。
2. 获得句柄之后，进程仍可能退出；某个编号存在，也不证明它属于预期应用。

在受限制的平台上，查询还可能失败或不受支持。不要为了“始终返回一个数字”而把所有错误吞掉。

## 四、Java 10+：RuntimeMXBean.getPid()

如果应用本来就在通过管理接口采集 JVM 信息，可以使用：

```java
import java.lang.management.ManagementFactory;
import java.lang.management.RuntimeMXBean;

public class ManagementPidDemo {
    public static void main(String[] args) {
        RuntimeMXBean runtime = ManagementFactory.getRuntimeMXBean();
        System.out.println("pid=" + runtime.getPid());
        System.out.println("jvmStartMillis=" + runtime.getStartTime());
    }
}
```

**这段代码要求 Java 10+。** `RuntimeMXBean` 接口很早就存在，但不能因此推断它的每个方法都能在 Java 8、Java 9 上使用。`getPid()` 的引入版本可在[官方 API 文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.management/java/lang/management/RuntimeMXBean.html#getPid())中查到。

模块化项目若使用 `java.lang.management`，需要在自己的模块描述中声明：

```java
module example.pid {
    requires java.management;
}
```

普通 classpath 应用不需要为了这一点新建 `module-info.java`。自定义运行时镜像则要保证包含所需模块。

`getStartTime()` 是 JVM 启动时间，单位为 Unix 纪元以来的毫秒；前面的 `ProcessHandle.Info.startInstant()` 是原生进程启动时间。对于普通 Java 启动器两者通常接近，但语义并不完全相同。

如果已经建立远程 JMX 连接，也可以查询目标 JVM 的 `java.lang:type=Runtime` MBean：目标为 Java 10+ 并暴露相应属性时，读取 `Pid` 属性；Java 8 的目标没有这个标准属性。**本地调用 `ManagementFactory.getRuntimeMXBean()` 获取的是本地 JVM 的管理对象**，不会因为已经连上远程 JMX，就自动变成远程目标。

远程 JVM 返回的 PID 仍属于它自己的操作系统与命名空间。它不能脱离主机、容器信息单独使用。

## 五、Java 8：解析 RuntimeMXBean.getName()，但明确边界

### 5.1 常见写法为什么能工作

在常见的 HotSpot/OpenJDK 实现中，运行时名称通常形如：

```text
24680@my-host
```

因此，经常能看到：

```java
String name = java.lang.management.ManagementFactory
        .getRuntimeMXBean().getName();
String pidText = name.split("@")[0];
```

它在很多现有系统中确实可用，问题是：**Java 规范没有规定 `getName()` 必须返回 `pid@hostname`。**

[Java 8 的 RuntimeMXBean 文档](https://docs.oracle.com/javase/8/docs/api/java/lang/management/RuntimeMXBean.html#getName--)允许实现返回任意名称字符串。换 JVM 厂商、嵌入式运行方式或其他实现时，不能假定格式永远不变。

### 5.2 一个带格式与数值检查的实现

保存为 `LegacyPid.java`，使用 JDK 8 编译：

```java
import java.lang.management.ManagementFactory;
import java.util.OptionalLong;

public final class LegacyPid {
    private LegacyPid() {
    }

    public static OptionalLong currentPid() {
        return parseRuntimeName(
                ManagementFactory.getRuntimeMXBean().getName());
    }

    static OptionalLong parseRuntimeName(String name) {
        if (name == null) {
            return OptionalLong.empty();
        }

        int separator = name.indexOf('@');
        if (separator <= 0 || separator == name.length() - 1) {
            return OptionalLong.empty();
        }

        String prefix = name.substring(0, separator);
        for (int i = 0; i < prefix.length(); i++) {
            char ch = prefix.charAt(i);
            if (ch < '0' || ch > '9') {
                return OptionalLong.empty();
            }
        }

        try {
            long pid = Long.parseLong(prefix);
            return pid > 0 ? OptionalLong.of(pid) : OptionalLong.empty();
        } catch (NumberFormatException e) {
            return OptionalLong.empty();
        }
    }

    public static void main(String[] args) throws InterruptedException {
        OptionalLong pid = currentPid();
        if (pid.isPresent()) {
            System.out.println("pid=" + pid.getAsLong());
        } else {
            System.out.println("pid=unknown");
        }
        System.out.println("runtimeName="
                + ManagementFactory.getRuntimeMXBean().getName());

        if (args.length == 1 && "--hold".equals(args[0])) {
            Thread.sleep(60000L); // 留出一分钟供另一个终端查询
        }
    }
}
```

这个工具类处理了没有分隔符、空前缀、非数字、非正数和 `long` 溢出的情况，用 `OptionalLong.empty()` 表示无法按约定解析。

它仍然依赖 JVM 的名称约定。校验字符串只会减少误解析，并不能把实现惯例变成跨 JVM 的标准 API。如果 PID 是业务运行的必要条件，应在获取失败时明确报错；如果只是日志附加字段，记录 `unknown` 通常更合适。

不要用 `0` 伪装“未知 PID”。某些工具对 `0` 有特殊含义，例如 `jcmd 0 ...` 会将命令发送给所有可用的目标 JVM，见 [jcmd 文档](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jcmd.html)。

### 5.3 为什么不优先使用反射内部类、JNI 或 JNA

旧资料可能通过 JVM 私有字段、`sun.*` 内部类获取进程编号。它们依赖实现细节，在模块封装和版本升级时更容易失效，不适合作为新代码的默认实现。

JNI/JNA 可以调用操作系统的原生进程接口，例如 Unix 的 `getpid()` 或 Windows 的 `GetCurrentProcessId()`，但需要额外处理原生库、平台类型、部署和架构差异。如果 Java 8 项目本身已经使用这类组件，并且确实要求绕开运行时名称约定，可以评估采用；仅为打印一条启动日志引入原生依赖，通常收益有限。

Java 8 标准 API 没有与 `ProcessHandle.current().pid()` 等价的直接方法。文章中的兼容写法不能消除这个事实。

## 六、同一份工具包同时支持 Java 8 与新版本

业务项目已经要求 Java 11、17、21 或更高版本时，直接使用 `ProcessHandle` 即可。只有工具包确实需要保留 Java 8 兼容性，才有必要增加适配层。

以下 `CompatiblePid.java` 与上一节的 `LegacyPid.java` 放在同一目录，可以用 JDK 8 编译：

```java
import java.lang.reflect.InvocationTargetException;

public final class CompatiblePid {
    private CompatiblePid() {
    }

    public static long currentPid() {
        try {
            Class<?> api = Class.forName("java.lang.ProcessHandle");
            Object current = api.getMethod("current").invoke(null);
            return ((Long) api.getMethod("pid").invoke(current)).longValue();
        } catch (ClassNotFoundException | NoSuchMethodException e) {
            // API 不存在时才进入旧版兼容路径。
            return LegacyPid.currentPid().orElseThrow(() ->
                    new IllegalStateException("Cannot determine current PID"));
        } catch (IllegalAccessException e) {
            throw new IllegalStateException("Cannot access ProcessHandle API", e);
        } catch (InvocationTargetException e) {
            throw new IllegalStateException("ProcessHandle invocation failed",
                    e.getCause());
        }
    }

    public static void main(String[] args) {
        System.out.println("pid=" + currentPid());
    }
}
```

这里反射的是公开接口 `java.lang.ProcessHandle`，没有对运行时实现类调用 `setAccessible(true)`，也不需要添加 `--add-opens`。

需要区分两类失败：

- API 不存在：进入 Java 8 的名称解析路径。
- API 存在，但访问或调用失败：保留异常原因，交给调用方决定如何处理。

不要使用 `catch (Throwable)` 把权限问题、运行时错误和兼容性问题全部转换成一个假 PID。发布通用工具包时，还可以采用 Multi-Release JAR 分别提供基础实现与新版实现，但需要额外维护打包和多版本验证；普通业务代码没有必要为这个需求增加复杂度。

另外，**编译目标字节码版本与可用 API 版本是两回事**。仅用较新 JDK 加 `-source 8 -target 8`，不能自动阻止代码引用新版 API。构建 Java 8 兼容包时，应使用合适的 JDK 8 工具链，或在支持的新版编译器中使用 `--release 8`；直接引用 `ProcessHandle` 的代码会在这种编译约束下被拒绝。`--release` 同时约束 API 与编译目标的行为见 [javac 文档](https://docs.oracle.com/en/java/javase/25/docs/specs/man/javac.html)。

## 七、获取 Java 启动的子进程 PID

### 7.1 对 Process 调用 pid()

当前 JVM 的 PID 与它创建的子进程 PID 不同。Java 9+ 可以直接对 `ProcessBuilder.start()` 返回的对象调用 `pid()`。

下面是一个完整示例，保存为 `ChildPidDemo.java`：

```java
import java.nio.file.Path;
import java.nio.file.Paths;

public class ChildPidDemo {
    public static void main(String[] args) throws Exception {
        String executable = System.getProperty("os.name").startsWith("Windows")
                ? "java.exe" : "java";
        Path java = Paths.get(System.getProperty("java.home"), "bin", executable);

        Process child = new ProcessBuilder(java.toString(), "-version")
                .inheritIO()
                .start();

        System.out.println("parentPid=" + ProcessHandle.current().pid());
        System.out.println("childPid=" + child.pid());
        int exitCode = child.waitFor();
        System.out.println("childExitCode=" + exitCode);
    }
}
```

这里通过当前运行时目录查找 Java 启动器，没有依赖 PATH 中可能指向另一版本的 `java`。子进程只打印版本后退出，所以在人工查询前可能已经结束；不同进程的控制台输出顺序也不保证固定。

`inheritIO()` 让示例直接继承标准输入输出。如果改用默认管道，就应及时消费子进程输出，避免管道缓冲区填满造成阻塞。这些行为和 `pid()` 的版本说明见 [Process 官方文档](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Process.html)。

### 7.2 Shell 包装层会改变你拿到的对象

下面启动的是 Shell：

```java
Process child = new ProcessBuilder(
        "sh", "-c", "java -jar /opt/apps/orders-service.jar")
        .inheritIO()
        .start();
```

`child.pid()` 对应直接创建的进程，不能保证永远就是最终 Java 应用。有些 Shell 会优化执行方式，有些会保留中间进程，脚本还可能再启动后台任务。

能直接启动 Java 时，使用分开的参数：

```java
Process child = new ProcessBuilder(
        "/opt/jdk/bin/java", "-jar", "/opt/apps/orders-service.jar")
        .inheritIO()
        .start();
```

不要写成 `new ProcessBuilder("java -jar app.jar")`：这会把整个字符串当成可执行文件名，并不等价于在 Shell 中输入一行命令。

Java 8 的标准 `Process` 没有 `pid()`。如果必须在 Java 8 管理子进程编号，应让被启动程序通过约定上报 PID、使用成熟的进程管理组件，或评估原生接口；反射私有 `pid` 字段无法提供跨平台保证。

## 八、在 Java 中枚举其他进程

Java 9+ 可以调用 `ProcessHandle.allProcesses()`，再根据可获取的信息筛选候选项。下面的 `FindJavaProcesses.java` 示例以常规 Java 启动器名称作为筛选条件：

```java
import java.nio.file.Path;
import java.nio.file.Paths;
import java.util.Locale;
import java.util.stream.Stream;

public class FindJavaProcesses {
    private static boolean isJavaLauncher(String command) {
        Path fileName = Paths.get(command).getFileName();
        if (fileName == null) {
            return false;
        }
        String name = fileName.toString().toLowerCase(Locale.ROOT);
        return "java".equals(name) || "java.exe".equals(name)
                || "javaw.exe".equals(name);
    }

    public static void main(String[] args) {
        try (Stream<ProcessHandle> processes = ProcessHandle.allProcesses()) {
            processes.forEach(handle -> {
                ProcessHandle.Info info = handle.info();
                if (info.command().map(FindJavaProcesses::isJavaLauncher)
                        .orElse(false)) {
                    System.out.println("pid=" + handle.pid()
                            + " command=" + info.command().orElse("unknown"));
                }
            });
        }
    }
}
```

这段代码是候选发现工具，不能保证找出全部 JVM：

- 可执行文件改名、服务包装器或原生程序内嵌 JVM，不一定叫 `java`。
- 某些进程信息受权限限制，`command()` 可能为空。
- 查询期间进程可能退出或新建，结果不会保持不变。
- 容器内通常无法枚举宿主机上的所有进程。

如果要区分多个服务，还要结合 `info.arguments()`、应用标识和部署信息。命令行中可能带有口令或令牌，诊断输出应按实际需要选择字段，不宜直接汇总到公共日志。

## 九、不修改代码：使用 JDK 工具查找 PID

### 9.1 jps：快速发现 Java 应用

在安装了相应 JDK 工具的环境中运行：

```bash
jps -l
```

示意输出：

```text
24680 /opt/apps/orders-service.jar
24701 com.example.BatchJob
24800 jdk.jcmd/sun.tools.jps.Jps
```

`jps` 自身也可能出现在结果里；不同 JDK 的工具名称显示可能不同。

| 命令 | 用途 |
| --- | --- |
| `jps -q` | 只列出本地 JVM 标识 |
| `jps -l` | 显示主类全名或 JAR 完整路径 |
| `jps -lm` | 再显示传给 `main` 方法的参数 |
| `jps -lv` | 再显示传给 JVM 的参数 |

`-m` 和 `-v` 不一样。对于 `java -Xmx512m -jar app.jar --server.port=8080`，`-Xmx512m` 是 JVM 参数，`--server.port=8080` 是应用参数。

[jps 官方文档](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jps.html)将输出编号称为 `lvmid`：通常对应操作系统 PID，但并不保证任何实现中都完全等价。它主要列出具有访问权限的、可被该工具发现的 HotSpot JVM，不能视为操作系统进程的完整清单；文档也不建议把其可变化的输出格式当作稳定脚本协议。

### 9.2 jcmd：发现后继续核对目标

```bash
jcmd -l
```

找到候选 PID 后，先核对命令行和版本：

```bash
java_pid=24680 # 替换成实际候选 PID
jcmd "$java_pid" VM.command_line
jcmd "$java_pid" VM.version
jcmd "$java_pid" help
```

`jcmd -l` 用于发现候选；向特定 PID 执行命令涉及与目标 JVM 的诊断通信。**系统里能看到进程，不代表诊断连接一定成功。**

常见影响包括：执行用户和组不匹配、目标关闭 Attach 能力、工具与目标环境不兼容，以及容器的进程或文件系统隔离。[jcmd 文档](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jcmd.html)要求工具与目标位于同一机器，并具有相同的有效用户和组身份，也说明了单独 Docker 容器中进程的枚举限制。

实际排查优先使用与目标 JDK 配套的工具。自定义运行时镜像、精简容器和部分运行环境可能根本没有 `jps`、`jcmd`，这时应使用操作系统工具或已有的应用日志。

## 十、Linux 与 macOS：ps、pgrep、端口和启动脚本

### 10.1 用 ps 查看候选和父子关系

下面的命令适用于常见 Linux 与 macOS 环境：

```bash
ps -axo pid=,ppid=,user=,args= | grep '[j]ava'
```

`[j]ava` 在正则意义上仍匹配 `java`，同时避免匹配当前这条 grep 命令自身。它仍然是字符串搜索：可能包含其他命令，也可能漏掉自定义启动器。

获得 PID 后再单独查看：

```bash
java_pid=24680
ps -p "$java_pid" -o pid=,ppid=,user=,lstart=,args=
```

不要依赖不同平台上 `ps` 默认输出的固定列序，也不要仅看进程名就判断哪个 Java 服务是目标。参数为空或输出缺失，还需要结合退出状态、进程是否已结束以及权限进一步判断。

### 10.2 用 pgrep 按完整命令行筛选

以下明确面向 **Linux 的 procps-ng 工具集**：

```bash
# 按进程名精确匹配，但会得到所有同名实例
pgrep -x java

# 按完整命令行匹配，-a 同时显示完整命令行
pgrep -af 'orders-service[.]jar'
```

`-f` 表示匹配完整命令行，模式是扩展正则表达式，`[.]` 用于匹配字面量的点。完整命令行匹配也可能选中携带相同参数的包装脚本或其他程序，结果需要复核，见 [pgrep 手册](https://man7.org/linux/man-pages/man1/pgrep.1.html)。

macOS 的 `pgrep` 选项与 Linux 不完全相同，不能照搬 `pgrep -af` 对输出含义的假设。可使用：

```bash
pgrep -f 'orders-service[.]jar'
```

然后逐个用 `ps -p` 查看 PID 的信息；平台的具体选项以本机 `man pgrep` 为准。

自动化脚本至少要区分三个结果：没有匹配、唯一匹配、多个匹配。不要用 `head -1` 把多个服务实例的问题悄悄变成“找到唯一 PID”。

### 10.3 已知监听端口时反查

如果机器已安装 `lsof`，可以查看监听 TCP 端口的进程：

```bash
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

Linux 也可以使用：

```bash
ss -ltnp 'sport = :8080'
```

进程详情受权限影响。端口只是一条线索：8080 可能由反向代理或容器端口转发组件监听，也可能有多个监听者。查到 PID 后还要核对可执行文件和命令行，不能直接认定它就是业务 JVM。选项含义可查阅 [lsof 官方教程](https://lsof.readthedocs.io/en/stable/tutorial/)和 [ss 手册](https://man7.org/linux/man-pages/man8/ss.8.html)。

### 10.4 启动时保存 $!，不要把 $$ 当作 Java PID

在 bash/zsh 中直接后台启动 Java，可以立即保存后台任务编号：

```bash
java -jar /opt/apps/orders-service.jar >orders-service.log 2>&1 &
java_pid=$!
printf '%s\n' "$java_pid"
```

对这种直接后台执行的简单命令，`$!` 对应启动的 Java 进程。它只说明后台任务已经被启动，不说明应用已经完成初始化或端口已经就绪。

`$$` 通常指当前 Shell 的 PID；Shell 的 `$PPID` 是它自己的父进程编号，都不是“当前 Java 应用 PID”的通用写法。管道、子 Shell、包装脚本和脚本内部二次后台启动都会改变关系。

如果启动脚本需要被服务管理器监管，可以让最后一步替换 Shell：

```bash
#!/usr/bin/env bash
exec /opt/jdk/bin/java -jar /opt/apps/orders-service.jar
```

`exec` 成功后用 Java 替换当前 Shell 进程，保留该进程 PID；脚本后面的语句不会继续执行。这也能减少服务管理器追踪到包装层的情况。Shell 特殊参数的含义可参考 [Bash 手册](https://www.gnu.org/software/bash/manual/html_node/Special-Parameters.html)。

### 10.5 systemd 服务优先查询服务状态

对于已经正确配置主进程的 Linux systemd 服务：

```bash
systemctl show orders.service --property=MainPID --value
systemctl status orders.service
```

这比全局搜索 JAR 名更能表达“找这个服务”。但 `MainPID` 取决于服务类型、包装方式和运行状态，未运行时可能为 `0`，主进程也可能是包装器。

对于前台运行的 Java 服务，通常让 systemd 直接启动并追踪 Java 即可；不必为了追踪进程额外模拟传统守护进程的后台化流程。服务类型和 PID 文件的处理规则见 [systemd.service 官方文档](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)。

### 10.6 Linux 中用 /proc 进一步核对目标

已经取得候选 PID 后，可以查看实际可执行文件与启动参数：

```bash
java_pid=24680
readlink "/proc/$java_pid/exe"
tr '\0' '\n' < "/proc/$java_pid/cmdline"
```

`exe` 通常指向实际执行的程序，访问受权限限制；`cmdline` 的参数通常以空字节分隔，因此示例将其转换为逐行显示。命令行内容可以被目标进程修改，也可能包含敏感参数，适合现场核对，不能当作不可伪造的身份凭证。相关规则见 [proc_pid_exe](https://man7.org/linux/man-pages/man5/proc_pid_exe.5.html) 和 [proc_pid_cmdline](https://man7.org/linux/man-pages/man5/proc_pid_cmdline.5.html)。

还要注意 `/proc/self` 的“自己”是谁：Java 自己读取它，与 Java 启动一个 `cat`、`readlink` 子进程去读取它，指向的访问进程可能不同。类似地，启动 Shell 执行 `echo $$`，拿到的是 Shell 的编号，不能用来替代 Java 当前 PID。`/proc` 属于 Linux 机制，不适合作为跨 Windows、macOS 的公共实现。

## 十一、Windows：任务管理器与 PowerShell

### 11.1 图形界面与简单列表

可以在任务管理器的“详细信息”页查看 `java.exe`、`javaw.exe` 及 PID，必要时显示命令行列。存在多个 Java 应用时，不能只看映像名称。

命令提示符可以运行：

```bat
tasklist /FI "IMAGENAME eq java.exe"
tasklist /FI "IMAGENAME eq javaw.exe"
```

这些命令适合初步查看，按应用区分时更推荐查询完整命令行。过滤语法见 [tasklist 官方文档](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tasklist)。

### 11.2 PowerShell 按命令行区分应用

```powershell
Get-CimInstance Win32_Process `
    -Filter "Name = 'java.exe' OR Name = 'javaw.exe'" |
    Select-Object ProcessId, ParentProcessId, ExecutablePath, CommandLine |
    Format-List
```

继续按 JAR 名筛选：

```powershell
Get-CimInstance Win32_Process `
    -Filter "Name = 'java.exe' OR Name = 'javaw.exe'" |
    Where-Object { $_.CommandLine -like '*orders-service.jar*' } |
    Select-Object ProcessId, ParentProcessId, CommandLine
```

反引号是 PowerShell 的续行符，后面不能再带空格；也可以把对应命令写成一行。

`Win32_Process` 中的 `ProcessId`、`ParentProcessId`、`ExecutablePath` 和 `CommandLine` 字段见 [Microsoft 官方文档](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-process)。部分字段可能因为权限而不可读；筛选结果也可能包含多个实例。

如果只需要简单查看：

```powershell
Get-Process -Name java,javaw -ErrorAction SilentlyContinue |
    Select-Object Id, ProcessName
```

这里 `Id` 就是系统进程 PID，见 [Get-Process 文档](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/get-process)。PowerShell 的 `$PID` 自动变量表示当前 PowerShell 进程编号，不能用于获取 Java PID，也不要用大小写变体 `$pid` 作为自定义赋值变量。

## 十二、Docker 与 Kubernetes：同一个进程可能有两个 PID

### 12.1 为什么应用打印 1，宿主机却看到 31542

Linux PID 命名空间可以让同一个进程在不同视角下使用不同编号。例如：

```text
Linux 宿主机视角                  容器内部视角
PID 31542  ───── 同一个 Java 进程 ───── PID 1
```

容器没有隐藏在 PID 后面的“全局统一编号”。Java 在容器内通过标准 API 获取的通常是它在自身 PID 命名空间中的编号。命名空间的隔离与层级关系见 [pid_namespaces 手册](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)。

Java 也不一定是容器内 PID 1：可能有 `tini`、其他 init 进程、Shell 包装层，或者共享进程命名空间配置。

### 12.2 Docker 中分别查询

容器中已经具备 JDK 工具时，可以在容器内部发现 JVM：

```bash
docker exec orders-container jcmd -l
```

如果只有操作系统工具，则根据镜像实际提供的命令查询；精简镜像可能连 Shell 和 `ps` 都没有，不能假定 `docker exec ... sh` 总是可用。

在 Docker 管理端，可以查询运行中容器的进程与入口进程编号：

```bash
docker top orders-container
docker inspect --format '{{.State.Pid}}' orders-container
```

`State.Pid` 是容器入口进程在 Docker 引擎所在主机上的 PID，**只有入口进程就是 Java 时，它才对应目标 JVM**。`docker top` 则用于查看容器中的运行进程，具体选项受引擎环境影响，参考 [Docker top](https://docs.docker.com/reference/cli/docker/container/top/) 与 [Docker inspect](https://docs.docker.com/reference/cli/docker/inspect/) 文档。

Docker Desktop 在 macOS/Windows 上运行 Linux 容器时，引擎位于 Linux 虚拟机中。此处所谓的宿主机 PID 属于那台 Linux 环境，不能拿它去本机 macOS/Windows 进程列表中逐号对应。连接远程 Docker 引擎时也要按引擎所在主机理解。

### 12.3 Linux 中核对命名空间映射

已在 Linux 宿主机确认目标 JVM 的宿主机 PID 后，可以读取：

```bash
host_java_pid=31542 # 替换为实际核对过的目标 JVM PID
grep -E '^(Name|Pid|PPid|NStgid|NSpid):' "/proc/$host_java_pid/status"
```

示意输出：

```text
Name:   java
Pid:    31542
PPid:   31490
NStgid: 31542  1
NSpid:  31542  1
```

`NStgid` 展示线程组 ID，即常说的进程 PID 在各层命名空间中的对应值；`NSpid` 展示线程 ID 的对应值。读取进程组长的状态时，二者通常一致。顺序从挂载该 procfs 的命名空间开始，向更内层排列，不能脱离 `/proc` 的挂载视角解释。字段定义见 [proc_pid_status 手册](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html)。

### 12.4 Kubernetes 中先明确 Pod 与容器

对于容器中自带 `jcmd` 的情况：

```bash
kubectl exec -n production orders-pod -c app -- jcmd -l
```

这里显式指定命名空间、Pod 和容器，避免多容器 Pod 中查错位置。替换这些示例名称后再运行。

如果业务镜像没有诊断工具，应根据集群允许的排障方式使用已有观测信息或调试环境；调试容器能看到什么，还取决于进程命名空间共享、目标选择和权限。不要仅凭“在同一个 Pod”就认定能够看见和 Attach 所有进程。可参考 Kubernetes 的[容器内执行命令说明](https://kubernetes.io/docs/tasks/debug/debug-application/get-shell-running-container/)与[运行中 Pod 调试指南](https://kubernetes.io/docs/tasks/debug/debug-application/debug-running-pod/)。

对于 `jcmd` 或其他需要 PID 的工具，始终先确认它运行的位置与 PID 来源是否处于可对应的命名空间。容器外发现的编号与容器内编号不能随意互换。

## 十三、工程实践：日志、PID 文件与 Spring Boot

### 13.1 在启动时记录进程身份

Java 9+ 的普通应用，可以在初始化阶段记录一次：

```java
ProcessHandle current = ProcessHandle.current();
System.out.println("application=orders-service"
        + " pid=" + current.pid()
        + " processStart=" + current.info().startInstant()
                .map(Object::toString).orElse("unknown"));
```

真实项目应接入现有日志框架，并补充实例或容器标识。Java 8 则使用已经验证过的兼容方式，不必为记录 PID 每次启动一个外部 `ps` 进程。

同一个存活进程中的 PID 不会因为创建线程而变化，通常在启动时获取一次即可。PID 也不能替代请求 trace ID，更不适合作为分布式环境的全局唯一实例标识。

### 13.2 PID 文件的用途与局限

传统启动脚本有时会写入：

```text
/run/orders-service/application.pid
```

文件内容只有一行 PID。它方便其他工具发现编号，但不是“应用仍在运行”的证明，也不是可靠的互斥锁。

使用时至少应考虑：

1. 目录由应用或服务管理器按合适权限创建，避免多实例共用同一个文件。
2. 读到的内容必须按正整数校验，不能直接拼接进命令执行。
3. 进程存在与否、命令行和启动时间需要重新核对，防止陈旧文件遇上 PID 复用。
4. 应用异常退出可能来不及删除文件；旧实例的清理逻辑也不应误删新实例的文件。
5. 文件应标明或约定 PID 的视角，容器内写出的 PID 不一定能直接给宿主机工具使用。

在 Unix 上，`kill -0` 只是存在性和信号权限检查，既不验证应用身份，也不能证明服务健康；失败还可能是权限问题。即便编号存在，也可能对应僵尸进程或错误实例。

服务已由 systemd、容器运行时或编排平台管理时，应优先使用它们维护的生命周期与健康状态，避免把 PID 文件变成第二套不一致的事实来源。

### 13.3 Spring Boot 的 ApplicationPidFileWriter

下面示例以 **Spring Boot 3.4 系列 API** 为参照，保留项目自身的 Spring Boot 入口注解和其他配置，仅将启动逻辑改成：

```java
import org.springframework.boot.SpringApplication;
import org.springframework.boot.context.ApplicationPidFileWriter;

// 放入现有的 @SpringBootApplication 入口类
public static void main(String[] args) {
    SpringApplication application = new SpringApplication(Application.class);
    application.addListeners(new ApplicationPidFileWriter());
    application.run(args);
}
```

把 `Application.class` 替换为项目真实入口类，并配置：

```properties
spring.pid.file=/run/orders-service/application.pid
spring.pid.fail-on-write-error=true
```

**仅配置 `spring.pid.file` 并不等于已经注册写文件监听器。** 还应确保目标目录存在且运行用户可写。

[ApplicationPidFileWriter 文档](https://docs.spring.io/spring-boot/3.4/api/java/org/springframework/boot/context/ApplicationPidFileWriter.html)说明了文件名覆盖、默认写入失败处理及监听事件要求。示例启用了写入失败时报错，避免运维依赖 PID 文件而实际未生成。

PID 文件的生成时间由监听事件决定，默认并不代表应用已经就绪。多应用上下文、同一 JVM 多次启动及其他 Spring Boot 版本的行为，应结合目标版本验证；不要把本文的 Java 8 基础示例与 Spring Boot 3.x 的 Java 版本要求混为一谈。

## 十四、动手验证：让 Java 输出与系统观察互相对照

### 14.1 在独立临时目录编译

下面实验适用于 macOS 的 bash/zsh 和常见 Linux bash，要求完整 JDK 8。先创建临时目录：

```bash
pid_lab_dir="$(mktemp -d "${TMPDIR:-/tmp}/worthy-pid-lab.XXXXXX")"
cd "$pid_lab_dir"
java -version
javac -version
```

将第五节的 `LegacyPid.java` 和第六节的 `CompatiblePid.java` 保存到这里：

```bash
javac LegacyPid.java CompatiblePid.java
java LegacyPid
java CompatiblePid
```

这两次命令启动了两个不同的 JVM，打印的 PID 通常不同。不能用“两个数字不一样”来判断工具实现有误。

### 14.2 对同一个存活进程交叉验证

在同一个实验终端执行：

```bash
java -cp . LegacyPid --hold >pid-demo.log 2>&1 &
java_pid=$!
printf 'shell observed pid=%s\n' "$java_pid"
ps -p "$java_pid" -o pid=,ppid=,user=,args=
jps -l
jcmd "$java_pid" VM.command_line
cat pid-demo.log
wait "$java_pid"
```

Java 程序只存活约一分钟，请及时执行查询。操作太晚时工具可能报告进程不存在；如果第一次读取日志时尚未完成初始化，稍后再读取。`wait` 等待的是当前 Shell 启动的这个后台进程，正常情况下将在一分钟内自然返回。

对于本实验的常规本地 HotSpot/OpenJDK 环境，预期核对关系为：

```text
$! 观察到的 PID
    = ps 显示的 PID
    = LegacyPid 打印的 PID
    = runtimeName 中 @ 前的数字
```

同时确认 `jps` 的候选项和 `jcmd` 返回的目标命令行确实指向 `LegacyPid --hold`。不要只比较数字。

### 14.3 验证 Java 8 名称解析的边界

将下面的 `LegacyPidChecks.java` 放在同一目录：

```java
public class LegacyPidChecks {
    private static void absent(String name) {
        if (LegacyPid.parseRuntimeName(name).isPresent()) {
            throw new AssertionError("Unexpected PID for: " + name);
        }
    }

    public static void main(String[] args) {
        if (LegacyPid.parseRuntimeName("24680@host").orElse(-1L) != 24680L) {
            throw new AssertionError("Valid name rejected");
        }
        absent(null);
        absent("");
        absent("custom-runtime");
        absent("@host");
        absent("24680@");
        absent("0@host");
        absent("-1@host");
        absent("abc@host");
        absent("+12@host");
        absent("9223372036854775808@host");
        System.out.println("LegacyPid parsing checks passed");
    }
}
```

运行：

```bash
javac LegacyPid.java LegacyPidChecks.java
java LegacyPidChecks
```

测试只证明这些输入的处理符合工具类约定，并不能证明所有 JVM 都提供相同名称格式。

### 14.4 本文实际验证范围

本机 Java 环境为 Zulu OpenJDK `1.8.0_512`、Apple Silicon、macOS。验证记录如下：

| 项目 | 验证方式与范围 |
| --- | --- |
| `LegacyPid` | 使用 JDK 8 编译运行，与存活进程的系统 PID 交叉核对 |
| 名称解析边界 | 执行 `LegacyPidChecks`，覆盖合法值、空值、格式异常、非正数和溢出 |
| `CompatiblePid` | 使用 JDK 8 编译运行，验证旧版回退路径 |
| `ps`、`jps`、`jcmd` | 对实验进程核对目标编号和启动命令 |
| Java 9+/10+ 示例 | 核对官方 API 文档；本机未安装相应 JDK，未实际编译运行 |
| Linux、Windows、容器和 Spring Boot 示例 | 依据对应官方 API 或命令文档整理，未在本机搭建这些环境实测 |

本次交叉核对中，实验 JVM 的 PID 为 `10986`：Java 输出 `pid=10986`、运行时名称前缀为 `10986@...`，`ps` 和 `jps` 指向同一 `LegacyPid` 进程，`jcmd 10986 VM.command_line` 返回 `LegacyPid --hold`。该编号仅是本次验证记录，实验结束后不能继续用于定位目标。

部署前应使用目标 JDK、操作系统、运行用户和容器镜像重新验证，尤其是跨版本工具包的新版路径与容器诊断通信。

## 十五、常见问题与排查顺序

| 现象 | 常见原因 | 如何确认 |
| --- | --- | --- |
| `System.getProperty("pid")` 为空 | `pid` 并不是 Java 规定的标准 PID 属性 | 使用正式 API；自定义属性只能按项目约定解释 |
| 找不到 `ProcessHandle` | 使用 Java 8 或编译配置限制为 Java 8 API | 检查 `java -version`、`javac -version` 和构建工具链 |
| `RuntimeMXBean` 没有 `getPid()` | 目标 API 版本低于 Java 10 | 使用 Java 9 的 `ProcessHandle`，或 Java 8 兼容方案 |
| 本机编译成功，服务器报版本错误 | 字节码目标高于运行环境 | 检查编译 release/target 与部署 JRE |
| `jps` 没列出已知 Java 进程 | 权限、实现、性能数据可见性或容器隔离 | 用系统进程工具和运行身份交叉核对 |
| `jcmd -l` 能发现但诊断失败 | Attach 限制、用户组、工具版本或命名空间问题 | 使用配套工具，并确认目标用户与运行位置 |
| 按 JAR 名搜出多个 PID | 多实例、灰度版本或包装层均匹配 | 核对命令行、用户、启动时间和部署实例 |
| Java 打印 1，宿主机找不到对应服务 | 使用了不同 PID 命名空间 | 查看容器进程和 Linux `/proc` 映射 |
| 子进程 PID 指向 `sh` 或包装器 | 实际启动的是包装层 | 直接启动 Java，或检查父子进程关系 |
| PID 文件存在，但服务不可用 | 陈旧文件、PID 复用或服务未就绪 | 同时检查身份、生命周期状态和健康状态 |
| Java 重启后 PID 改了 | 新进程获得了新编号 | 使用实例标识与启动时间关联日志 |

排查时可以按下面顺序收敛：

1. 明确要获取当前 JVM、子进程，还是外部运行中的服务。
2. 确认 Java 版本，以及命令实际在哪个主机、用户和命名空间中运行。
3. 用最直接的 API 或服务管理器信息得到候选 PID。
4. 用命令行、启动时间与应用标识确认目标身份。
5. 将“进程编号存在”“诊断连接可用”“应用健康”分别验证。

对于新项目，Java 9+ 的 `ProcessHandle.current().pid()` 已经解决了获取当前 PID 的大部分需求。剩下的工程工作，是让这个编号始终和正确的运行实例、时间及观察位置关联起来。
