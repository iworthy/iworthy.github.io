在飞牛 fnOS 上运行 Mihomo，最初只是希望 NAS 访问外部服务时不必逐个应用设置代理。真正打开 TUN 后，问题才陆续出现：容器运行正常，TUN 却初始化失败；节点测速成功，系统请求仍然超时；IPv4 通了，IPv6 又解析不到地址。同时，原有的 Tailscale 异地访问还必须保留。

这篇文章整理一次实际部署：使用 MetaCubeXD 一体化镜像管理 Mihomo，让 NAS 本机流量按规则分流，内网与 Tailscale 绕过 TUN，并把系统 DNS、IPv6 和故障回退一起配置完整。文中的 IP、密钥和订阅地址均使用示例或占位符。

## 一、先确定范围：NAS 自用，还是 OpenWrt 旁路由

| 需求 | NAS 上运行 Mihomo TUN | OpenWrt／iStoreOS 旁路由 |
| --- | --- | --- |
| NAS 本机程序自动分流 | 本文配置的目标 | 需要 NAS 将相应流量交给旁路由 |
| 家中多台设备统一分流 | 还需要额外设计转发、网关和 DNS | 更适合承担这一角色 |
| 部署组成 | Docker、Mihomo 配置、宿主机 DNS | 虚拟机或独立设备、路由系统、网关与 DNS |
| 本文验证范围 | NAS 主机网络、IPv4／IPv6、管理入口 | 没有部署或验证旁路由方案 |

如果目标是让电视、手机、电脑一起经同一个出口分流，可以继续阅读本站的 [fnOS 虚拟 iStoreOS 软路由安装与配置指南](/pages/54ee09/)。本次目标只涉及 NAS 自用，因此保持原有家庭网关和 DHCP，不把 NAS 改成全家设备的网关。

**Host 网络模式只说明这个容器与宿主机共享网络命名空间，不能据此推断所有 bridge、macvlan 容器都已被代理。** 这些容器要按各自的网络路径另外验证。

本次环境为 fnOS 1.2.1011、x86_64，下载到的一体化镜像面板版本为 1.275.2，内置 Mihomo 为 1.19.27。以下排障结论来自这组版本，不能推断其他版本一定具有相同行为。`latest` 是可变化的标签，稳定运行后建议记录镜像摘要和实际内核版本。

## 二、准备目录、密钥和 Docker 项目

本文约定：

| 项目 | 示例值 |
| --- | --- |
| NAS 管理地址 | `http://192.168.1.100:5666` |
| 原有路由器 | `192.168.1.1` |
| MetaCubeXD 面板 | `http://192.168.1.100:17880` |
| Mihomo API | `http://192.168.1.100:19090` |
| 本机混合代理端口 | `7890` |
| 本机 DNS | `127.0.0.2:53` |
| 项目目录 | `/vol1/1000/docker/metacubexd` |

IP 和目录都要按实际情况替换。先记录当前网口的 IP、网关、IPv4／IPv6 DNS 分配方式，保留一个通过局域网 IP 登录 fnOS 的管理窗口。若已有旧 Clash 和面板，先备份配置与 Compose 文件；确认新服务可用后，再停用并删除旧容器，避免端口冲突，也保留回退材料。

这里使用官方提供的 `ghcr.io/metacubex/metacubexd-server`，把面板、配置管理和内核运行集中到一个容器。其 TUN 部署方式见 [MetaCubeXD 官方说明](https://github.com/MetaCubeX/metacubexd#readme)。

可在 fnOS 的 Docker 项目中部署以下 Compose；使用 SSH 时，先进入项目目录，再执行 `docker compose up -d`。创建 `data` 子目录，并在项目目录创建 `.env`：

```dotenv
CONTROL_TOKEN=REPLACE_WITH_RANDOM_CONTROL_TOKEN
CLASH_SECRET=REPLACE_WITH_DIFFERENT_RANDOM_CLASH_SECRET
```

分别运行两次 `openssl rand -hex 32` 生成不同的随机值，替换占位符。不要把真实 `.env`、订阅地址或导出的节点配置提交到公开仓库。

`docker-compose.yaml`：

```yaml
services:
  clash:
    image: ghcr.io/metacubex/metacubexd-server:latest
    container_name: fnos-clash
    restart: unless-stopped
    network_mode: host
    cap_add:
      - NET_ADMIN
    devices:
      - /dev/net/tun:/dev/net/tun
    environment:
      TZ: Asia/Shanghai
      CONTROL_TOKEN: "${CONTROL_TOKEN:?CONTROL_TOKEN required}"
      CLASH_SECRET: "${CLASH_SECRET:?CLASH_SECRET required}"
      CONTROL_PORT: "17880"
      CLASH_API_PORT: "19090"
      MIXED_PORT: "7890"
      DEFAULT_BACKEND_URL: "http://192.168.1.100:19090"
    volumes:
      - /vol1/1000/docker/metacubexd/data:/data
    stop_grace_period: 30s
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:17880/api/control/health"]
      interval: 30s
      timeout: 5s
      start_period: 20s
      retries: 3
```

Host 网络模式下不需要再写 `ports`，对应宿主机端口必须空闲。本次使用 `NET_ADMIN` 和 `/dev/net/tun`，没有启用整个容器的 `privileged`。

`CONTROL_TOKEN` 是控制接口令牌，**不是面板登录密码**：服务会将它注入浏览器页面。`CLASH_SECRET` 用于 Mihomo API。面板和 API 应限制在可信管理网络内，Host 模式本身不提供来源限制；若 NAS 有公网入口，需要用实际生效的访问控制限制这些端口。相关设计见 [官方控制接口说明](https://github.com/MetaCubeX/metacubexd#readme)。

如果 NAS 拉取 GHCR 镜像很慢，可以在能正常下载、且有 Docker 的机器上执行：

```bash
docker pull --platform linux/amd64 ghcr.io/metacubex/metacubexd-server:latest
docker save -o metacubexd-server.tar ghcr.io/metacubex/metacubexd-server:latest
```

把归档上传到 NAS，再从 fnOS 的“Docker → 本地镜像 → 添加镜像 → 从 NAS 文件添加”导入。这是 x86_64 场景的下载替代方式，其他架构应选择对应平台。

## 三、在本地面板创建完整 Mihomo 配置

打开面板，连接后端 `http://192.168.1.100:19090`，Secret 填 `.env` 中的 `CLASH_SECRET`。在配置管理中创建本地配置，把下面的内容粘贴到编辑器。

先替换四处信息：NAS 面板地址、`secret`、订阅链接、路由器 DNS 地址。订阅需要提供 Mihomo 可读取的代理提供者内容；如果是网页、登录页面或不兼容的格式，应先确认订阅格式。此处订阅通过 `DIRECT` 更新，首次下载要能直接访问订阅服务器。

**模板先设 `tun.enable: false`。先保存、校验并激活，确认订阅和节点正常，再开启 TUN；此时先不要修改系统 DNS。**

国内域名与 IP 规则来自 [MetaCubeX/meta-rules-dat](https://github.com/MetaCubeX/meta-rules-dat)，需要确认两份规则都已加载。模板中 `allow-lan: false` 将混合代理端口限制为本机使用；它不影响已经单独设置监听地址的面板与 API。

### 为什么既写排除网段，又写 DIRECT

`route-exclude-address` 在 TUN 路由层让目标流量绕过接管；`DIRECT` 是流量进入 Mihomo 后的出站选择。两者作用位置不同，所以这里同时保留。字段含义见 [Mihomo TUN 文档](https://wiki.metacubex.one/config/inbound/tun/)。

Tailscale 的常见 IPv4 地址来自 `100.64.0.0/10`，IPv6 使用 `fd7a:115c:a1e0::/48`，其本机 DNS 地址为 `100.100.100.100`。IPv6 前缀虽然已包含在 `fc00::/7` 中，仍单独列出以便维护。[Tailscale 保留地址说明](https://tailscale.com/docs/reference/reserved-ip-addresses)

这张排除表适合本次私网布局。若 Tailscale 还接收其他子网路由，应逐项核对目标网段；使用公网形式的内网地址时，也要补充对应 CIDR。本文没有配置 Tailscale exit node 与代理的组合出口策略。

`+.ts.net` 的 DNS 策略交给 Tailscale 本机解析器；只有在 NAS 已运行 Tailscale、该解析器可用时才保留。没有 Tailscale 的环境应删除这一条。内网域名则交给原路由器，前提是路由器确实能解析这些名称；mDNS 的 `.local` 仍依赖原有组播机制。

## 四、分两步启用：先验证代理，再接管宿主机

保存并激活配置后，先在面板确认订阅有节点、规则提供者没有报错，再选一个可用节点测试。规则下载使用 `PROXY`，节点本身需要先可用。

此时可以在 NAS 上显式指定本机代理测试：

```bash
curl --proxy http://127.0.0.1:7890 --connect-timeout 10 --max-time 30 \
  -sS -o /dev/null -w '%{http_code}\n' \
  https://www.gstatic.com/generate_204
```

返回 `204` 说明这次请求通过显式代理成功。它还不能证明 TUN 或宿主机默认 DNS 已经正常。先备份这份可用配置，再将 `tun.enable` 改为 `true`，保存并激活，查看运行状态与日志。

### 坑一：容器还在运行，TUN 已经失败

本次启用 `auto-redirect: true` 时反复出现：

```text
Start TUN listening error: auto redirect: conn.Receive: netlink receive: file exists
```

进程和面板仍在，但实际运行配置中的 TUN 没有成功开启。`auto-redirect` 涉及 Linux 自动配置重定向规则；本次未进一步证明究竟是哪一项现有网络对象导致 `EEXIST`。最终保留 `auto-route: true`，关闭 `auto-redirect`，NAS 本机流量通过后续验证。

因此，本文的 `auto-redirect: false` 是这组环境下的可用配置，不是所有 Linux 场景的通用建议。遇到类似问题，应先核对日志、运行配置与实际流量，不要直接清空宿主机的整套防火墙规则，影响 Docker 或 Tailscale。

## 五、把系统 DNS 真正接到 Mihomo

### 坑二：排除了内网，也绕开了去路由器的 DNS

本次最容易误判的现象是：**面板节点测速成功，NAS 普通 HTTPS 请求却超时。** 对比发现，系统仍向局域网路由器查询 DNS，部分目标域名拿到异常地址；显式使用 Mihomo DNS 后，同一请求就成功了。

原因在于：模板排除了 `192.168.0.0/16`，发往路由器的 DNS 请求也可能沿这条绕过路径出去。只写 `dns-hijack: any:53`，并不能据此认定系统一定使用了 Mihomo DNS。

本次采用显式的本机 DNS 路径：

```text
NAS 系统 DNS → 127.0.0.2:53 → Mihomo
                            ├─ 国内域名 → 国内 DoH
                            ├─ 其他域名 → 经 PROXY 查询 DoH
                            ├─ ts.net → Tailscale 本机 DNS
                            └─ 内网域名 → 原路由器
```

`proxy-server-nameserver` 用于解析代理节点的域名，避免节点解析依赖尚未建立的代理连接；具体字段以 [Mihomo DNS 文档](https://wiki.metacubex.one/config/dns/) 为准。

### 坑三：fnOS 全局手动 DNS 与本机 53 端口冲突

在这台 fnOS 上，使用全局“手动设置 DNS 服务器”时，系统尝试启用自己的 DNS 转发服务。Mihomo 已监听 53 端口后，界面提示“端口 53 已被占用，请停止相关服务后重试”。输入 `127.0.0.1:1053` 也不行，因为该输入框要求 DNS IP 地址，不接受附带端口的形式。

最终没有开启这个全局选项，而是修改**正在联网的网口**：

1. 确认 Mihomo 已成功监听 `127.0.0.2:53`，且这个地址端口没有被其他服务占用。
2. 进入“系统设置 → 网络设置”，编辑当前网口。
3. IPv4 地址分配保持原来的 DHCP 或静态方式，仅将 **DNS 分配改为手动，填写 `127.0.0.2`**。
4. IPv6 地址分配继续自动并保持启用，将 IPv6 DNS 改为手动且留空，避免继续从路由器接收另一条 DNS 路径。本次版本允许保存这一设置。
5. 保持全局手动 DNS 选项关闭，保存后重新核对网口显示的 DNS，并确认 fnOS 管理页面仍可访问。

不需要因为 DNS 调整关闭 OVS，也不需要改网关。通过 IPv4 地址访问 DNS 服务器，照样可以查询 AAAA 记录，因此不必为了让 DNS 路径统一而关闭 IPv6。

### IPv6：记录观察结果，不把版本问题写成通则

本次在内置 Mihomo 1.19.27 上使用 `fake-ip` 时，测试目标的 AAAA 查询没有得到可用结果，强制 IPv6 HTTPS 访问随之失败。换成 `redir-host` 后，IPv4 与 IPv6 测试都通过，因此最终模板采用后者。

这只是本次配置和版本下的观察，不能推出所有 Mihomo 版本的 Fake-IP 都不支持 IPv6。更换版本或 DNS 模式后，应重新验证 A、AAAA 和实际 HTTPS 请求；拥有公网 IPv6 地址本身不能证明代理链路正常。

## 六、验证要覆盖系统请求、管理入口和重启

下面的命令可在 NAS SSH 中执行。`--noproxy '*'` 用于绕过 curl 的显式代理设置，检查当前宿主机网络路径；它不会绕过 TUN。应先确认 TUN 已在运行，且测试目标按预期命中代理策略。

```bash
# 不指定 HTTP 代理，分别测试 IPv4 和 IPv6
curl --noproxy '*' -4 --connect-timeout 10 --max-time 30 \
  -sS -o /dev/null -w '%{http_code}\n' \
  https://www.gstatic.com/generate_204

curl --noproxy '*' -6 --connect-timeout 10 --max-time 30 \
  -sS -o /dev/null -w '%{http_code}\n' \
  https://www.gstatic.com/generate_204

# 测试直连规则覆盖的国内站点
curl --noproxy '*' --connect-timeout 10 --max-time 30 \
  -sS -o /dev/null -w '%{http_code}\n' https://www.baidu.com/
```

也可使用具备相应工具的临时 Host 网络容器做同类测试。本次实际从宿主机网络进行的无显式代理测试结果为：外部测试地址 IPv4、IPv6 均返回 `204`，国内 HTTPS 站点返回 `200`。

随后从另一台电脑分别通过以下路径访问 fnOS 管理页：

| 路径 | 本次结果 | 验证目的 |
| --- | --- | --- |
| NAS 局域网 IP | HTTP 200 | 本地管理连接仍可用 |
| NAS 的 Tailscale IPv4 | HTTP 200 | Tailscale IPv4 管理访问仍可用 |
| NAS 的 Tailscale IPv6 | HTTP 200 | Tailscale IPv6 管理访问仍可用 |

IPv6 字面地址作为 URL 主机时要加方括号，例如 `http://[实际地址]:5666/`。实际 Tailscale 地址无需写入公开文章。

最后重启 `fnos-clash` 容器，再重复上面的测试。本次重启后这些检查仍然通过，其他业务容器保持运行。这里验证的是这些管理入口和 HTTP／HTTPS 请求，没有覆盖所有 Tailscale 对端、MagicDNS 名称解析或全部容器协议。

## 七、提前准备两种回退

第一种是保留订阅的备份：复制当前完整配置，把 `tun.enable` 改为 `false`。需要排查自动接管问题时，可以切回它，并继续用显式代理测试。

第二种是完全直连的应急配置。它仍然保留 `127.0.0.2:53` 的 DNS 服务，关闭 TUN，删除代理提供者、代理组及远程规则提供者，把所有请求设为直连。独立保存以下配置，不要直接覆盖正常配置：

```yaml
mixed-port: 7890
allow-lan: false
mode: rule
log-level: info
ipv6: true
external-controller: 0.0.0.0:19090
secret: "REPLACE_WITH_CLASH_SECRET"
external-controller-cors:
  allow-origins:
    - "http://192.168.1.100:17880"
  allow-private-network: true
tun:
  enable: false
dns:

  listen: 127.0.0.2:53

```

这份配置不依赖订阅和远程规则；本机 Tailscale 仍需按实际环境决定是否保留。切换到它只能帮助恢复直接可达的网络，不会让原本无法直连的服务自动可用。

**如果准备停止或卸载整个容器，要先把网口 IPv4／IPv6 DNS 分配恢复为原来的自动或有效服务器设置，再停容器。** 否则系统仍向已停止服务的 `127.0.0.2` 查询，表面现象就是“关掉代理后连普通网站都打不开”。

这次部署中，增加 TUN 本身只需要设备、权限和少量配置；后续工作主要在于确认 DNS 实际走向、保留原有内网路由，并用系统请求和重启验证结果。把这些步骤与回退配置一起准备好，才算完成 NAS 自用代理的部署。
