Homebrew 日常维护最容易混淆的几件事，是把“更新软件定义”当成“升级软件”，把“清理缓存”当成“卸载依赖”，以及遇到任何异常都给命令加上 `--force`。这些操作各有边界，用错命令可能毫无效果，也可能删除本来需要保留的内容。

本文以 macOS 上已安装的 Homebrew 为主，按查询、安装、升级、强制修复、空间清理和故障排查逐项说明。Formula 相关命令通常也适用于 Linux；Cask 应用示例面向 macOS。各节命令是独立示例，请按场景选择执行，尤其不要整篇复制运行。

## 一、先理解 Homebrew 管理的对象

| 名称 | 含义 | 常见例子或位置 |
| --- | --- | --- |
| Formula | 软件包定义，常用于命令行工具、库和服务 | `wget`、`git`、`redis` |
| Cask | 应用安装定义，macOS 上常用于桌面应用等 | `firefox` |
| Bottle | Formula 的预编译包，能避免本地源码编译 | 安装时出现的 bottle 下载与解包步骤 |
| Tap | 提供软件定义或扩展命令的仓库 | 第三方维护的软件源 |
| Prefix | Homebrew 安装前缀 | 用 `brew --prefix` 查询 |
| Cellar | Formula 各个已安装版本的存放目录 | 用 `brew --cellar` 查询 |
| Keg | 某个 Formula 的某一个已安装版本目录 | `Cellar/wget/某版本/` |
| Keg-only | 安装后不会自动链接到公共前缀的软件包 | 具体原因和使用方法见 `brew info` |

Formula 并不意味着每次都从源码编译：有适用的 Bottle 时，Homebrew 通常直接使用预编译包。Cask 则按定义处理上游应用或安装器。术语解释见[官方命令手册](https://docs.brew.sh/Manpage#terminology)。

Apple Silicon 常见前缀是 `/opt/homebrew`；Intel Mac 的既有安装常见于 `/usr/local`；Linux 常见于 `/home/linuxbrew/.linuxbrew`。自定义安装、迁移或 Rosetta 环境可能不同，脚本应优先查询路径，而不是写死目录。当前支持范围与安装要求请查[官方安装文档](https://docs.brew.sh/Installation)。

```bash
# Homebrew 版本和环境信息
brew --version
brew config

# 当前正在使用哪一个 brew
command -v brew
type -a brew

# 关键目录
brew --prefix
brew --repository
brew --cellar
brew --cache
```

`brew --repository` 是 Homebrew 自身 Git 仓库的位置，不能与 Cellar、缓存目录混为一谈。后面的仓库重置、软件卸载和缓存清理，分别作用于不同对象。

## 二、查询、搜索与安装

### 2.1 搜索软件，先看安装说明

```bash
# 按名称搜索
brew search wget
brew search --cask firefox

# 用正则表达式缩小范围
brew search '/^python@/'

# 查看版本、来源、依赖和安装后提示
brew info wget
brew info --cask firefox
```

安装前留意 `brew info` 中的 **Caveats**，它可能包含 PATH、服务启动、初始化或版本迁移要求。安装成功不一定意味着软件已经进入当前终端的搜索路径，也不意味着数据库已经完成配置。查询命令参见 [`brew info` 官方实现](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/info.rb)。

### 2.2 安装 Formula 和 Cask

```bash
# 命令行软件
brew install wget

# 一次安装多个 Formula
brew install wget jq tree

# macOS 桌面应用
brew install --cask firefox
```

显式使用 `--formula`、`--cask` 能在名称有歧义时明确对象。Formula 的日常安装和更新通常不需要 `sudo`；部分 Cask 安装器确实可能要求系统授权，按实际提示处理即可。不要把所有命令都改成 `sudo brew ...`。权限边界见[官方安装说明](https://docs.brew.sh/Installation#running-without-sudo)。

### 2.3 查看已安装内容

```bash
# 所有已安装的 Formula 和 Cask
brew list

# 按类型查看
brew list --formula
brew list --cask

# Formula 已安装的版本
brew list --formula --versions

# 查看某个 Formula 的安装文件
brew list wget
```

列表和版本参数的含义见 [`brew list` 官方实现](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/list.rb)。核对桌面应用的版本时，可结合 `brew info --cask 应用名` 与应用自身的“关于”窗口；应用可能通过自己的更新器升级。

## 三、日常更新：update、outdated、upgrade

### 3.1 三个命令分别做什么

| 命令 | 主要作用 | 是否升级已安装应用或工具 |
| --- | --- | --- |
| `brew update` | 更新 Homebrew 自身及软件定义等元数据 | 不执行已安装软件的常规版本升级 |
| `brew outdated` | 列出当前元数据判断为可升级的软件 | 否 |
| `brew upgrade` | 升级符合条件的已安装软件 | 是 |

一个清晰的维护流程是：

```bash
brew update
brew outdated --verbose
brew upgrade
```

如果只想升级一个软件：

```bash
brew upgrade wget
brew upgrade --cask firefox
```

`brew update` 成功后，旧版工具仍然存在是正常现象；接下来的 `brew upgrade` 才负责升级。该流程见[官方 FAQ](https://docs.brew.sh/FAQ#how-do-i-update-my-local-packages)。

### 3.2 按类型查看、预览和升级

```bash
# 查看待升级的 Formula 和 Cask
brew outdated --formula --verbose
brew outdated --cask --verbose

# 预览升级计划
brew upgrade --dry-run

# 分别升级
brew upgrade --formula
brew upgrade --cask
```

预览针对当前环境与软件定义；正式执行前若软件源或依赖状态发生变化，结果也可能变化。升级目标软件时，Homebrew 还可能升级依赖，或重装链接已损坏的相关软件。因此“只指定一个包”并不保证只改变一个安装目录。参见 [`outdated`](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/outdated.rb) 和 [`upgrade`](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/upgrade.rb) 的官方说明。

数据库、语言运行时等软件升级前，还应阅读其迁移说明。包管理器完成安装，并不代表应用数据格式、项目依赖和服务配置已经兼容新版本。

### 3.3 为什么部分 Cask 没有进入升级列表

普通检查默认会跳过一部分 Cask，例如声明 `auto_updates true` 的应用，以及使用 `version :latest` 的应用。需要把它们也纳入检查时：

```bash
# 先查看扩大范围后的结果
brew outdated --cask --greedy --verbose

# 再按需要升级
brew upgrade --cask --greedy
```

`--greedy` 扩大的是 Cask 检查范围，不能保证精确识别所有应用内部版本，也不是“强制升级全部软件”的通用开关。已有应用内自动更新机制时，是否交给 Homebrew 再次处理，应按应用情况决定。具体语义见 [`upgrade` 的 Cask 参数](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/upgrade.rb)。

## 四、“强制更新”应当选哪个命令

### 4.1 强制完整检查：brew update --force

```bash
brew update --force

# 需要观察检查目录与 Git 操作时
brew update --force --verbose
```

这里的 `--force` 表示执行较慢的完整更新检查，即使 Homebrew 认为没有必要。它不会因此升级所有已安装软件，也不是用来放弃本地 Git 修改的重置开关。适合希望重新做完整检查、观察更新过程的情况。准确含义见 [`brew update` 官方参数定义](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/update.rb)。

### 4.2 仓库损坏或分支异常：brew update-reset

`update-reset` 会拉取并把目标仓库重置到最新的 `origin/HEAD`。**它会丢弃受影响仓库中的本地修改和本地提交。** 这里指 Homebrew 自身仓库或 Tap 仓库里的改动，不能把它当成日常升级命令。

处理前先检查并另行备份需要保留的内容：

```bash
# 查看 Homebrew 自身仓库状态
git -C "$(brew --repository)" status --short
git -C "$(brew --repository)" remote -v

# 列出本地已添加的 Tap
brew tap
```

确认只需要恢复 Homebrew 自身仓库时，可指定仓库路径，缩小影响范围：

```bash
brew update-reset "$(brew --repository)"
brew update
```

只有明确希望连同所有本地 Tap 一起恢复，且已处理各仓库本地改动时，才执行不带参数的形式：

```bash
# 破坏性操作：重置 Homebrew 自身及所有本地 Tap 仓库
brew update-reset
brew update
```

它不负责把 Git 远程地址改回官方地址；如果 `origin` 本来指向镜像，重置仍然依据该远程仓库。它也不会修复断网、代理或 TLS 错误。重置范围和风险见 [`update-reset` 官方定义](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/update-reset.rb)。

### 4.3 缓存下载损坏：重新获取指定软件包

```bash
brew fetch --force --retry wget

# Cask 对应形式
brew fetch --cask --force --retry firefox
```

`fetch` 只下载，不安装。`--force` 删除相应的既有缓存并重新下载，`--retry` 在下载失败或缓存校验失败时重试。下载完成后，根据实际目的选择 `brew install wget`、`brew upgrade wget` 或 `brew reinstall wget`。

如果新下载仍然校验失败，应检查上游文件、软件定义和镜像同步状态，不要关闭校验来绕过问题。参数说明见 [`brew fetch` 官方实现](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/fetch.rb)。

### 4.4 已安装文件异常：重新安装

```bash
brew reinstall wget
brew reinstall --cask firefox
```

`reinstall` 先卸载再重新安装指定软件，采用原有安装选项并结合本次指定的适用选项。它不是锁定旧版本的恢复工具；更新定义后重装可能安装当前可用版本，也可能触发相关依赖处理。服务和有状态软件重装前，应先备份数据并阅读 Caveats。见 [`brew reinstall` 官方实现](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/reinstall.rb)。

### 4.5 --force 没有统一含义

| 命令 | 该命令中 `--force` 的主要含义 |
| --- | --- |
| `brew update --force` | 强制进行完整更新检查 |
| `brew fetch --force 软件名` | 移除相应下载缓存并重新获取 |
| `brew upgrade --force 软件名` | Formula 安装时跳过既有 keg-only 或未迁移版本检查；Cask 安装时覆盖已有文件，但二进制文件和符号链接仅在原本来自同一 Cask 时覆盖 |
| `brew link --force 软件名` | 允许链接 keg-only Formula 等特定情形 |
| `brew uninstall --force 软件名` | 对 Formula 删除所有已安装版本；Cask 的处理规则另有定义 |

不能将 `brew upgrade --force` 理解成“任何软件都无条件重装”。遇到“已经是最新版但文件坏了”的问题，应优先看 `reinstall`。每个子命令的选项都应单独查帮助；具体语义分别见 [`upgrade`](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/upgrade.rb)、[`link`](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/link.rb)、[`uninstall`](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/uninstall.rb)。

## 五、空间清理：旧版本、缓存与依赖分别处理

### 5.1 先确认磁盘占用来自哪里

```bash
# 下载缓存目录及其占用
brew --cache
du -sh "$(brew --cache)"

# 已安装 Formula 的目录占用
du -sh "$(brew --cellar)"
```

缓存是下载文件及可再生成的数据；Cellar 是安装内容。直接删除 Cellar 里的目录并不等于规范卸载。macOS 上 Cask 应用通常还涉及 `/Applications` 等位置，仅统计 Cellar 不能代表 Homebrew 管理软件的全部占用。

### 5.2 常规清理：brew cleanup

```bash
# 先预览
brew cleanup --dry-run

# 确认后执行
brew cleanup

# 只针对指定软件
brew cleanup wget
```

`cleanup` 会处理过期锁文件、过时下载和 Formula 的旧安装版本等。当前默认还会按 120 天的缓存年龄阈值清理下载，该阈值可通过 `HOMEBREW_CLEANUP_MAX_AGE_DAYS` 调整。清理旧版本会减少回退时能直接利用的本地内容，不应期待清理后还能随时切回旧版本。见 [`cleanup` 官方定义](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/cleanup.rb)及[环境变量说明](https://docs.brew.sh/Manpage#environment)。

### 5.3 按缓存年龄清理

```bash
# 预览超过 7 天的缓存清理，以及 cleanup 的其他清理项
brew cleanup --prune=7 --dry-run

# 正式清理
brew cleanup --prune=7
```

`--prune=7` 表示采用 7 天的缓存年龄阈值。它仍然是 `cleanup`，还会执行该命令适用的其他清理工作，不能理解为“只删除七天前的下载文件”。

### 5.4 更积极地清理下载缓存：--prune=all

```bash
# 先看将清理什么
brew cleanup --prune=all --dry-run

# 按不保留缓存年龄的方式清理
brew cleanup --prune=all
```

`--prune=all` 让缓存年龄检查不再保留较新的文件，也可能清掉已安装软件对应的下载包；已安装软件本体不因此被卸载。以后重装、重新安装或构建时，可能需要再次下载。

不过，它仍然受 Homebrew 自身缓存管理规则约束，不应据此判断整个缓存目录必定被物理清空。参数和清理路径见 [`cleanup` 命令定义](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/cleanup.rb)与[缓存清理实现](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cleanup.rb)。

### 5.5 cleanup -s 与 --prune=all 有什么区别

```bash
brew cleanup -s --dry-run
brew cleanup -s
```

`-s`，即 `--scrub`，会把最新版本的下载也纳入清理考虑，但这个选项本身仍保留已安装 Formula 和 Cask 对应的下载。不能把单独的 `cleanup -s` 解释成“清空所有缓存”。如果另加 `--prune`，缓存年龄规则还会影响结果，不能沿用这一保留结论。准确说明见 [`cleanup` 官方参数](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/cleanup.rb)。

### 5.6 确实要删除整个 Homebrew 缓存目录时

通常先使用 `cleanup` 即可。如果确实需要把整个缓存目录删除，例如排查持续的缓存异常，可先停止正在运行的 Homebrew 安装、下载与构建任务，然后检查实际路径：

```bash
brew --cache
du -sh "$(brew --cache)"
```

**确认输出是专用于 Homebrew 的缓存目录后**，才执行下列删除命令：

```bash
rm -rf -- "$(brew --cache)"
```

这一步没有预览，也不会进入废纸篓；如果曾自定义 `HOMEBREW_CACHE`，必须先核实它没有指向家目录、共享数据目录等其他位置。它会删除该目录中的下载与元数据等缓存，后续通常会重新生成或获取，离线安装能力也会受到影响。不要顺手删除 `brew --prefix`、Cellar 或 Homebrew 仓库。官方也在 [`cleanup` 帮助中给出了缓存目录删除方式](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/cleanup.rb)。

### 5.7 清理不再需要的依赖：brew autoremove

```bash
# 预览不再需要的依赖
brew autoremove --dry-run

# 确认后卸载
brew autoremove
```

`autoremove` 卸载的是“当初仅作为依赖安装、如今已不再需要的 Formula”，它会删除安装内容，与清理下载缓存不同。Homebrew 不了解你在项目脚本里对某个工具的隐式依赖，预览后仍应判断自己是否还在使用它。命令定义见 [`autoremove` 官方实现](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/autoremove.rb)。

### 5.8 自动清理与保留旧版本

Homebrew 在安装、升级或重装后通常会执行相应清理，并周期性做更大范围的清理。如果一次升级后需要暂时保留旧安装内容用于排查，可对该次命令设置：

```bash
HOMEBREW_NO_INSTALL_CLEANUP=1 brew upgrade wget
```

这只控制相关自动清理，不会阻止之后手动执行 `brew cleanup`，也不会提供完整的版本回滚机制。长期保留旧版本还要考虑依赖兼容与安全更新。自动清理行为及长期配置见[官方 FAQ](https://docs.brew.sh/FAQ#how-do-i-keep-old-versions-of-a-formula-when-upgrading)。

## 六、卸载软件与检查依赖

```bash
# 卸载 Formula
brew uninstall wget

# 卸载 Cask 应用
brew uninstall --cask firefox
```

普通卸载不代表应用偏好设置、用户文件和数据库数据都会被删除。部分残留是为了保留用户数据；需要按软件自身说明处理。

对于 Cask，`--zap` 会进一步清理定义中列出的关联文件：

```bash
# 可能删除用户设置、数据或其他应用共享的文件，先查对应 Cask 定义
brew uninstall --cask --zap firefox
```

`--zap` 的实际范围由 Cask 定义决定，并非保证发现系统内所有残留。`--ignore-dependencies` 则会绕过卸载依赖检查，可能使其他软件失效，不应作为常规卸载参数。两者的边界见 [`uninstall` 官方定义](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/uninstall.rb)。

卸载前，可以先看依赖关系：

```bash
# wget 需要哪些依赖
brew deps wget
brew deps --tree wget

# 哪些已安装软件依赖 openssl@3，包含递归关系
brew uses --installed --recursive openssl@3

# 哪些已安装 Formula 没有被其他已安装 Formula 或 Cask 依赖
brew leaves
```

`leaves` 列出的是依赖关系中的叶子包，里面可能有你每天使用的命令行工具。**叶子包不等于垃圾包**，不要把 `brew leaves` 的输出直接批量传给 `uninstall`。依赖查询的准确范围见 [`deps`](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/deps.rb)、[`uses`](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/uses.rb)和 [`leaves`](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/leaves.rb)。

## 七、版本控制：暂缓升级与指定版本系列

### 7.1 暂时固定已安装软件

```bash
brew pin wget
brew list --pinned

# 解除后再升级
brew unpin wget
brew upgrade wget
```

`pin` 用于阻止 `brew upgrade` 升级指定的已安装包，不会把任意历史版本安装到机器上，也不会冻结整个依赖图。其他软件如果需要更新的依赖，仍可能发生安装冲突；固定期间也会错过该包的安全修复。当前命令还支持 Cask，但不能控制应用自身更新器。见 [`pin` 官方说明](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/pin.rb)。

### 7.2 使用仓库实际提供的版本化 Formula

```bash
brew search '/^python@/'
brew info python@3.13
brew install python@3.13
```

示例中的名称须以当前仓库提供的结果为准。`软件名@版本` 只有在对应 Formula 存在时才成立，不能任意拼出一个历史版本。版本化 Formula 也可能是 keg-only，应按 `brew info` 提示配置。需要大量项目级版本切换时，可以采用对应语言的版本管理工具；Homebrew 主要负责安装受其维护的软件定义。历史版本与版本化 Formula 的维护边界见[官方版本说明](https://docs.brew.sh/Versions)。

### 7.3 临时跳过自动更新检查

```bash
HOMEBREW_NO_AUTO_UPDATE=1 brew install wget
```

该变量跳过命令前的自动元数据更新，既不固定软件版本，也不意味着“安装绝不升级依赖”。遇到旧定义、失效下载地址等问题时，仍应先 `brew update`。长期禁用会延迟获取修复，因此更适合作为有明确目的的临时设置。详见[官方关于版本控制的说明](https://docs.brew.sh/Versions#locking-installed-formulae-at-specific-versions)。

## 八、后台服务：启动、停止与检查

Redis、数据库等 Formula 可能提供服务定义，可以通过 `brew services` 管理：

```bash
brew services list
brew services info redis

# 启动并注册为登录时启动
brew services start redis

# 重启
brew services restart redis

# 停止并取消相应启动注册
brew services stop redis

# 运行但不注册为登录时启动
brew services run redis
```

以上是不加 `sudo` 的用户服务形式。macOS 使用 `launchctl`，Linux 使用 `systemctl`；用户服务通常随登录启动。加 `sudo` 管理的是系统服务，启动时机、配置位置和运行身份随之改变，不应随意混用。不是每个 Formula 都提供可管理的服务。

升级服务端软件后，应检查服务状态、端口和日志，不能仅根据 `brew upgrade` 的退出结果判断业务可用。服务级别的区别见 [`services` 官方定义](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/services.rb)，子命令行为可用 `brew services --help` 核实。

## 九、链接与 PATH：安装成功却找不到命令

先检查当前终端使用哪个可执行文件：

```bash
command -v wget
type -a wget
brew --prefix wget
brew info wget
```

如果 `brew` 本身都找不到，但已确认安装位置，可按安装器的 Next steps 配置环境。以下适用于 zsh 或 bash，两个路径应根据实际安装选择其中一个：

```bash
# Apple Silicon 常见安装路径：在当前终端加载
eval "$(/opt/homebrew/bin/brew shellenv)"
```

```bash
# Intel Mac 既有安装的常见路径：在当前终端加载
eval "$(/usr/local/bin/brew shellenv)"
```

持久生效时，将匹配本机路径的那一行加入实际会读取的 Shell 配置文件；macOS 的 zsh 登录 Shell 常用 `~/.zprofile`。不要同时加入两套 Homebrew 的环境初始化。`shellenv` 的用途和配置位置参见[官方命令定义](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/shellenv.rb)。

对于某个 Formula 的链接异常：

```bash
brew unlink wget
brew link wget
```

`unlink` 移除 Homebrew 前缀中的链接，不卸载软件。如果提示文件冲突，先看将被覆盖的路径：

```bash
brew link --overwrite --dry-run wget

# 仅在确认预览中的冲突文件可以删除时执行
brew link --overwrite wget
```

`--overwrite` 会删除冲突文件；`--force` 则主要用于允许 keg-only Formula 链接等情形，两者作用不同。对于 keg-only 软件，优先按 Caveats 配置 PATH 或编译环境，避免盲目强制链接。见 [`brew link` 官方实现](https://github.com/Homebrew/brew/blob/main/Library/Homebrew/cmd/link.rb)。

## 十、Tap、镜像与更新缓慢

### 10.1 管理第三方 Tap

```bash
# 列出已有 Tap
brew tap

# 以下是占位示例，须替换为真实、可信的仓库
brew tap user/repository
brew install user/repository/formula

# 移除不再需要的 Tap
brew untap user/repository
```

第三方 Tap 中的代码可能以当前用户权限执行，使用前应核对维护者和来源；移除 Tap 也不是卸载其中所有已安装软件的替代操作。Tap 的命名、安装与信任机制见[官方 Tap 文档](https://docs.brew.sh/Taps)。

现代 Homebrew 的普通官方软件安装可以通过 API 获取定义，本地没有完整 `homebrew/core`、`homebrew/cask` Git 仓库并不一定是故障。不要仅因找不到旧教程中的仓库目录，就强行添加 Tap 或全局设置 `HOMEBREW_NO_INSTALL_FROM_API=1`。官方说明见[安装文档中的 API 模式](https://docs.brew.sh/Installation)。

### 10.2 区分不同网络来源

Homebrew 更新与下载涉及不同通道，常见环境变量包括：

| 变量 | 主要影响 |
| --- | --- |
| `HOMEBREW_BREW_GIT_REMOTE` | Homebrew 自身 Git 更新来源 |
| `HOMEBREW_CORE_GIT_REMOTE` | 本地 core Git 仓库使用的远程来源 |
| `HOMEBREW_API_DOMAIN` | Formula、Cask 等 JSON API 元数据来源 |
| `HOMEBREW_BOTTLE_DOMAIN` | Formula 预编译 Bottle 的下载镜像 |

修改 Bottle 镜像并不会自动解决 Homebrew 自身 Git 更新失败，也不能假定所有 Cask 应用下载都经过 Bottle 镜像。来源配置说明见[官方安装文档](https://docs.brew.sh/Installation#git-remote-mirroring)及[环境变量手册](https://docs.brew.sh/Manpage#environment)。

排查时先获取配置和详细输出：

```bash
brew config
brew update --verbose
git -C "$(brew --repository)" remote -v
```

根据报错判断失败发生在 Git、API、Bottle 还是应用上游下载，再检查对应的网络、代理和镜像同步状态。镜像使用方法应以镜像维护者当前文档为准；过期的地址和不同通道混配可能造成版本定义与下载内容不同步。

## 十一、常见故障的处理顺序

### 11.1 更新或安装失败

先按照[官方故障排查流程](https://docs.brew.sh/Troubleshooting)更新并诊断：

```bash
brew update
brew update
brew doctor
brew config
```

连续两次 `update` 是官方当前建议：让第一次更新后取得的新版 Homebrew 再完成一次更新检查。若第一次就出现明确网络错误，应先解决连接问题，而不是机械重复命令。

`brew doctor` 的警告需要结合失败操作判断，不必为了消除所有提示而修改系统。随后重试原命令并保留完整错误输出；下载校验异常看 `fetch`，仓库异常看 `update-reset`，文件损坏看 `reinstall`，链接冲突看 `link`。不要把这些不同问题都用“重置一切”处理。

### 11.2 提示另一个 Homebrew 进程正在运行

先检查是否仍有安装、升级、下载或构建在进行。等待其完成，或在原终端正常中止。不要直接删除所有锁文件后启动第二个写入任务；有锁不一定意味着锁已经失效。确认没有活动进程后，再根据具体报错及[官方常见问题](https://docs.brew.sh/Common-Issues)处理。

### 11.3 权限错误

先看错误指向哪个目录，以及该目录的所有者、权限和安装方式。不要套用网上的整目录 `chmod -R 777`，也不要对整个 `/usr/local` 递归改所有者，其中可能包含其他软件的数据。官方特别提醒不要在不理解影响范围时执行旧教程中的破坏性 Git 或权限修改，见[排查说明](https://docs.brew.sh/Troubleshooting)。

### 11.4 Apple Silicon 上同时存在两套 Homebrew

通过以下命令确认当前架构与命令来源：

```bash
uname -m
type -a brew
brew --prefix
brew config
```

如果一套在 `/opt/homebrew`，另一套在 `/usr/local`，先确认当前 Shell、Rosetta 运行状态和目标软件架构，再分别维护。当前 `brew` 的更新、清理和卸载不会自动替另一套执行同样操作。不要仅按目录名称判断哪套可以删除。

## 十二、用 Brewfile 记录软件清单

换机器、重装系统或整理开发环境时，可以导出清单：

```bash
# 导出到当前目录；已有同名文件时默认不会直接覆盖
brew bundle dump --file=./Brewfile

# 仅在明确要覆盖已有清单时加 --force
brew bundle dump --file=./Brewfile --force
```

在目标环境安装 Homebrew 后恢复：

```bash
brew bundle install --file=./Brewfile

# 检查清单的依赖状态
brew bundle check --file=./Brewfile --verbose

# 不主动升级已过时的已安装依赖
brew bundle install --file=./Brewfile --no-upgrade
```

Brewfile 主要记录软件及相关声明，不是精确版本锁文件，也不是数据库、应用设置和个人文件的备份。默认恢复还可能升级软件；`--no-upgrade` 也不保证底层安装完全不改变依赖。另需注意，`brew bundle cleanup` 清理的是未在清单中声明的软件等内容，不能与 `brew cleanup` 的缓存和旧版本清理混用。详见[官方 Bundle 文档](https://docs.brew.sh/Brew-Bundle-and-Brewfile)。

## 十三、按场景选择的命令速查

| 需求 | 优先使用 |
| --- | --- |
| 查看环境与路径 | `brew config`、`brew --prefix` |
| 搜索和阅读安装提示 | `brew search 软件名`、`brew info 软件名` |
| 安装命令行工具 | `brew install 软件名` |
| 安装 macOS 应用 | `brew install --cask 应用名` |
| 更新 Homebrew 与软件定义 | `brew update` |
| 强制进行完整更新检查 | `brew update --force --verbose` |
| 查看可升级软件 | `brew outdated --verbose` |
| 预览升级 | `brew upgrade --dry-run` |
| 升级指定软件 | `brew upgrade 软件名` |
| 扩大 Cask 更新检查范围 | `brew outdated --cask --greedy --verbose` |
| 指定包重新下载 | `brew fetch --force --retry 软件名` |
| 修复已安装文件 | `brew reinstall 软件名` |
| 预览常规清理 | `brew cleanup --dry-run` |
| 清理旧版本和适用缓存 | `brew cleanup` |
| 更积极地清理缓存 | `brew cleanup --prune=all`，先加 `--dry-run` 预览 |
| 预览无用依赖卸载 | `brew autoremove --dry-run` |
| 卸载无用依赖 | `brew autoremove` |
| 检查健康状态 | `brew doctor` |
| 查看后台服务 | `brew services list` |
| 导出软件清单 | `brew bundle dump --file=./Brewfile` |

平时维护可以按“更新定义 → 查看变化 → 按需升级 → 验证使用情况 → 预览并清理”的顺序操作。只有遇到明确的仓库异常时才考虑重置；只有确认下载缓存损坏时才需要重新下载或清空缓存。这样能让每一次变更都有具体目的，也便于出问题后定位原因。
