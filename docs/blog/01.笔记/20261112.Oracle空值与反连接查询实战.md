## 二、NOT IN 为什么会丢掉所有行

先运行最容易出错的写法：

```sql
SELECT o.row_id, o.customer_id
FROM null_order_lab o
WHERE o.customer_id NOT IN (
    SELECT b.customer_id FROM null_block_lab b
)
ORDER BY o.row_id;
```

结果为零行。对于客户 10，可以把这个单列判断理解为 `10 <> 20 AND 10 <> NULL`。前半部分为 TRUE，后半部分为 UNKNOWN，合起来仍为 UNKNOWN，不能通过 `WHERE`。客户 20 因已有相等项而得到 FALSE；左侧本身为空也不能通过。`NOT UNKNOWN` 仍是 UNKNOWN。[Oracle 19c IN 条件](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/IN-Condition.html)，[逻辑条件与真值表](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Logical-Conditions.html)

| 判断 | 结果 | 通过 WHERE |
| --- | --- | --- |
| `10 = 20` | FALSE | 否 |
| `10 = NULL` | UNKNOWN | 否 |
| `NULL = NULL` | UNKNOWN | 否 |
| `NULL IS NULL` | TRUE | 是 |
| `TRUE AND UNKNOWN` | UNKNOWN | 否 |
| `FALSE AND UNKNOWN` | FALSE | 否 |
| `TRUE OR UNKNOWN` | TRUE | 是 |

“结果被过滤”不等于逻辑值就是 FALSE。用下面的 `CASE` 可以保留第三种状态，而非把所有未命中值都显示成 FALSE。

```sql
SELECT CASE
         WHEN 10 NOT IN (20, NULL) THEN 'TRUE'
         WHEN NOT (10 NOT IN (20, NULL)) THEN 'FALSE'
         ELSE 'UNKNOWN'
       END AS truth_value
FROM dual;
```

预期为 `UNKNOWN`。判断缺失值要用 `IS NULL`，不能写 `= NULL`。Oracle 19c 还把长度为零的字符值当作 NULL，因此字符串子查询也可能触发同类问题；不要依赖应用把空字符串当成一个独立客户编码。[Oracle 19c 空值语义](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Nulls.html)，[空值条件](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Null-Conditions.html)

## 三、按业务规则选择改写

### 1. 忽略名单中的缺失编号，订单编号缺失也排除

显式过滤两侧空值，规则最清晰。预期返回订单 `1、4、5`。

```sql
SELECT o.row_id, o.customer_id
FROM null_order_lab o
WHERE o.customer_id IS NOT NULL
  AND o.customer_id NOT IN (
      SELECT b.customer_id
      FROM null_block_lab b
      WHERE b.customer_id IS NOT NULL
  )
ORDER BY o.row_id;
```

外层 `IS NOT NULL` 看起来多余，但当名单过滤后为空集时，它会影响结果。空集没有需要否定的成员，此时 `NULL NOT IN (空子查询)` 也成立。业务若要求缺失编号始终不参与，不能只过滤右侧。下面的查询预期返回全部五个订单，包括第三行：

```sql
SELECT o.row_id, o.customer_id
FROM null_order_lab o
WHERE o.customer_id NOT IN (
    SELECT b.customer_id FROM null_block_lab b WHERE 1 = 0
)
ORDER BY o.row_id;
```

### 2. 只排除找到相等客户的订单，保留缺失编号

使用相关 `NOT EXISTS`，预期返回 `1、3、4、5`。子查询内 `SELECT 1` 表示仅检查是否存在匹配行，其投影不参与客户比较。[Oracle 19c EXISTS 条件](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/EXISTS-Condition.html)

```sql
SELECT o.row_id, o.customer_id
FROM null_order_lab o
WHERE NOT EXISTS (
    SELECT 1
    FROM null_block_lab b
    WHERE b.customer_id = o.customer_id
)
ORDER BY o.row_id;
```

左侧第三行的 NULL 无法通过子查询中的相等判断，所以没有匹配行，最终被保留。如果要求排除它，就再加 `o.customer_id IS NOT NULL`。将 `NOT IN` 直接改成 `NOT EXISTS` 可能正好修复错误，也可能改变空编号订单的处理规则，代码审查时应列出预期主键集合。

### 3. 业务要求“两个缺失编号也算匹配”

把空值相等作为显式业务规则，预期返回 `1、4、5`。这不是 SQL 普通等号自带的语义。

```sql
SELECT o.row_id, o.customer_id
FROM null_order_lab o
WHERE NOT EXISTS (
    SELECT 1
    FROM null_block_lab b
    WHERE b.customer_id = o.customer_id
       OR (b.customer_id IS NULL AND o.customer_id IS NULL)
)
ORDER BY o.row_id;
```

不要随手用 `NVL(customer_id, -1)` 代替显式规则：当 `-1` 后来成为合法数据时，就会把真实编号与缺失编号混在一起；列上的表达式也可能改变索引访问方式。选择哨兵值需要有约束保证其不可能出现，并验证表达式类型和计划。

## 四、外连接也能写错：检测哪一列没有匹配

下面的写法与第三节第二种规则一致，预期 `1、3、4、5`。

```sql
SELECT o.row_id, o.customer_id
FROM null_order_lab o
LEFT JOIN null_block_lab b ON b.customer_id = o.customer_id
WHERE b.block_id IS NULL
ORDER BY o.row_id;
```

`block_id` 是非空主键：匹配成功就一定非空，只有外连接补出来的行才为空。若误写 `WHERE b.note IS NULL`，订单 2 也会进结果，因为名单中客户 20 的备注本来就为空。匹配条件里的业务过滤应仔细决定放在 `ON` 还是 `WHERE`，后者可能过滤掉外连接补出的行。[Oracle 19c 外连接说明](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Joins.html)

右表存在重复客户编号时，`NOT EXISTS` 不会把一个订单复制成多行；正确的外连接反查也只留下未匹配订单。不要在结果上随意加 `DISTINCT customer_id`，那会把本实验订单 4、5 合成一个客户，改变“按订单返回”的粒度。

## 五、复合键不能套用单列口诀

“NOT IN 的右侧含 NULL 就一定零行”只适用于前述单列表达式，不能机械套到行值比较。下面两条查询都不依赖实验表：

```sql
SELECT 'KEPT' AS result FROM dual
WHERE (1, 2) NOT IN ((2, NULL));

SELECT 'KEPT' AS result FROM dual
WHERE (1, 2) NOT IN ((1, NULL));
```

第一条返回 `KEPT`，因为第一分量已经确定不相等，右侧不可能匹配这组键；第二条零行，因为第一分量相同，而第二分量的比较无法确定。这来自行值比较和三值逻辑的组合，而不是简单扫描 NULL 是否出现。[Oracle 19c 比较条件](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Comparison-Conditions.html)

对于租户编号加客户编号等复合业务键，优先写明相关子查询中的每个关联条件，并分别确定各列的 NULL 规则。若需“任一列缺失都拒绝参与”，就在外层逐列增加非空条件。把两列拼成字符串再比较还会引入分隔符冲突、隐式转换及索引问题。

## 六、进阶实践：用执行计划验证成本

先保证结果主键集合正确，再讨论性能。`NOT EXISTS` 的相关写法不意味着数据库一定逐行执行完整子查询；优化器可将其转换为反连接，并选择不同连接方法。反过来，`NOT IN` 也不总是慢：Oracle 11g 起支持处理可空值的 `ANTI NA`、`ANTI SNA` 优化，必须维持原有空值语义。[Oracle 19c SQL Tuning Guide：反连接](https://docs.oracle.com/en/database/oracle/oracle-database/19/tgsql/joins.html)

在获得必要权限的测试会话中，运行下面两条相邻语句，第一条应完整取完结果。SQL*Plus 保持 `SERVEROUTPUT OFF`，减少客户端额外调用干扰默认“上一游标”的选择：

```sql
SET SERVEROUTPUT OFF
SELECT /*+ gather_plan_statistics */ o.row_id, o.customer_id
FROM null_order_lab o
WHERE NOT EXISTS (
    SELECT 1 FROM null_block_lab b WHERE b.customer_id = o.customer_id
);

SELECT * FROM TABLE(
    DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST +PREDICATE')
);
```

`gather_plan_statistics` 收集这条语句的运行时统计，`ALLSTATS LAST` 展示最后一次执行的统计，`+PREDICATE` 展示访问及过滤条件。检查实际游标、`Starts`、估算行数 `E-Rows`、实际行数 `A-Rows` 及缓冲区读取，而非只看 Cost。如果客户端插入了其他 SQL，应指定目标 `SQL_ID` 和 child number。[Oracle 19c DBMS_XPLAN](https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_XPLAN.html)

`DISPLAY_CURSOR` 需要对 `V$SQL`、`V$SQL_PLAN`、`V$SESSION`、`V$SQL_PLAN_STATISTICS_ALL` 的读取权限及包执行权限，由 DBA 按最小范围提供；不要为此直接给应用账号 `SELECT_CATALOG_ROLE`。本例只有七行样本，无法代表生产性能，计划出现全表扫描也完全合理。

真实数据中，评估右表关联列的索引能否降低探测成本；若大比例数据都要处理，扫描加哈希反连接也可能更合适。租户、状态等额外谓词需一起评估索引列顺序、选择率及统计信息。限制统计采集的范围与时间，避免长期对所有 SQL 强制收集运行统计。不要凭一份小样本计划固定 hint 或承诺某种改写能提高多少倍。

## 七、故障排查与安全清理

| 现象 | 优先核对 |
| --- | --- |
| NOT IN 从正常结果变成零行 | 单独运行右侧查询，统计 NULL；检查 ETL、外连接和表达式是否产生空值。 |
| 改成 NOT EXISTS 后多了一些订单 | 检查左侧 NULL 是否被保留、关联条件是否遗漏租户编号。 |
| 子查询有数据就所有订单都被排除 | 检查是否忘写内外层关联，导致子查询对所有订单返回同一个存在性结果。 |
| 外连接反查混入已匹配订单 | 是否用可空备注列判断未匹配；改用右侧非空主键。 |
| 空名单时缺失客户订单重新出现 | 检查外层是否显式要求非空，加入“右侧空集”回归用例。 |
| 计划查询报 ORA-00942 或无统计 | 核对视图权限、当前游标、是否启用统计并完整获取结果。 |

可先用下面的只读查询检查右侧空值数量，避免在应用中打印整张名单或敏感客户信息。`COUNT(*)` 统计所有行，`COUNT(customer_id)` 只统计该列非空行。[Oracle 19c COUNT](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/COUNT.html)

```sql
SELECT COUNT(*) AS total_rows,
       COUNT(customer_id) AS known_ids,
       COUNT(*) - COUNT(customer_id) AS null_ids
FROM null_block_lab;
```

本例预期 `2 / 1 / 1`。若改写之后要执行 `DELETE`，先用完全相同谓词查询主键、确认数量和抽样；不能把“修复 NULL 陷阱”当作扩大删除范围的授权。所有比较值应通过绑定变量传入，不把用户输入拼进 SQL。

实验结束，确认仍在专用 schema 后执行以下清理。它只针对本文两张测试表，删除表及数据，DDL 隐式提交，不能用 `ROLLBACK` 恢复；若需要这些样本，重新运行第一节。这里不使用 `PURGE`，也不把回收站可用性作为恢复保证。

```sql
ROLLBACK;
DROP TABLE null_block_lab;
DROP TABLE null_order_lab;
```
