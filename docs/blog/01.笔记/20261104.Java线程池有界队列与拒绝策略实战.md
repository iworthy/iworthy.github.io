服务把任务交给线程池后，任务并不会凭空变快：它可能立即执行，也可能排队、被拒绝，甚至在请求已经超时后继续访问数据库。真正需要设计的，是系统愿意同时处理多少工作、愿意等待多久，以及超过边界之后如何让调用方知道。

## 二、任务如何进入线程池

先看本文的实验配置：

| 参数 | 实验值 | 含义 |
| --- | --- | --- |
| `corePoolSize` | `1` | 工作线程少于此值时，优先创建线程接任务 |
| `maximumPoolSize` | `2` | 允许的工作线程数上限 |
| `keepAliveTime` | `30` | 默认作用于超过 core 数量的空闲线程 |
| `unit` | `TimeUnit.SECONDS` | 上一项的时间单位 |
| `workQueue` | 容量为 `1` 的 `ArrayBlockingQueue` | 尚未开始执行的排队位置 |
| `threadFactory` | 自定义命名工厂 | 让日志和线程转储可以定位业务池 |
| `handler` | Abort 或 CallerRuns | 无法接收任务时的处理方式 |

这是观察行为的微型配置，**不是生产参数建议**。这些参数的约束见 [ThreadPoolExecutor 构造器文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html#ThreadPoolExecutor-int-int-long-java.util.concurrent.TimeUnit-java.util.concurrent.BlockingQueue-java.util.concurrent.ThreadFactory-java.util.concurrent.RejectedExecutionHandler-)：core 不能为负，max 必须大于零且不小于 core，存活时间不能为负。

在池正常运行、线程创建成功的前提下，提交路径可以概括为：

```text
提交任务
  |
  +-- 工作线程数 < core ------> 尝试创建工作线程执行
  |
  +-- 否则，尝试放入队列 -----> 入队成功后等待工作线程领取
  |
  +-- 队列放不下且线程数 < max -> 尝试创建额外工作线程执行
  |
  +-- 无法接收 ---------------> 调用拒绝处理器
```

因此，`core=1, max=2, queue=1` 并不意味着“第二个任务就开第二个线程”。当第一个任务仍在运行时，第二个任务先排队，第三个任务才可能触发扩容。

这也解释了另一个现象：[Executors.newFixedThreadPool](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Executors.html#newFixedThreadPool-int-) 使用共享无界队列；任务可能持续积压，而不会因为队列增长自动增加工作线程。把一个自建池的 max 改大，如果它仍使用通常不会放满的无界队列，同样无法解决排队问题。

上图省略了并发状态变化。实际 `execute()` 在入队后还会重新检查关闭状态；若池已关闭且成功移除该任务，就会转入拒绝处理；如果队列里有任务但没有工作线程，还会尝试补充线程。这些边界可对照 [OpenJDK 8u 的 execute 实现](https://github.com/openjdk/jdk8u/blob/master/jdk/src/share/classes/java/util/concurrent/ThreadPoolExecutor.java)。

`ArrayBlockingQueue` 是容量固定的 FIFO 队列，详见[官方类文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ArrayBlockingQueue.html)。队列有阻塞接口，并不意味着 `execute()` 会自动阻塞等待空位：正常提交路径尝试入队失败后，会继续扩容或拒绝。队列 FIFO 也不保证整个池按提交顺序开始执行，因为新创建的线程可能直接执行后提交的任务。

## 三、完整实验：固定住运行状态，观察第四个任务

把下面代码保存为实验目录中的 `BoundedPoolLab.java`。它支持两个参数：`abort` 和 `caller`。

本实验使用两个“任务已启动”信号和一个“允许结束”闸门，先确保第一个工作线程被占用，再占满队列并启动第二个工作线程。闸门由[CountDownLatch](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/CountDownLatch.html) 实现，避免使用 `sleep()` 猜测调度时机。

```java
import java.util.List;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class BoundedPoolLab {
    private static void check(boolean condition, String message) {
        if (!condition) {
            throw new AssertionError(message);
        }
    }

    private static Runnable holdingTask(String id,
                                        CountDownLatch started,
                                        CountDownLatch release) {
        return () -> {
            System.out.println(id + " on " + Thread.currentThread().getName());
            started.countDown();
            try {
                release.await();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        };
    }

    private static void waitStarted(CountDownLatch signal)
            throws InterruptedException {
        check(signal.await(5, TimeUnit.SECONDS), "worker did not start");
    }

    // 针对本例直接提交的 FutureTask，显式结束尚未运行的 Future。
    private static void cancelQueued(List<Runnable> tasks) {
        for (Runnable task : tasks) {
            if (task instanceof Future<?>) {
                ((Future<?>) task).cancel(false);
            }
        }
    }

    public static void closePool(ExecutorService pool) {
        pool.shutdown();
        try {
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
                cancelQueued(pool.shutdownNow());
                if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
                    throw new IllegalStateException("pool did not terminate");
                }
            }
        } catch (InterruptedException e) {
            cancelQueued(pool.shutdownNow());
            Thread.currentThread().interrupt();
            throw new IllegalStateException("closing thread interrupted", e);
        }
    }

    public static void main(String[] args) throws Exception {
        String mode = args.length == 0 ? "abort" : args[0];
        if (!"abort".equals(mode) && !"caller".equals(mode)) {
            throw new IllegalArgumentException("use abort or caller");
        }

        AtomicInteger names = new AtomicInteger();
        AtomicInteger rejections = new AtomicInteger();
        AtomicInteger task4Runs = new AtomicInteger();
        ThreadFactory factory = task -> {
            Thread thread = new Thread(task,
                    "orders-worker-" + names.incrementAndGet());
            thread.setDaemon(false);
            return thread;
        };
        RejectedExecutionHandler policy = "caller".equals(mode)
                ? new ThreadPoolExecutor.CallerRunsPolicy()
                : new ThreadPoolExecutor.AbortPolicy();
        RejectedExecutionHandler observedPolicy = (task, executor) -> {
            rejections.incrementAndGet();
            policy.rejectedExecution(task, executor);
        };
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                1, 2, 30, TimeUnit.SECONDS,
                new ArrayBlockingQueue<Runnable>(1),
                factory, observedPolicy);

        CountDownLatch firstStarted = new CountDownLatch(1);
        CountDownLatch thirdStarted = new CountDownLatch(1);
        CountDownLatch release = new CountDownLatch(1);
        Thread submittingThread = Thread.currentThread();

        try {
            pool.execute(holdingTask("task-1", firstStarted, release));
            waitStarted(firstStarted);
            pool.execute(() -> System.out.println(
                    "task-2 on " + Thread.currentThread().getName()));
            pool.execute(holdingTask("task-3", thirdStarted, release));
            waitStarted(thirdStarted);

            check(pool.getPoolSize() == 2, "expected two workers");
            check(pool.getQueue().size() == 1, "expected one queued task");
            System.out.println("snapshot: workers=2, queued=1");

            try {
                pool.execute(() -> {
                    check(Thread.currentThread() == submittingThread,
                            "task-4 should run on submitting thread");
                    task4Runs.incrementAndGet();
                    System.out.println("task-4 on "
                            + Thread.currentThread().getName());
                });
                check("caller".equals(mode), "abort should reject");
            } catch (RejectedExecutionException e) {
                check("abort".equals(mode), "unexpected rejection");
                System.out.println("task-4 rejected: "
                        + e.getClass().getSimpleName());
            }
            check(rejections.get() == 1, "expected one rejection callback");
            check(task4Runs.get() == ("caller".equals(mode) ? 1 : 0),
                    "unexpected task-4 count");
        } finally {
            release.countDown();
            closePool(pool);
        }

        check(pool.getCompletedTaskCount() == 3,
                "expected three tasks completed by workers");
        System.out.println("terminated=" + pool.isTerminated()
                + ", workerCompleted=" + pool.getCompletedTaskCount()
                + ", rejectionCallbacks=" + rejections.get());
        System.out.println("PASS " + mode);
    }
}
```

释放闸门后，task-2 可能由任一工作线程执行，线程名不是验收条件。验收条件是两个 `PASS`、终止状态为 true、工作线程完成三个任务，以及第四个任务在两种模式下的不同结果。

实验还说明了两点：

- task-3 可以先于 task-2 开始。线程池的 FIFO 队列只约束队列内的取出顺序。
- CallerRuns 中 task-4 虽然完成了，却不是工作线程完成的任务。线程池的完成计数不能直接当成业务成功总数，任务异常结束也不代表业务成功。

## 四、拒绝策略决定调用方看见什么

### 4.1 AbortPolicy：显式告知接收失败

[AbortPolicy](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.AbortPolicy.html) 直接抛出 `RejectedExecutionException`。调用方应在提交处处理它，返回明确的繁忙结果或进入可靠的补偿流程。

拒绝可能由饱和引起，也可能发生在关闭期间。排查时同时记录队列长度、活动线程数和 `isShutdown()`。不要只根据异常类名就认定“线程数太小”。

对于重要任务，应在业务协议中区分“未接收”和“已接收但执行失败”。收到拒绝后立即无限重试，只会把压力重新灌回入口；需要重试时，应设置总期限、次数和退避，并考虑幂等。

### 4.2 CallerRunsPolicy：把压力传回提交线程

[CallerRunsPolicy 官方文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.CallerRunsPolicy.html) 明确指出：池尚未关闭时，由调用线程直接运行任务；池关闭后，任务会被丢弃。

因此，执行 `execute()` 的线程可能直到任务完成才返回。如果它是 HTTP 工作线程，就会延长请求处理时间；如果它是事件循环、持有业务锁的线程或 GUI 事件线程，后果可能更严重。选择该策略前，应明确“提交线程是否允许承担这个任务”。

另一个边界是并发总量：max 限制的是**池内工作线程**。多个提交线程都进入 CallerRuns 时，总业务并发还包括这些调用线程，可能超过 max。因此它不能单独作为数据库连接数或外部 API 并发数的严格上限。

需要绝不静默丢弃的语义时，不要直接使用内置 CallerRuns。可以自定义“未关闭则调用方执行，已关闭则抛出”的策略，但仍须接受调用线程被占用和并发增加的影响。

### 4.3 静默丢弃会与 Future 形成危险组合

`DiscardPolicy` 丢弃新任务，`DiscardOldestPolicy` 丢弃队列头后尝试接收新任务；后者丢弃的是队列头，不是“业务上最不重要的任务”。这两种策略的定义见 [ThreadPoolExecutor 拒绝任务说明](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)。

根据 [AbstractExecutorService 的 submit 实现](https://github.com/openjdk/jdk8u/blob/master/jdk/src/share/classes/java/util/concurrent/AbstractExecutorService.java)，本例的 `submit()` 会先包装出 `FutureTask`，再交给 `execute()`。由此可以推导：若拒绝处理器正常返回但既不运行、也不取消包装任务，调用方仍可能拿到一个永远不完成的 Future。关闭后的 CallerRuns 也有这一风险。

这里的解决目标不是“让异常不出现”，而是保证每个已接收任务都有明确终态。关键任务通常更适合显式拒绝；如果确实允许丢弃，必须有业务损失指标，并为相关 Future 明确定义取消或失败行为。

## 五、完整实验：submit 的异常、等待超时与取消

在同一目录保存 `FutureFailureLab.java`。它依赖前一个文件中的关闭工具，验证三件互不等价的事情：任务失败、调用方等待超时、任务被取消。

```java
import java.util.concurrent.*;

public class FutureFailureLab {
    private static void check(boolean condition, String message) {
        if (!condition) {
            throw new AssertionError(message);
        }
    }

    public static void main(String[] args) throws Exception {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                1, 1, 0, TimeUnit.SECONDS,
                new ArrayBlockingQueue<Runnable>(1),
                new ThreadPoolExecutor.AbortPolicy());
        CountDownLatch started = new CountDownLatch(1);
        CountDownLatch release = new CountDownLatch(1);
        CountDownLatch stopped = new CountDownLatch(1);
        Future<String> waiting = null;

        try {
            Future<Integer> failed = pool.submit(() -> {
                throw new IllegalStateException("simulated failure");
            });
            try {
                failed.get(5, TimeUnit.SECONDS);
                throw new AssertionError("expected failure");
            } catch (ExecutionException e) {
                check(e.getCause() instanceof IllegalStateException,
                        "unexpected cause");
                System.out.println("cause="
                        + e.getCause().getClass().getSimpleName());
            }

            waiting = pool.submit(() -> {
                started.countDown();
                try {
                    release.await();
                    return "released";
                } finally {
                    stopped.countDown();
                }
            });
            check(started.await(5, TimeUnit.SECONDS), "task did not start");
            try {
                waiting.get(50, TimeUnit.MILLISECONDS);
                throw new AssertionError("expected timeout");
            } catch (TimeoutException e) {
                check(!waiting.isDone(), "timeout should not finish task");
                System.out.println("timeout leaves task pending=true");
            }

            check(waiting.cancel(true), "cancel should succeed");
            try {
                waiting.get(5, TimeUnit.SECONDS);
                throw new AssertionError("expected cancellation");
            } catch (CancellationException e) {
                System.out.println("cancelled=" + waiting.isCancelled());
            }
            check(stopped.await(5, TimeUnit.SECONDS),
                    "task body did not exit");
        } finally {
            if (waiting != null && !waiting.isDone()) {
                waiting.cancel(true);
            }
            release.countDown();
            BoundedPoolLab.closePool(pool);
        }

        System.out.println("PASS future");
    }
}
```

### 5.1 为什么 submit 的错误不一定打印出来

`execute()` 直接执行一个抛出未处理运行时异常的 Runnable 时，异常可以到达工作线程的未捕获异常处理流程。`submit()` 默认使用的 [FutureTask](https://github.com/openjdk/jdk8u/blob/master/jdk/src/share/classes/java/util/concurrent/FutureTask.java) 则把任务异常保存为计算结果，供 `get()` 读取。只设置线程的 `UncaughtExceptionHandler`，不能覆盖后一种情况。

异步接口需要安排结果的拥有者：由谁读取 Future、记录失败、更新业务状态，以及触发补偿。不能把返回的 Future 丢在一边，就认为任务已被可靠处理。实现统一观测时，也可以扩展执行器钩子，但必须考虑 `submit()` 的异常包装，以及日志代码自身的异常与性能开销。

### 5.2 等待超时不是执行超时

[Future.get(timeout, unit)](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Future.html#get-long-java.util.concurrent.TimeUnit-) 限制的是这次等待，不会自动停止任务。例子中的 50 毫秒只是制造一个可观察的等待超时，不是下游服务的建议超时。

`cancel(true)` 请求中断正在执行任务的线程，并使 Future 进入取消状态；这不证明所有副作用都已停止。示例额外使用 `stopped` 确认任务代码退出，因为 Future 的取消状态可能早于实际退出。本例的 `await()` 可响应中断，其他代码是否退出取决于它的实现。

生产环境应把请求总期限、排队预算、连接超时和读取超时一起设计。数据库或 HTTP 客户端是否支持取消，需要按所用驱动验证；已经提交到外部系统的写操作，也不会因为 Java Future 被取消而自动回滚。

## 六、关闭线程池：拒绝新任务、处理旧任务、确认结束

前面 `closePool()` 的顺序是：先 `shutdown()`，有界等待，再必要时 `shutdownNow()`，最后再次等待。其行为依据 [ExecutorService 官方文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ExecutorService.html)：

| 方法或状态 | 表达的事实 | 不应据此推断 |
| --- | --- | --- |
| `shutdown()` | 开始有序关闭；旧任务继续处理 | 所有任务已结束 |
| `shutdownNow()` | 尝试中断运行任务，并返回未开始的排队任务 | 中断一定有效、外部操作已回滚 |
| `awaitTermination()` 返回 true | 关闭后执行器已经终止 | 所有业务任务都成功 |
| `isShutdown()` | 关闭已开始 | 没有线程正在工作 |

一个容易遗漏的细节是 `shutdownNow()` 返回值。对于本文直接提交的 `FutureTask`，从队列取出并返回，不等于它的 Future 自动变成已取消。示例对返回列表中实现了 Future 的任务调用 `cancel(false)`，避免结果拥有者继续等待一个根本不会启动的任务。

这段工具的适用范围是本文直接提交给 `ThreadPoolExecutor` 的任务；若业务通过装饰器或其他执行框架包装 Runnable，应检查包装对象与原始 Future 的关系。返回列表还应进入审计、补偿或重投流程，不能只取消 Future 就认定业务完成。

示例中的两个 5 秒等待仅用于实验兜底。实际关闭预算应与流量摘除、容器终止宽限期和下游超时配套。应先停止业务入口继续生产任务，再关闭它使用的线程池；对关闭线程收到中断的情况，示例保留中断标志并报告失败，不把它当作正常收尾。

若第二次等待仍失败，继续排查任务阻塞位置和资源释放情况。`shutdownNow()` 不具备强制杀死任意 Java 代码的能力，不要用 `Thread.stop()` 代替正确的取消协议。

## 七、如何为生产环境选择边界

### 7.1 线程、队列和下游资源要一起计算

线程数控制同时运行的工作量，队列控制等待任务的数量。容量为 1 的实验只说明控制逻辑，不能套用到线上。规划时至少收集：任务到达率、单任务执行时间分布、排队时间、任务持有的内存和下游并发限制。

例如，**假设**每秒接收 200 个任务，平均执行时间为 0.05 秒，在稳定状态下平均在执行工作量约为 `200 × 0.05 = 10`。这是用于初步估算的假设算例，不是实测吞吐，也不意味着配置 10 个线程就能满足尾延迟和突发流量。

如果任务都访问一个受限数据库，扩大线程池可能只会让更多线程等待连接。CPU 密集任务也可能因线程过多增加切换开销。应围绕已测得的瓶颈调整，随后验证尾延迟、拒绝量和下游资源使用，而不是只追求线程利用率。

队列越长，短时拒绝可能越少，但请求等待和内存占用可能越大。一个仅供容量讨论的近似关系是：`队列中任务数 ÷ 可持续完成速率 ≈ 排队时间`。它假设负载相对稳定，不能预测突发情况下每个任务的等待，也不能替代直接采样排队时长。

### 7.2 同一个池中等待同一个池的任务

不要让池里的所有工作线程都阻塞等待提交给同一个池的子任务：如果子任务还在队列里，而所有工作线程都被父任务占用，就没有线程可以执行它们。有界队列和拒绝异常可能暴露这个问题，却不能自动修复任务依赖设计。

处理方式应根据依赖关系选择，例如移除同步嵌套等待、拆分资源隔离，或采用明确的异步编排。简单增大 max 可能只是把故障延后到更大的负载。

### 7.3 观测数据必须覆盖业务结果

建议按业务池名记录以下指标，而不是只看线程总数：

- 当前活动线程数、池大小、队列长度和剩余容量。
- 进入拒绝处理器的次数，并区分饱和与关闭。
- 业务成功、失败、取消、丢弃和重试次数。
- 从提交到开始执行的等待时长，以及实际执行时长。

线程池活动数、任务总数等统计在并发运行时通常是近似或瞬时观察值；不能写出“先看队列没满，再保证提交成功”的业务逻辑。即使某一瞬间看到空位，另一个提交线程也可能先占用它。

自定义线程名不要包含口令、令牌或客户信息。任务对象也应避免捕获整个请求体、大集合或长生命周期资源；排队会延长这些对象的存活时间。线程复用时，业务创建的 ThreadLocal 上下文应在 `finally` 中清理，防止请求之间污染。

## 八、常见错误与排查路径

| 现象 | 优先检查 | 处理方向 |
| --- | --- | --- |
| 队列不断增长，线程数不增加 | 队列是否无界、是否真正达到容量 | 明确队列边界，并核对扩容顺序 |
| 队列未满却收到拒绝 | `isShutdown()`、线程工厂和资源异常 | 区分生命周期拒绝与容量拒绝 |
| 引入 CallerRuns 后接口变慢 | 提交线程名、该任务执行时间 | 确认提交线程能否承担任务 |
| 任务失败却没有预期日志 | 是否使用 submit、是否读取 Future | 明确异步结果处理责任 |
| `get()` 一直不返回 | 静默拒绝、未运行 Future、嵌套等待 | 使用有界等待，并修复终态或依赖问题 |
| 进程迟迟不退出 | 池是否关闭、非守护线程、阻塞栈 | 先确认任务状态，再定位阻塞资源 |

需要查看真实 JVM 的线程栈时，可在 **Linux/macOS 上以目标 JVM 的同一用户**执行以下 JDK 诊断命令；若 JVM 关闭了 attach 或运行在隔离容器中，需要在相应环境内操作，不要直接假定是命令故障：

```bash
jps -l
# 将 12345 替换为上一步确认的目标 JVM PID
jstack -l 12345 > pool-thread-dump.txt
```

这两条命令是故障现场的操作示例，不针对已退出的实验进程；本文未在真实故障 JVM 上执行。命令说明见 [JDK 8 jps](https://docs.oracle.com/javase/8/docs/technotes/tools/unix/jps.html) 与 [JDK 8 jstack](https://docs.oracle.com/javase/8/docs/technotes/tools/unix/jstack.html)。线程转储可能短暂影响目标进程，并包含内部类名与锁信息，应妥善保存。重定向会覆盖当前目录中同名文件，已有采样应使用不同文件名。

关注 `orders-worker-*` 的栈是否集中等待数据库连接、锁或网络读取。同一类线程处于 WAITING 不一定是故障：空闲工作线程等待队列任务很正常；判断必须结合队列积压、任务时长和业务进度。

## 十、实践要点

为线程池设定边界，需要同时回答：允许多少任务运行、允许多少任务排队、满载后如何反馈，以及任务如何走到成功、失败或取消终态。工作线程数的上限并不等同于业务的总并发上限，Future 的完成也不等同于外部副作用已经结束。

落地时先选择明确的容量与拒绝语义，再建立业务结果和排队时长观测；异步失败有人处理，关闭过程能够报告未终止和未执行任务，之后才有依据进行调优。
