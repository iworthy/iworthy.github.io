这次遇到一个 MacBook Air 的异常：没有主动设置合盖保持唤醒，也没有连接充电线，但合上屏幕后再打开，仍然直接进入桌面。最后执行 `sudo pmset -a disablesleep 0` 后，合盖行为恢复正常。

这条命令值得记录，但排查时还需要分清：**屏幕关闭、系统睡眠和需要身份验证，是三个不同的状态。** 看到桌面不能直接证明电脑没有睡眠，找到一条防睡眠断言，也不能直接认定某个应用就是原因。

本文从这一现象出发，整理锁屏设置、外接显示器、电源配置、后台断言和睡眠日志的完整检查流程。设置路径以使用“系统设置”的 macOS 版本为主；旧版系统的名称和位置可能不同。Apple 芯片与 Intel 机型的后续处理会分别说明。

## 一、先判断是哪一种异常

日常说的“合盖不锁屏”，可能对应几种不同情况：

| 现象 | 优先检查 |
| --- | --- |
| 合盖后屏幕关闭，打开时直接回到桌面 | 需要密码的等待时间，以及是否已通过自动解锁 |
| 合盖后持续运行，伴随明显耗电或发热 | 系统级睡眠开关、防睡眠工具和睡眠日志 |
| 只有连接显示器或扩展坞时合盖仍能工作 | 是否处于正常的外接显示器使用场景 |
| 手动锁屏也无法进入锁定界面 | 先排查登录会话或系统异常 |

锁屏控制的是是否需要重新验证身份；息屏控制的是显示器状态；睡眠则是整机的电源状态。电脑可以锁屏后继续运行，也可能睡眠后在允许的时间内免输密码。

因此，第一步可以按 `Control + Command + Q`，或者从苹果菜单选择“锁定屏幕”。如果手动锁屏正常，而合盖后打开却不要求验证，就继续检查下面的设置和电源状态。

测试时注意不要顺手使用 Touch ID 解锁，也要留意 Apple Watch 自动解锁等情况，避免把“已经快速解锁”误认为“没有锁屏”。

## 二、检查锁定屏幕设置

打开：

**系统设置 → 锁定屏幕 → 启动屏幕保护程序或显示器关闭后需要输入密码**

如果希望离开后立即要求验证，将等待时间设为“立即”。不同 macOS 版本的文字可能略有不同，核心是检查“需要密码”的时间，而不只是屏幕多久关闭。

Apple 在[从睡眠中唤醒 Mac 后要求输入密码](https://support.apple.com/en-ie/guide/mac-help/mchlp2270/27/mac/27)中说明了这一设置。它决定身份验证的等待时间，不能单独用来证明系统是否进入睡眠。

调整后合盖等待片刻，再打开检查。若验证行为符合预期，但仍存在持续耗电或发热，应继续检查睡眠状态。不要为了排查睡眠而将密码等待时间改为“永不”，这会改变设备离开视线后的访问保护。

## 三、先排除正常的外接显示器模式

MacBook 合盖后继续向外接显示器输出画面，可能是正常的合盖使用模式。Apple 在[外接显示器排查说明](https://support.apple.com/zh-cn/102501)中要求，合盖使用时应连接电源，并使用外接键盘和鼠标。

这里的“连接电源”包括显示器或扩展坞通过 USB-C 向 Mac 供电，不只是连接独立充电器。可以用以下只读命令确认当前电源来源：

```bash
pmset -g batt
```

关注输出中的 `Battery Power` 或 `AC Power`。如果显示外接供电，即使没有连接独立充电器，也不能按纯电池场景分析。

做对比时，先推出外置磁盘，断开显示器、扩展坞及非必要 USB 或雷雳设备，再测试。如果异常只在某个组合下出现，逐个接回设备，检查供电、线缆、扩展坞及配套软件。

仅连接鼠标、耳机或硬盘，不足以证明系统进入了外接显示器模式；外设活动或设备故障也可能是另一类唤醒、阻止睡眠问题。锁屏仍然单独控制身份验证，不能因为正在外接办公就认为离开时无需手动锁屏。

## 四、查看系统是否禁用了睡眠

### 1. 先保存当前状态

打开“终端”，执行以下只读命令：

```bash
# 当前电源设置，包含系统级设置
pmset -g

# 分别查看电池和外接电源的配置
pmset -g custom
```

在 `pmset -g` 输出中寻找类似内容，下面只是格式示例：

```text
System-wide power settings:
 SleepDisabled        1
```

`SleepDisabled` 为 `1` 表示系统级禁止睡眠开关已开启；为 `0` 表示该开关关闭。如果没有看到这个字段，不要直接按 `1` 处理，也不要把 `sleep 0` 与它混为一谈：后者通常表示不因闲置计时自动睡眠。

可以先复制保存输出，便于后续比较。这里的检查比直接修改一批电源参数更容易定位问题。

### 2. 解除系统级睡眠禁用

如果确认睡眠被禁用，并且没有保留该配置的需要，可以执行：

```bash
sudo pmset -a disablesleep 0
```

命令会要求管理员权限。终端输入密码时不会显示字符，输入完成后按回车即可。

`disablesleep 0` 的作用是**解除系统级睡眠禁用**。Apple 的 [pmset 开源实现](https://github.com/apple-oss-distributions/PowerManagement/blob/main/pmset/pmset.m)将它作为系统级布尔开关处理；它不属于分别保存的电池与充电闲置计时配置。`-a` 通常选择所有电源配置，但这里不能将它理解为只修改电池和充电两套定时器。

这个参数可在 Apple 开源实现中核对，但不是所有版本的用户手册都会列出，不能据此承诺所有 macOS 版本与机型的行为完全相同。目标系统是否支持、执行是否成功，应以该机实际输出及后续验证为准；开源代码也不能代替故障现场证据。

执行后再次检查：

```bash
pmset -g
```

确认 `SleepDisabled` 是否变为 `0`，然后重新测试合盖行为。如果命令报错，先记录错误信息并查阅本机 `man pmset`，不要继续尝试不明参数。

这次异常在执行该命令后恢复，说明系统级睡眠禁用是一个值得优先检查的方向。但仅凭恢复结果，无法确认修改前的开关值，也无法确定是谁改动了它。

### 3. 这条命令的作用范围

解除睡眠禁用，不等于立即进入睡眠，也不等于将全部电源选项恢复出厂值。闲置睡眠时间、显示器关闭时间和锁屏验证时间仍然需要分别检查。

如果修改后再次复发，应在异常发生时保存状态，检查防睡眠工具、登录项或管理脚本。反复运行同一条命令，只能恢复当时的开关，不能解释它为什么又被改动。

## 五、检查后台应用与电源断言

### 1. 从活动监视器入手

不熟悉终端时，可以打开“活动监视器”的“能耗”页面，查看“防止睡眠”列；没有显示时，在可用列中检查该字段。它适合找出需要进一步检查的应用，见 Apple 的[查看能耗说明](https://support.apple.com/en-kw/guide/activity-monitor/actmntr43697/10.14/mac/27)。

这一列显示“是”，不代表应用异常，更不能单独证明它阻止了合盖睡眠。先确认是否正在播放、下载、备份或执行长时间任务，再决定是否正常退出并复测。

### 2. 查看断言类型和持有进程

如果系统级开关没有异常，或者问题仍然存在，可以执行：

```bash
pmset -g assertions
```

按照 [pmset 官方手册源码](https://github.com/apple-oss-distributions/PowerManagement/blob/main/pmset/pmset.1)，该命令用于查看电源断言摘要及相关进程。阅读时关注断言类型、持有进程、持续时间和对应任务。

| 常见字段 | 含义与判断边界 |
| --- | --- |
| `PreventUserIdleSystemSleep` | 阻止因用户闲置触发的系统睡眠，不能据此判定合盖睡眠被阻止 |
| `PreventUserIdleDisplaySleep` | 阻止因用户闲置触发的显示器睡眠 |
| `PreventSystemSleep` | 与阻止系统睡眠有关，需结合具体断言和运行条件分析 |
| `Listed by owning process` | 列出持有断言的进程，帮助定位当时的任务 |

Apple 在 [IOPMLib.h 的断言说明](https://github.com/apple-oss-distributions/IOKitUser/blob/main/pwr_mgt.subproj/IOPMLib.h)中明确指出：`PreventUserIdleSystemSleep` 生效时，系统仍可能因合盖、苹果菜单命令、低电量等原因睡眠。

所以，看到某个应用持有值为 `1` 的断言，只能说明它当时提出了对应请求。播放音频、传输文件等正常任务也可能持有断言，不能直接把这些进程当成故障程序。

更有用的验证方法是：保存工作，正常退出可疑应用，再以相同条件测试合盖；重新打开应用后复测。如果行为可重复地随应用变化，再检查其设置或向开发者反馈。不要随意结束系统进程。

`pmset -g assertions` 只是执行时的快照。电脑已经重新开盖、应用已经完成任务时，之前持有的断言可能已经释放；此时没有相关记录，也不能排除它曾经参与过问题。

### 3. caffeinate 不能笼统理解为合盖不睡眠

系统自带的 `caffeinate` 通过断言保持特定状态，不同参数的目标不同：

| 参数 | 主要作用 | 需要注意 |
| --- | --- | --- |
| `-i` | 阻止用户闲置导致的系统睡眠 | 不等于阻止合盖睡眠 |
| `-d` | 阻止显示器因闲置关闭 | 与锁屏验证策略不同 |
| `-s` | 请求阻止系统睡眠 | 按手册，仅在外接电源供电时有效 |
| `-t 秒数` | 限定断言持续时间 | 与被包装命令共同使用时，手册说明该超时值不生效 |

这些区别可查 [caffeinate 官方手册源码](https://github.com/apple-oss-distributions/PowerManagement/blob/main/caffeinate/caffeinate.8)。因此，不能把 `caffeinate` 或某个第三方应用“正在运行”，直接等同于系统级 `SleepDisabled` 已被设为 `1`。两者应分别取证。

## 六、用日志区分没有睡眠与睡后被唤醒

验证时先推出外置磁盘，再断开显示器、扩展坞和其他非必要外设，使用电池供电进行对比。没有插独立充电器，也要注意 USB-C 显示器或扩展坞可能仍在供电。

建议按以下顺序检查：

1. **手动锁屏**：确认能进入锁定界面，并需要有效身份验证才能返回桌面。
2. **合盖后重新打开**：等待片刻再开盖，检查验证行为是否符合锁定屏幕设置。
3. **核对睡眠日志**：记录测试时间，用日志判断是否有对应的睡眠与唤醒事件。

查看近期日志可以使用：

```bash
pmset -g log | tail -n 120
```

按刚才的测试时间查找 Sleep、Wake 等记录。某些版本或机型可能显示合盖相关原因，但日志格式和原因文字并不完全相同；如果测试事件不在最后 120 行，可扩大查看范围。

一次后台唤醒记录不等于电脑整个合盖期间都没有睡眠。应观察事件顺序、发生时间和是否重新睡眠，而不是只搜索到一个 Wake 就下结论。

| 测试时段的记录 | 可以支持的判断 | 仍需确认 |
| --- | --- | --- |
| 有对应的 Sleep，开盖后有 Wake | 至少发生过一次睡眠与唤醒 | 是否同时满足锁屏验证要求 |
| Sleep 后很快出现 Wake，随后又 Sleep | 发生过唤醒，之后重新睡眠 | 是否频繁发生、是否伴随异常耗电 |
| 有 DarkWake | 记录了后台唤醒活动 | 不应仅凭这一词认定屏幕被点亮或桌面已解锁 |
| 没找到对应的 Sleep | 当前查看范围内没有对应记录 | 日志范围、记录完整性及其他证据 |

日志中的原因字段通常表示当次事件的触发来源，未必能直接定位到某个第三方应用。把同一时间的电源来源、外设状态和断言记录放在一起分析，才有机会判断原因。

如果确认已经睡眠，但很快被唤醒，可再查看“电池 → 选项”中的“唤醒以供网络访问”，以及“通用 → 共享”中的相关服务；也可逐一排查外设。只在不需要对应功能时临时调整，并记录原值以便恢复。Apple 的[意外睡眠或唤醒排查指南](https://support.apple.com/zh-cn/guide/mac-help/mchlp2995/27/mac)提供了这些检查方向。

合盖验证应在通风桌面上完成。电池百分比在短时间内不变不能证明已经睡眠，单次掉电也不足以证明故障；先核对事件和状态，再观察相同条件下是否持续异常。

## 七、复发时先取证再修改

如果修复后再次出现，先记录发生时间、供电方式、连接设备和正在运行的任务，再保存状态。下面的命令适用于 macOS 自带的 zsh 或 Bash，使用普通用户权限；只读取系统状态，并将结果写入一个新建的临时目录，不修改电源设置：

```bash
# 在同一个终端会话执行，先采集，后决定是否修复
(
  umask 077
  pm_diag_dir=$(mktemp -d /tmp/mac-sleep-diag.XXXXXX) || exit 1

  {
    date '+%Y-%m-%d %H:%M:%S %z'
    sw_vers
    sysctl -n hw.model
  } > "$pm_diag_dir/system.txt"

  pmset -g > "$pm_diag_dir/settings.txt"
  pmset -g custom > "$pm_diag_dir/profiles.txt"
  pmset -g batt > "$pm_diag_dir/power-source.txt"
  pmset -g assertions > "$pm_diag_dir/assertions.txt"
  pmset -g sched > "$pm_diag_dir/schedule.txt"
  pmset -g log | tail -n 300 > "$pm_diag_dir/sleep-wake.txt"

  printf '记录目录：%s\n' "$pm_diag_dir"
)
```

最后 300 行只是便于初步查看的范围，并非完整故障历史；需要更早记录时应扩大范围。检查终端是否报错，并查看生成文件是否包含有效内容。临时目录适合短期排查，需要长期保留时将其复制到自己的文档目录。

这些文件可能包含进程名、路径、设备或网络信息，对外提供前先检查并去除个人信息。它们用于记录状态，不是一个能够自动识别根因的诊断程序。

若怀疑某个任务会短暂持有断言，可以另外运行：

```bash
pmset -g assertionslog
```

观察断言的创建与释放，完成后按 `Control + C` 停止。它不提供启动之前的完整历史，也不负责审计是谁写入了 `SleepDisabled`；不能用断言日志替代配置修改来源的调查。

如果每次启动某个防睡眠工具、登录项或维护脚本后开关都会变化，可以在启动前后分别保存 `pmset -g` 输出。每次只改变一个条件，并重复验证；不要因为曾安装过某个应用就直接认定它是原因。

## 八、软件排查无效后的处理顺序

### 1. 重启和更新

保存工作后正常重启，重新测试相同场景。若问题持续，再备份重要数据，检查适用的 macOS 和相关应用更新。重启后暂时正常，只能说明状态发生了变化，不足以证明根因已经消除。

### 2. 用安全模式缩小范围

安全模式可用于判断问题是否与启动时加载的软件有关。两类机型的进入方式不同：

| 机型 | 进入方式 |
| --- | --- |
| Apple 芯片 Mac | 关机后长按电源键进入启动选项，选中启动宗卷，按住 Shift 并点按“在安全模式中继续” |
| Intel Mac | 启动或重启时立即按住 Shift，直到出现登录窗口 |

完整操作以 Apple 的[安全模式指南](https://support.apple.com/zh-cn/guide/mac-help/mh21245/27/mac/27)为准。正常重启可退出安全模式。若只有安全模式下正常，优先检查登录项、后台软件和相关扩展；这仍不是某个具体应用有问题的直接证明。

### 3. 不同机型采用不同的电源排查方法

不要把 Intel 机型的 SMC 重置组合键照搬到 Apple 芯片 Mac。Apple 的[睡眠与唤醒故障指南](https://support.apple.com/en-ie/guide/mac-help/mchlp2995/27/mac/27)对 Apple 芯片机型建议先重启；Intel 机型如需重置 SMC，应按具体机型的官方步骤进行。

### 4. 必要时进行硬件检测

断开非必要外设、重启并排除常见软件因素后，若合盖检测仍持续异常，可使用 [Apple Diagnostics](https://support.apple.com/en-ie/102550)，记录参考代码并联系 Apple 支持。

屏幕接近闭合时仍亮着，不能单独证明合盖传感器损坏；一次诊断没有报错，也不能排除所有间歇性问题。送检时提供可复现步骤、时间、机型、系统版本和已做过的对比，比只描述“不锁屏”更有帮助。

## 九、几个容易误用的处理方法

| 常见做法或判断 | 问题所在 | 更合适的处理 |
| --- | --- | --- |
| 将 `sleep 0` 当成恢复睡眠 | 它关闭的是对应配置的闲置睡眠计时 | 先区分定时器和系统级禁用开关 |
| 修改 `lidwake` 解决合盖不睡眠 | 该项控制开盖唤醒，不是合盖睡眠开关 | 先核对本机 `man pmset` 的含义 |
| 看到断言为 `1` 就强杀进程 | 断言可能对应正常任务 | 正常退出应用并做前后对比 |
| 一次性重置所有电源设置 | 会扩大修改范围，也不利于比较 | 先记录原值，再修改与问题相关的项目 |
| 强制结束 `loginwindow` 来锁屏 | 可能中断登录会话和未保存工作 | 使用系统提供的锁屏、注销或正常重启 |
| 看到耗电就调整 `hibernatemode` | 不同平台的支持情况和睡眠机制不同 | 沿事件日志定位，避免套用其他机型参数 |

其中 `sleep`、`lidwake` 和休眠相关参数的定义，可在本机 `man pmset` 及 [Apple 的 pmset 手册源码](https://github.com/apple-oss-distributions/PowerManagement/blob/main/pmset/pmset.1)中核对。解除系统级睡眠禁用，也不需要顺带删除电源配置文件。

## 十、这次修复能说明什么

对于“合盖后打开直接回到桌面”，先检查身份验证等待时间；对于“合盖后持续运行”，再检查 `SleepDisabled`、电源断言和睡眠日志。把现象对应到具体状态，后续操作才有明确目标。

这次有效的修复命令是：

```bash
sudo pmset -a disablesleep 0
```

它适用于解除系统级睡眠禁用，不能代替所有合盖问题的诊断。本次恢复结果能说明这项操作有效，但不足以追溯原始配置、修改者或全部触发条件；本文的扩展排查步骤不代表这些问题都曾在这台设备上出现。

修复完成应分别满足两个目标：离开设备后需要身份验证，合盖时的电源行为符合当前使用场景。以后若再次出现异常，先保存状态，再针对证据处理，才能从“这次恢复了”进一步走向“知道为什么会发生”。
