每分钟执行一次报表任务，某次数据库查询却耗时三分钟，下一轮应该跳过、等待，还是同时运行？如果运维人员看到一个几天前创建的 `job.lock`，能否直接删除它来“解除死锁”？这两个问题都需要回到同一件事：**实际持有锁的是哪一组打开的文件描述符，以及受保护的工作何时结束。**

本文只讨论 Linux 上使用 util-linux `flock` 控制同一任务重入的实践。以一个不访问外部系统的报表模拟脚本为起点，说明如何接入 cron、区分锁争用与业务失败，并用七项实验复现描述符继承和锁文件删除陷阱。

## 一、应用场景、目标与适用边界

适合定时生成报表、扫描待处理文件、同步单机缓存、执行维护脚本等任务。读者需要了解 Bash 的退出码、重定向、前台与后台进程，不需要编写内核代码。

完成后应能回答：

- 任务已在运行时，为什么要明确选择跳过或限时等待？
- 为什么“文件存在”不等于“锁被占用”，进程退出也不一定马上释放锁？
- 如何保留业务错误码，同时为正常争用建立独立的可观测状态？
- 为什么删除锁文件、对脚本自身加锁、部署时替换锁目录都可能破坏互斥？
- 如何用实验确认锁行为，而不是只看一条“任务开始”日志？

本文的基础模型限定为：**同一 Linux 内核、同一文件对象、所有入口使用相同的 flock 协议、任务在锁覆盖范围内完成**。不同机器上的两个本地同名路径没有共同锁；容器若各有独立文件系统，路径相同也不会自动互斥。

示例使用 util-linux 2.32.1 已支持的 `-n`、`-w`、`-E`、`-F` 和 `--close`，不依赖较新版的 `--fcntl`。旧 BusyBox 实现的选项不保证相同，先执行：

```bash
# Linux，普通用户，只读检查
uname -srmo
bash --version
flock --version
command -v bash flock stat lslocks
```

可对照 [util-linux v2.32.1 的 flock 官方手册源码](https://raw.githubusercontent.com/util-linux/util-linux/v2.32.1/sys-utils/flock.1)核实实际版本的参数。不要仅依据网上最新手册判断旧服务器支持哪些功能。

## 二、先建立正确的锁模型

### 2.1 路径、文件对象与打开描述并非同一层

可以把一次加锁过程画成：

```text
job.lock 路径
    -> 文件系统中的文件对象（设备号 + inode）
        <- open() 建立的打开文件描述
            <- Bash 文件描述符 9
            <- fork 后子进程继承的描述符 9
```

按照 [Linux flock(2) 官方手册](https://man7.org/linux/man-pages/man2/flock.2.html)，锁关联打开文件描述；复制或继承的描述符可以引用同一把锁。显式解锁，或者引用该打开描述的所有描述符都关闭后，锁才释放。

由此得到三个排查结论：

1. 空文件也能持锁，锁状态无需写进文件内容。
2. 一个留在磁盘上的旧锁文件可以完全没有锁，不能用修改时间判断任务是否存活。
3. 父脚本退出后，如果后台子进程仍继承持锁描述符，锁可能继续存在。

不要把 PID 文件、哨兵文件和内核文件锁混为一谈。“创建文件成功即拥有执行权”的方案需要另一套原子性与崩溃恢复设计。

### 2.2 必须让检查和占有成为同一次原子竞争

下面这种设计存在时间窗口：

```text
进程 A：检查文件不存在
进程 B：检查文件不存在
进程 A：创建文件并开始工作
进程 B：创建文件并开始工作
```

正确做法是让所有入口先请求同一文件上的排他锁，只允许获得锁的入口进入临界区。临界区应包含读取状态、计算和提交结果的整个业务过程。把锁仅放在日志输出周围，保护不了后续的数据修改。

本地普通文件上的 flock 是协作式锁：绕过加锁的程序仍可写文件。因此手工补跑、cron、维护脚本和应用内调度都必须走约定入口。锁也不赋予文件读写权限，目录访问仍受 Unix 权限控制。

### 2.3 跳过、等待与业务补偿要分别决定

| 策略 | 命令形式 | 适用情况 | 需要接受的代价 |
| --- | --- | --- | --- |
| 立即跳过 | `flock -n -E 75 ...` | 下一轮会重新扫描全部待处理项 | 本次触发不执行 |
| 限时等待 | `flock -w 10 -E 75 ...` | 短暂重叠可以排队 | 占用等待进程，可能最终超时 |
| 无限等待 | `flock ...` | 明确需要串行且外部控制积压 | 调度持续触发时可能堆积 |

这些等待参数约束的是**取得锁之前的等待**，不会限制业务运行时间。运行上限应另行设计，并验证终止时的子进程、事务与临时文件处理；简单在外层加一个超时命令并不能证明全部业务已停止。

若要求每个事件都处理一次，应该把事件放入可恢复的任务队列或数据库记录，再由消费者领取。flock 只决定某一时刻谁能进入，无法保存被跳过的触发，也无法让已经提交的外部副作用自动回滚。

## 三、构建一个可直接运行的任务入口

### 3.1 创建私有实验目录

以下命令适用于 Linux Bash，使用普通用户，不需要 sudo。它只创建独立临时目录，不修改 crontab、系统配置或业务数据。请在同一个终端继续执行后续步骤。

```bash
umask 077
job_demo=$(mktemp -d /tmp/worthy-report-demo.XXXXXX)
mkdir -m 700 "$job_demo/state"
printf '实验目录：%s\n' "$job_demo"
```

将下面完整脚本保存为该目录的 `report-job`，例如使用 `cat > "$job_demo/report-job" <<'SCRIPT'`，粘贴代码后在新行输入 `SCRIPT`。

```bash
#!/bin/bash
set -euo pipefail
umask 077
export PATH=/usr/bin:/bin

work_dir=${1:?usage: report-job ABSOLUTE_STATE_DIRECTORY}
if [[ "$work_dir" != /* || ! -d "$work_dir" ]]; then
  printf 'ERROR: state directory must exist and be absolute\n' >&2
  exit 64
fi

# This directory is private to the service account. Never unlink job.lock.
exec 9>>"$work_dir/job.lock"
if flock -n -E 75 9; then
  :
else
  rc=$?
  if [[ "$rc" == 75 ]]; then
    printf 'SKIP: another report-job is running\n'
  else
    printf 'ERROR: lock failed, rc=%s\n' "$rc" >&2
  fi
  exit "$rc"
fi

# All protected work stays in the foreground. No explicit unlock is needed.
printf 'START pid=%s time=%s\n' "$$" "$(date -u +%FT%TZ)" >> "$work_dir/job.log"
sleep 2
printf 'DONE pid=%s time=%s\n' "$$" "$(date -u +%FT%TZ)" >> "$work_dir/job.log"
```

先检查语法，再启动：

```bash
bash -n "$job_demo/report-job"
bash "$job_demo/report-job" "$job_demo/state"
cat "$job_demo/state/job.log"
```

预期有一条 START 和一条 DONE，PID 一致、时间相差约两秒。时间不是性能数据，`sleep 2` 只是让并发窗口容易观察。真实报表逻辑应替换这段前台模拟工作，并自行检查业务命令的失败条件。

### 3.2 为什么先打开描述符，再请求锁

`exec 9>>"$work_dir/job.lock"` 在当前 Bash 中打开文件，并让描述符 9 持续存在；这里的 exec 没有启动另一个程序。追加模式可在文件不存在时创建它，也避免每次打开都截断文件内容。

随后 `flock -n -E 75 9` 针对已打开的描述符申请排他锁。flock 命令本身结束后，Bash 仍保留描述符 9，所以后面的前台工作仍处于锁内。

默认排他与共享、`-n` 的非阻塞行为及 `-w` 的限时等待，可查 [Debian 随 util-linux 发布的 flock 手册](https://manpages.debian.org/bookworm/util-linux/flock.1.en.html)。本文选择排他锁，因为两个任务即使读取同一批数据，也可能同时写出重复结果。

不要把这个专用锁文件同时当成业务输出文件，也不要在程序结束时删除它。文件可以长期保留，锁状态由内核管理。

### 3.3 在两个终端观察重入

终端 A 启动任务：

```bash
bash "$job_demo/report-job" "$job_demo/state"
```

在其两秒运行窗口内，终端 B 用相同的绝对路径执行：

```bash
# 把路径换成第一步打印的实际目录；另一个终端没有原来的变量
job_demo=/tmp/worthy-report-demo.替换为实际后缀
rc=0
bash "$job_demo/report-job" "$job_demo/state" || rc=$?
printf 'exit=%s\n' "$rc"
```

B 预期输出 `SKIP: another report-job is running`，退出码为 75，且不增加自己的 START/DONE。A 结束后再执行一次，应正常完成。

这里保留 75 用于锁争用。脚本在取得锁之前判断该退出码，因此不会把业务失败误判为正常跳过。若直接使用“flock 包裹命令”的写法，业务命令也可能返回 75，应保留一个不会与业务码混淆的约定，或结合明确的阶段日志判断。

另外，`if ! flock ...; then rc=$?` 中的 `$?` 是取反后的状态，不是原始失败码。本例通过普通 `if/else` 保存原始值；不能为了让 cron 看起来全绿而把所有错误都改成退出 0。

## 四、用七项实验验证容易误判的行为

下面脚本适用于 Linux Bash 与 GNU stat，普通用户即可运行。它为每次运行创建私有临时目录，所有删除操作只针对该目录。保存为 `verify-flock.sh` 后运行 `bash verify-flock.sh`。

实验用 ready/release 文件协调进程：先确认持锁者已经进入，再测试争用，避免仅靠“睡一会儿应该开始了”的假设。等待标记有上限；如果机器异常繁忙而失败，应结合错误信息排查，不能直接当作内核语义变化。

```bash
#!/bin/bash
set -euo pipefail
umask 077
lab=$(mktemp -d /tmp/worthy-flock-check.XXXXXX)
pids=()
cleanup() {
  if ((${#pids[@]})); then
    kill "${pids[@]}" 2>/dev/null || true
  fi
  wait 2>/dev/null || true
  rm -rf -- "$lab"
}
trap cleanup EXIT
await_file() {
  local i
  for ((i=0; i<200; i++)); do
    [[ -e "$1" ]] && return 0
    sleep 0.05
  done
  printf 'FAIL: marker missing: %s\n' "$1" >&2
  return 1
}
expect_rc() {
  local expected=$1 actual=0
  shift
  "$@" || actual=$?
  if [[ "$actual" != "$expected" ]]; then
    printf 'FAIL: expected rc=%s, got %s\n' "$expected" "$actual" >&2
    return 1
  fi
}
start_holder() {
  bash -c '
    exec 9>>"$1"
    flock -x 9 || exit
    : > "$2.ready"
    for ((i=0; i<200; i++)); do
      [[ -e "$2.release" ]] && exit 0
      sleep 0.05
    done
    exit 70
  ' _ "$1" "$2" &
  holder_pid=$!
  pids+=("$holder_pid")
  await_file "$2.ready"
}

lock="$lab/job.lock"
start_holder "$lock" "$lab/holder"
expect_rc 75 flock -n -E 75 "$lock" touch "$lab/unexpected"
[[ ! -e "$lab/unexpected" ]]
printf 'PASS 1: nonblocking conflict never ran command\n'

expect_rc 75 flock -w 0.1 -E 75 "$lock" true
printf 'PASS 2: bounded wait returned conflict status\n'

flock -w 5 -E 75 "$lock" touch "$lab/acquired" &
waiter_pid=$!
pids+=("$waiter_pid")
: > "$lab/holder.release"
wait "$holder_pid"
wait "$waiter_pid"
[[ -e "$lab/acquired" ]]
printf 'PASS 3: waiting command acquired after release\n'

expect_rc 23 flock -n -E 75 "$lock" bash -c 'exit 23'
flock -n -E 75 "$lock" true
printf 'PASS 4: command status preserved and lock released\n'

cat > "$lab/child.sh" <<'CHILD'
#!/bin/bash
: > "$1.ready"
for ((i=0; i<200; i++)); do
  if [[ -e "$1.release" ]]; then
    : > "$1.done"
    exit 0
  fi
  sleep 0.05
done
exit 70
CHILD

bash -c '
  exec 9>>"$1"
  flock -x 9 || exit
  bash "$2" "$3" &
' _ "$lock" "$lab/child.sh" "$lab/inherited" &
launcher_pid=$!
pids+=("$launcher_pid")
wait "$launcher_pid"
await_file "$lab/inherited.ready"
expect_rc 75 flock -n -E 75 "$lock" true
: > "$lab/inherited.release"
flock -w 5 -E 75 "$lock" true
await_file "$lab/inherited.done"
printf 'PASS 5: background child kept inherited descriptor\n'

bash -c '
  exec 9>>"$1"
  flock -x 9 || exit
  bash "$2" "$3" 9>&- &
' _ "$lock" "$lab/child.sh" "$lab/closed" &
launcher_pid=$!
pids+=("$launcher_pid")
wait "$launcher_pid"
await_file "$lab/closed.ready"
[[ ! -e "$lab/closed.done" ]]
flock -n -E 75 "$lock" true
: > "$lab/closed.release"
await_file "$lab/closed.done"
printf 'PASS 6: unrelated child closed descriptor\n'

start_holder "$lock" "$lab/deleted"
old_inode=$(stat -c '%d:%i' "$lock")
rm -- "$lock"
flock -n -E 75 "$lock" true
new_inode=$(stat -c '%d:%i' "$lock")
[[ "$old_inode" != "$new_inode" ]]
[[ ! -e "$lab/deleted.release" ]]
: > "$lab/deleted.release"
wait "$holder_pid"
printf 'PASS 7: unlink created independent lock identity\n'
printf 'ALL 7 CASES PASSED\n'
```

本次实际输出为：

```text
PASS 1: nonblocking conflict never ran command
PASS 2: bounded wait returned conflict status
PASS 3: waiting command acquired after release
PASS 4: command status preserved and lock released
PASS 5: background child kept inherited descriptor
PASS 6: unrelated child closed descriptor
PASS 7: unlink created independent lock identity
ALL 7 CASES PASSED
```

这些断言验证了退出码、标记文件和锁身份，不是吞吐量或公平性测试。实验 7 中的删除是故意制造错误，只能在隔离实验目录执行。

### 4.1 等锁超时与业务返回失败的区别

实验 1、2 在另一个持锁者存活期间，分别使用非阻塞和 0.1 秒等待，返回 75。未创建 unexpected 文件，证明被包裹的业务命令没有运行。

实验 3 在持锁者释放后，等待中的命令成功执行。这里不对多个等待者的先后顺序作保证；若业务依赖严格 FIFO，应选择有明确排序语义的队列。

实验 4 的业务主动返回 23，外层也得到 23，随后重新加锁成功。这验证了正常退出路径能释放锁，却不表示失败之前的业务写入已经回滚：文件锁从来没有提供数据库事务或业务幂等性。

### 4.2 后台进程可能让锁活得更久，也可能让锁过早结束

实验 5 故意让子进程继承描述符 9。启动它的 Bash 已经退出，但子进程仍在等待 release，因此竞争者拿不到锁。

实验 6 用 `9>&-` 关闭与锁无关子进程的描述符，启动者退出后，其他任务就能取得锁。这个技巧只适用于**确实不属于受保护业务的后台辅助进程**。

如果后台运行的是报表本身，正确方向通常是保持前台执行，或在父脚本里显式 `wait`，检查它的返回值后才结束保护范围。先关闭锁再让真正的工作继续运行，会重新引入重叠。

命令包装形式也可使用 `flock --close lockfile command`，让外层 flock 保留锁、执行的 command 不继承锁描述符；其保护持续到受等待的 command 退出。若 command 又把真正的工作丢到后台并提前退出，保护仍会提前结束。相对地，`-F` 会让 flock 被 command 替换，所以不能和 `--close` 同时使用。这些进程模式见 [util-linux 官方 flock 手册源码](https://raw.githubusercontent.com/util-linux/util-linux/v2.39.3/sys-utils/flock.1.adoc)。

还要注意：若显式对共享的打开描述执行 `flock -u`，即使子进程保留描述符，也会释放这把锁。本例采用自然关闭，不插入提前解锁。

### 4.3 删除锁文件为什么可能出现两个“成功持锁者”

实验 7 的过程是：

```text
A 打开 job.lock -> 文件对象 X -> 持锁并运行
管理员删除 job.lock 的目录项
B 再打开 job.lock -> 新文件对象 Y -> 加锁成功
A 与 B 保护的已经不是同一个文件对象
```

[Linux unlink(2) 官方手册](https://man7.org/linux/man-pages/man2/unlink.2.html)说明，删除路径后，只要进程仍打开文件，该对象就能继续存在。本实验用设备号和 inode 的组合确认新旧对象不同，旧持锁者直到最后才收到 release。

因此不要用退出 trap 删除锁文件，不要把锁文件纳入日志轮转、临时文件清理或发布目录整体替换。对脚本文件自身加锁也需谨慎：部署工具用 rename 替换脚本后，新旧任务可能锁住不同对象。把锁单独放在稳定的状态目录更容易维护。

若线上已经误删锁文件，重新 touch 同名文件无法把旧持锁者迁移过去。恢复步骤是：暂停所有调度与手工入口，核对旧新两组任务，等待它们完成或通过既有停机方式停止全部相关进程，确认没有残留工作后，再统一使用稳定路径恢复调度。期间应核查重复写入，必要时依业务补偿；不要只恢复一个文件就认定互斥已恢复。

## 五、接入 cron：固定路径、用户与失败语义

以下是配置示例，不会由本文实验自动安装。假设专用账号为 `report`，其家目录为 `/home/report`。目录与脚本由该账号管理，普通用户执行：

```bash
# 以 report 身份执行；不要在共享可写目录部署高权限脚本
install -d -m 700 /home/report/bin
install -d -m 700 /home/report/.local/state/report-job
install -m 700 ./report-job /home/report/bin/report-job

# 用绝对路径完成一次手动验证
/home/report/bin/report-job /home/report/.local/state/report-job
```

正式任务读取的文件、数据库账号和凭据应按最小权限配置。本文模拟脚本只写本目录日志，不需要 root；不要为了省去目录授权而直接改为 root 定时任务。

先用 `crontab -l` 检查已有配置。有现有条目时，将其备份到私有文件：

```bash
crontab -l > /home/report/.local/state/report-job/crontab.before
crontab -e
```

若 `crontab -l` 提示没有 crontab，确认是首次配置后再编辑，不把空的重定向输出误认成有效备份。用编辑器增加以下三行，保留已有条目：

```text
SHELL=/bin/bash
PATH=/usr/bin:/bin
* * * * * /home/report/bin/report-job /home/report/.local/state/report-job >> /home/report/.local/state/report-job/scheduler.log 2>&1
```

这是**用户 crontab**，五个时间字段后直接接命令；`/etc/crontab` 和常见 `/etc/cron.d/` 文件的格式还含用户名，不能原样互抄。每分钟只是演示频率，生产应根据业务时效和任务耗时确定。

[Debian cron 官方包中的 crontab(5) 手册](https://manpages.debian.org/bookworm/cron/crontab.5.en.html)说明了默认 shell、用户身份和百分号的特殊处理。本例把含 `date +%...` 的逻辑放在脚本里，避免直接写入 cron 命令行时被解释为换行。cron 也不应依赖交互终端中的 alias、工作目录或 shell 初始化文件。

启用后的检查顺序：

1. 用 `crontab -l` 核对实际保存的条目，确认发行版对应的 cron 服务正在运行。
2. 观察 scheduler.log，区分 SKIP 和 ERROR；观察 job.log，核对一次 START 是否对应一次 DONE。
3. 人为让测试业务耗时超过调度间隔，确认同一时刻只有一个受保护任务进入。
4. 观察跳过次数、最近一次成功时间和业务积压，验证频率与跳过策略符合要求。

cron 本身不等于退出码监控系统。仅凭非零退出码不保证有人收到通知，重定向全部输出后尤其如此，应接入现有日志或监控采集。

回退时先通过 `crontab -e` 删除本次添加的那条任务，并保留其他条目；核对所有在途任务完成后，再考虑归档脚本与状态目录。只有确认备份完整且之后没有其他编辑时，才可用 `crontab /home/report/.local/state/report-job/crontab.before` 整体恢复，否则会覆盖后续配置。停用 cron 条目也不会自动停止已经启动的任务。

## 六、线上排查：先看对象和进程，再决定处置

以下都是 Linux 只读命令。查看自己账号通常无需 sudo；其他账号的 /proc、命令行或路径信息可能受权限、hidepid 和容器命名空间限制，需要按运维授权执行。

```bash
# 明确列，不依赖不同版本的默认展示
lslocks -o COMMAND,PID,TYPE,MODE,PATH

# 路径当前指向哪个文件对象
stat -c 'device=%d inode=%i links=%h path=%n' \
  /home/report/.local/state/report-job/job.lock

# 当前 PID 命名空间可见的内核锁记录
cat /proc/locks

# 将 12345 替换为经过核对的持锁任务 PID；本例固定描述符为 9
ps -p 12345 -o pid,ppid,etime,args
readlink /proc/12345/fd/9
stat -L -c 'device=%d inode=%i links=%h' /proc/12345/fd/9
```

可结合 [lslocks 官方手册](https://man7.org/linux/man-pages/man8/lslocks.8.html)和 [/proc/locks 官方手册](https://man7.org/linux/man-pages/man5/proc_locks.5.html)核对字段。/proc/locks 自 Linux 4.9 起会受到对应 PID 命名空间过滤；容器内看不到另一组锁记录，不能据此判定宿主没有锁。

尤其不要把 lslocks 的一个 PID 当成全部持有者清单：打开描述可以由多个进程共享。排查时还需沿父子关系和 /proc/PID/fd 检查描述符继承；命令包装模式持锁描述符也未必恰好是 9。

| 现象 | 优先检查 | 处理方向 |
| --- | --- | --- |
| 长期 SKIP，却看不到业务进展 | 是否有后台子进程继承描述符、业务是否卡住 | 定位完整进程树与依赖，再按既有流程停机 |
| 锁文件存在，但任务仍能启动 | 是否根本没有活跃锁 | 用实际竞争和内核记录确认，不依据文件年龄 |
| 两个任务都打印 START | 路径、设备号/inode、容器挂载、是否绕过入口 | 恢复同一锁身份与统一入口 |
| 不是 75，而是权限错误 | 父目录存在性、属主权限、只读挂载 | 修复访问条件，不把基础设施错误算作跳过 |
| 等待者越来越多 | 是否用了无限等待、耗时是否长期超出间隔 | 改为明确的跳过/限时等待，或任务队列 |
| 父进程退出但锁还在 | 存活子进程与共享打开描述 | 不直接删文件，也不盲目 kill 任意 PID |

对卡住进程发送信号会影响业务，可能留下半成品或中断外部操作。本篇不提供一键强杀命令；应先确认事务、子进程与恢复流程，再采用应用既有的优雅停止方式。锁释放只能说明互斥条件变化，不能说明数据已经一致。

## 七、性能、安全与跨平台注意事项

### 7.1 等待上限不能解决处理能力不足

假设每分钟触发，而每次都要三分钟，互斥可以抑制并发，却不能让系统每分钟处理完一轮。选择跳过意味着降低实际执行频率；选择等待则可能持续增加等待进程。

应监控任务耗时分布、等待时间、跳过率、连续失败数、最近成功时间和待处理条目数。先优化扫描批量、索引、增量状态和外部调用，再决定是否需要拆分任务。只有业务资源互相独立时，才按资源建立不同锁；为每次触发随机生成锁名会完全失去防重入作用。

涉及多把锁时统一获取顺序并设置合理上限，避免 A 等 B、B 等 A。不要依赖 flock 替应用检测死锁。

### 7.2 稳定目录与权限是协议的一部分

高权限任务不要在所有人可写目录中使用可预测锁路径，以免遇到预置符号链接或目录项替换。本文实验使用 mktemp 私有目录，部署示例使用服务账号私有状态目录。

发布代码时保留状态目录和锁文件对象；清理脚本只清理明确的输出、缓存和历史日志。状态目录若被删除重建，即使配置中的字符串路径完全一样，互斥关系仍可能断裂。

所有竞争方还应使用相同锁机制。本文不使用新版本的 `--fcntl`；该选项建立另一类 OFD 锁，在本地 Linux 上不能想当然地与 flock(2) 锁互斥，见 [util-linux v2.41.1 官方说明](https://kernel.googlesource.com/pub/scm/utils/util-linux/util-linux/+/refs/tags/v2.41.1/sys-utils/flock.1.adoc)。

### 7.3 网络文件系统与多机任务需要单独设计

NFS、SMB/CIFS 的 flock 实现受到内核、服务器和挂载选项影响，可能通过其他协议锁模拟；不能把本文 tmpfs 实验结果直接推广过去。尤其不能把“共享目录里有同名文件”直接等同于可靠的跨机协调。

生产确需跨机互斥时，应明确故障模型：网络分区、节点重启、持有者失联、锁服务不可用时，业务允许怎样继续；根据数据权威来源选择数据库约束、可恢复领取协议或有明确租约语义的协调机制。本文没有实现或验证分布式锁。

### 7.4 Linux 与 macOS 的区别

| 项目 | 本文 Linux 环境 | macOS 原生环境 |
| --- | --- | --- |
| 命令行 flock | util-linux 工具 | 本机未提供同名原生工具，不能直接照搬 |
| stat 标识对象 | `stat -c '%d:%i' 文件` | BSD stat 使用 `stat -f '%d:%i' 文件` |
| 锁与描述符观察 | /proc/locks、/proc/PID/fd、lslocks | 没有相同的 Linux /proc 接口 |
| 调度示例 | Linux cron 用户条目 | 持续管理任务通常需结合 launchd 单独设计 |
| 本文实测范围 | AlmaLinux 容器内 tmpfs | 只作为容器宿主，不算原生 macOS flock 验证 |

macOS 提供底层文件锁接口，不代表第三方同名命令与 util-linux 参数和行为完全兼容。复现本文应进入 Linux 虚拟机或容器；Docker Desktop/OrbStack 的宿主绑定挂载也不自动等同于 Linux 本地文件系统，因此本次刻意把锁放在容器内 tmpfs。

| 检查项 | 本次实际结果 | 限制 |
| --- | --- | --- |
| 完整 report-job | 实际运行；重入返回 75，持有者完成后可再次执行，日志有两组 START/DONE | 业务仅为 sleep 与写日志 |

| 网络文件系统、分布式故障、性能 | 未执行 | 不提供吞吐量、延迟或跨机安全结论 |

实验结束后，确认任务和测试进程全部完成，再清理第三节的目录：

```bash
# Linux Bash；仅删除本次 mktemp 目录，内容无法从该命令直接恢复
case "${job_demo:-}" in
  /tmp/worthy-report-demo.?*) rm -rf -- "$job_demo" ;;
  *) printf '拒绝清理：请核对实验目录\n' >&2 ;;
esac
```

生产实践可以归纳为：使用私有且稳定的专用锁路径；所有入口遵守同一协议；将全部受保护工作留在持锁范围内；明确跳过和等待的业务含义；分别记录争用、基础设施错误与业务失败；用业务幂等和恢复机制处理执行中断。

flock 解决的是一次进入权的竞争。把锁对象、进程生命周期和业务完成条件对齐，才能让这个简单工具成为可靠的定时任务入口。
