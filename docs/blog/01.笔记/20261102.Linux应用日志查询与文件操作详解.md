Linux 排障中，最常见的工作往往是：找到应用真正写入的日志，在大量记录里定位故障时间和请求链路，保留完整异常上下文，再检查配置、权限和磁盘状态。熟悉几个命令只是起点；理解输入格式、匹配规则、文件描述符和操作边界，才能避免“查到了内容，却得出了错误结论”。

本文围绕**应用日志查询**与**文件、目录操作**两条主线展开，既适合作为系统学习材料，也可以在实际排障时按章节查阅。除基本用法外，还会解释日志轮转、多行堆栈、时间筛选、结构化日志、特殊文件名、批量清理和备份恢复中的常见陷阱。

## 一、适用环境与示例约定

正文以 **Bash、GNU coreutils、GNU grep、GNU findutils、GNU sed 和常见 awk 实现**为基础，面向 Ubuntu、Debian、RHEL 系列等常见 GNU/Linux 环境。`journalctl` 需要 systemd；`jq`、`rg`、`rsync`、`lsof`、Docker 和 `kubectl` 按场景使用，可能需要另行安装。

macOS 默认使用多种 BSD 工具；Alpine、路由器与精简容器常使用 BusyBox。本文中的 `find -printf`、`xargs -r`、`du --max-depth`、`stat -c` 等选项不能直接视为所有 Unix 系统通用。遇到参数不支持时，先查看本机 `man`、`--help` 和版本信息。

示例统一使用以下占位名称，执行前应替换为真实路径与服务名：

| 项目 | 示例 | 含义 |
| --- | --- | --- |
| 应用目录 | `/opt/myapp` | 应用程序与配置目录 |
| 当前日志 | `/var/log/myapp/app.log` | 应用正在写入的文本日志 |
| 历史日志 | `/var/log/myapp/archive/` | 已轮转、归档的日志 |
| systemd 单元 | `myapp.service` | 应用服务名称 |
| 请求标识 | `traceId=abc123` | 贯穿请求处理过程的关联标识 |
| 故障窗口 | `2026-11-02 10:00:00` 至 `10:10:00` | 演示用时间，不代表实际事件 |

正文里的命令是**按场景选择的示例**，不是应从头到尾执行的脚本。复制、覆盖、修改权限、删除和截断文件会改变系统状态；相应章节会说明具体影响。

### 1.1 先区分三类问题

| 要解决的问题 | 应优先使用的工具 | 示例 |
| --- | --- | --- |
| 文件在哪里 | `find`、应用配置、服务配置 | 按名称寻找 `app.log` |
| 文件里有什么 | `less`、`grep`、`sed`、`awk`、`jq` | 按请求标识检索日志 |
| 文件本身是什么状态 | `ls`、`stat`、`file`、`du`、`df` | 检查大小、权限、磁盘占用 |

`find` 主要按目录项和文件属性筛选；`grep` 主要按内容筛选。把这两层组合起来，比直接递归搜索整台服务器更容易控制范围。

### 1.2 引号、通配符和 `--`

```bash
# 双引号保留路径中的空格，同时允许变量展开
log_file='/var/log/myapp/app.log'
tail -n 100 -- "$log_file"

# 单引号让 *.log 交给 find 解释，避免被当前 Shell 提前展开
find /var/log/myapp -type f -name '*.log' -print

# -- 结束选项解析；./ 也可以避免文件名被误当作选项
ls -l -- ./-debug.log
grep -nF -- '-timeout' ./app.log
```

`*.log` 是 Shell 通配模式；`ERROR|WARN` 是扩展正则表达式中的“或”。二者属于不同语法。文件名、搜索文本来自变量时，通常都应加引号。

## 二、先确认应用日志究竟写在哪里

### 2.1 常见日志来源

| 场景 | 常见位置或入口 | 注意事项 |
| --- | --- | --- |
| 应用自行写文件 | 应用的 `logs/`、`/var/log/myapp/` | 路径和名称以日志配置为准 |
| systemd 启动的服务 | `journalctl -u 服务名` | 标准输出是否进 journal 取决于单元配置 |
| Web 服务 | `/var/log/nginx/`、Apache 日志目录 | access 与 error 日志承担不同职责 |
| 传统系统日志 | `/var/log/syslog`、`/var/log/messages` | 发行版及日志服务配置不同，文件不一定存在 |
| Docker 容器 | `docker logs` | 依赖日志驱动及应用的输出方式 |
| Kubernetes 容器 | `kubectl logs` | 需要选对命名空间、Pod 和容器 |
| `nohup` 启动 | 显式重定向的目标，或 `nohup.out` | 不要假定文件一定在应用安装目录 |

先确认启动方式和日志配置，避免只因为某个文件叫 `app.log` 就认定它是当前实例的日志。

```bash
# 查看服务启动参数、工作目录、运行账户及输出去向
systemctl cat myapp.service
systemctl show myapp.service \
  -p ExecStart -p WorkingDirectory -p User \
  -p StandardOutput -p StandardError

# 查看当前服务状态和最近的少量日志
systemctl status myapp.service --no-pager -l

# 已知应用 PID 时，查看其打开的文件
sudo lsof -p 12345

# 定向查找日志文件，不从 / 开始无差别扫描
find /opt/myapp /var/log/myapp -type f \
  \( -name '*.log' -o -name '*.out' \) -print
```

服务可能在 `ExecStart` 中调用包装脚本；脚本可能再次切换目录或重定向输出。`lsof` 只能看到进程当时打开的文件，不能替代完整配置检查。

### 2.2 判断是否找对实例、时间和文件

```bash
date '+%Y-%m-%d %H:%M:%S %z %Z'
timedatectl status
ls -lh -- /var/log/myapp/app.log
stat -- /var/log/myapp/app.log
head -n 5 -- /var/log/myapp/app.log
tail -n 20 -- /var/log/myapp/app.log
```

重点核对：日志中的主机、实例、版本、时区是否正确，末尾时间是否持续更新，文件是否刚刚轮转。文件修改时间只能说明文件被修改过，**不能代替日志记录自身的业务时间**。

## 三、查看日志：`cat`、`head`、`tail` 与 `less`

### 3.1 小文件用 `cat`，首尾片段用 `head`、`tail`

```bash
# 小型配置或少量日志
cat -- /opt/myapp/config/app.properties

# 查看前 30 行、后 200 行
head -n 30 -- /var/log/myapp/app.log
tail -n 200 -- /var/log/myapp/app.log

# 从第 1000 行开始输出到文件末尾
tail -n +1000 -- /var/log/myapp/app.log
```

`tail -n 1000` 是末尾 1000 行，`tail -n +1000` 是从第 1000 行开始，含义完全不同。对数 GB 的文件直接 `cat` 会产生大量终端输出，也很难保留排查位置。

### 3.2 大日志用 `less` 交互阅读

```bash
less -N -S -- /var/log/myapp/app.log

# 打开后先跳到末尾
less +G -- /var/log/myapp/app.log

# 打开后定位第 1200 行
less +1200 -- /var/log/myapp/app.log
```

| 按键 | 功能 |
| --- | --- |
| `Space` / `b` | 下一屏 / 上一屏 |
| `g` / `G` | 文件开头 / 文件末尾 |
| `1200g` | 跳到第 1200 行 |
| `/timeout` | 向后搜索 `timeout`，回车执行 |
| `?timeout` | 向前搜索 |
| `n` / `N` | 沿当前搜索方向继续 / 反向继续 |
| 左右方向键 | 在长行中横向移动 |
| `F` | 持续等待新增内容；通常用 `Ctrl+C` 返回交互模式 |
| `q` | 退出 |

`-N` 显示行号，`-S` 将长行截在屏幕宽度，剩余内容可横向查看。`less` 无需在显示第一页前读完整个普通文件；但跳到末尾、计算行号或执行远距离搜索仍可能需要大量读取。参考 [less 手册](https://man7.org/linux/man-pages/man1/less.1.html)。

## 四、实时查看与日志轮转：理解 `tail -f` 和 `tail -F`

```bash
# 先显示最后 100 行，再持续追踪
tail -n 100 -f -- /var/log/myapp/app.log

# 按文件名追踪，并在文件暂时不存在时继续重试
tail -n 100 -F -- /var/log/myapp/app.log

# 只看启动追踪后新增的行
tail -n 0 -F -- /var/log/myapp/app.log

# 同时观察应用日志与错误日志
tail -n 50 -F -- \
  /var/log/myapp/app.log /var/log/myapp/error.log
```

GNU `tail -f` 默认追踪已打开的**文件描述符**。如果日志轮转通过“旧文件重命名，再创建同名新文件”完成，它可能继续盯着旧文件。`-F` 相当于 `--follow=name --retry`，更适合按路径观察这种日志轮转；它仍不能替代可靠的日志采集系统，也不保证保留短时间内连续轮转的所有记录。参考 [GNU tail 文档](https://www.gnu.org/software/coreutils/manual/html_node/tail-invocation.html)。

### 4.1 实时过滤及输出缓冲

```bash
tail -n 200 -F -- /var/log/myapp/app.log \
  | grep --line-buffered -E 'ERROR|WARN|Exception'

# 多级过滤时，中间的 grep 也使用行缓冲
tail -n 0 -F -- /var/log/myapp/app.log \
  | grep --line-buffered -F -- 'traceId=abc123' \
  | grep --line-buffered -vF -- 'healthcheck'
```

输出接入管道后，某些程序会使用块缓冲，表现为日志积累一段时间才出现。`grep --line-buffered` 在每个输出行后刷新，但不能消除上游应用自身的缓冲，也不会让不带换行符的半行立即完整显示。参见 [GNU grep 缓冲选项](https://www.gnu.org/software/grep/manual/html_node/Other-Options.html)。

实时观察用于发现变化，故障复盘还应查询历史窗口。只看 `tail -n 200` 可能在高吞吐应用中仅覆盖几秒钟。

## 五、`grep` 内容检索：关键字、正则、上下文和计数

### 5.1 高频参数

| 参数 | 含义 | 使用要点 |
| --- | --- | --- |
| `-n` | 显示行号 | 便于回到原文件定位 |
| `-H` / `-h` | 始终显示 / 不显示文件名前缀 | 多文件分析时通常保留文件名 |
| `-i` | 忽略大小写 | 适合大小写不统一的日志 |
| `-F` | 按固定字符串匹配 | URL、IP、请求标识优先考虑 |
| `-E` | 使用扩展正则 | 用于分组、交替等模式 |
| `-v` | 选择不匹配的行 | 谨慎排除，以免隐藏故障证据 |
| `-A N` / `-B N` / `-C N` | 显示后 / 前 / 前后 N 行 | 上下文按物理行计算 |
| `-c` | 统计匹配行数 | 不是单词出现次数或业务事件数 |
| `-l` / `-L` | 只列出匹配 / 不匹配的文件名 | 先定位文件，再阅读内容 |
| `-m N` | 每个输入文件最多选择 N 个匹配行 | 是读取顺序靠前的匹配 |
| `-e 模式` | 指定一个模式，可重复 | 多个模式通常按“或”匹配 |
| `-r` | 递归搜索目录 | 应配合文件范围限制 |

### 5.2 固定字符串优先，减少误匹配

```bash
grep -nF -- 'ERROR' /var/log/myapp/app.log
grep -niF -- 'connection refused' /var/log/myapp/app.log
grep -nF -- '10.0.0.12' /var/log/myapp/app.log
grep -nF -- '/api/orders?id=1001' /var/log/myapp/app.log
```

普通正则中的 `.` 表示任意单个字符，`[]` 表示字符集合。查询 IP、带方括号的线程名和 URL 时，`-F` 能让它们按字面值处理。`-F` 表示固定字符串，**不表示整行相等**；需要整行完全相等时用 `-Fx`。

### 5.3 “或”“与”和排除

```bash
# ERROR 或 WARN
grep -nE -- 'ERROR|WARN' /var/log/myapp/app.log

# 多个固定字符串，任意一个匹配即可
grep -nF -e 'timeout' -e 'connection refused' \
  /var/log/myapp/app.log

# 同一行同时包含 ERROR 和指定请求标识
grep -F -- 'ERROR' /var/log/myapp/app.log \
  | grep -F -- 'traceId=abc123'

# 排除包含 DEBUG 的行
grep -vF -- 'DEBUG' /var/log/myapp/app.log

# 固定格式中，匹配独立的 ERROR 级别
grep -nE -- '(^|[[:space:]])ERROR([[:space:]]|$)' \
  /var/log/myapp/app.log
```

最后一条依赖日志格式，不应拿去解析任意 JSON 或不同字段布局。连续两次 `grep` 实现的是**同一物理行**上的“与”，并不自动关联同一请求的不同日志行。模式组合语义见 [GNU grep 匹配控制](https://www.gnu.org/software/grep/manual/html_node/Matching-Control.html)。

### 5.4 查看异常上下文

```bash
grep -n -C 15 -F -- 'NullPointerException' /var/log/myapp/app.log
grep -n -B 10 -A 40 -F -- 'Caused by:' /var/log/myapp/app.log
```

固定行数上下文适合快速查看，但不能保证包含完整的 Java、Python 或其他多行堆栈。先用 `grep` 定位，再在 `less` 中向前后阅读；需要自动提取完整记录时，使用后面的多行记录示例。

### 5.5 统计与返回码

```bash
# 包含 ERROR 的物理行数
grep -cF -- 'ERROR' /var/log/myapp/app.log

# 最近 100 条匹配行；需要读取完整输入文件
grep -F -- 'ERROR' /var/log/myapp/app.log | tail -n 100

# 最早遇到的 100 条匹配行，不是最新 100 条
grep -m 100 -F -- 'ERROR' /var/log/myapp/app.log
```

一条异常可能占据几十行，同一行也可能出现多次 `ERROR`，因此“匹配行数”“异常数量”和“失败请求数”必须分开。`grep -o` 可输出各次非空匹配，但这仍属于文本匹配统计。

GNU `grep` 通常以 `0` 表示选中了匹配行，`1` 表示未匹配，`2` 表示出错。脚本不能把所有非零状态都当成“没有错误日志”；尤其在使用 `set -e`、`pipefail` 时，应按业务预期分别处理。参考 [GNU grep 退出状态](https://www.gnu.org/software/grep/manual/html_node/Exit-Status.html)。

## 六、跨文件、压缩日志和 `ripgrep`

### 6.1 限定递归范围

```bash
grep -rnH -F \
  --include='*.log' \
  --exclude-dir=archive \
  -- 'traceId=abc123' /var/log/myapp

# 只找出包含目标的日志文件
grep -rlF --include='*.log' -- 'OutOfMemoryError' /var/log/myapp

# 按文件属性先筛选，再批量搜索内容
find /var/log/myapp -type f -name '*.log' -mmin -60 \
  -exec grep -nH -F -- 'traceId=abc123' {} +
```

最后一条的 `-mmin -60` 筛选的是**文件最近修改时间**，不是日志行的时间。仍在持续写入的长日志会入选，其中可能包含更早的记录。

GNU `grep -r` 与 `-R` 对符号链接的处理有差别，`-R` 会更积极地跟随符号链接，可能扩大搜索范围。一般从明确的日志目录开始，避免无意进入挂载目录或重复扫描。参考 [GNU grep 文件与目录选项](https://www.gnu.org/software/grep/manual/html_node/File-and-Directory-Selection.html)。

### 6.2 查询 `.gz` 历史日志

```bash
# 查询一个压缩文件并显示解压内容中的行号
zgrep -nF -- 'traceId=abc123' \
  /var/log/myapp/archive/app.log.2.gz

# 多个压缩文件保留文件名前缀
find /var/log/myapp/archive -type f -name '*.gz' \
  -exec zgrep -nH -F -- 'traceId=abc123' {} +

# 解压到标准输出后分页阅读，不修改原压缩包
gzip -cd -- /var/log/myapp/archive/app.log.2.gz | less
```

压缩文件中的搜索通常需要解压数据，读取成本依然存在。多文件输出的顺序也不能直接当成跨实例的全局时间顺序。

### 6.3 使用 `rg` 提高交互检索效率

```bash
rg -n -F -g '*.log' -- 'traceId=abc123' /var/log/myapp
rg -n -C 10 -- 'ERROR|Exception' /var/log/myapp

# 明确需要搜索隐藏和被忽略文件时，再显式扩大范围
rg -n --hidden --no-ignore -F -- 'traceId=abc123' /var/log/myapp
```

`rg` 默认遵循忽略规则，并跳过隐藏文件和部分二进制内容；“没有结果”可能来自搜索范围。不同版本的选项以本机帮助为准。其默认过滤行为见 [ripgrep 官方指南](https://github.com/BurntSushi/ripgrep/blob/master/GUIDE.md)。

## 七、按行号与时间范围提取日志

### 7.1 按行号截取：`sed` 与 `awk`

```bash
# 输出第 120 至 180 行，并在读到 180 行后退出
sed -n '120,180p;180q' /var/log/myapp/app.log

# 同时显示原始行号
awk 'NR >= 120 && NR <= 180 {print NR ":" $0}
     NR == 180 {exit}' /var/log/myapp/app.log
```

这些命令默认只读取，不会修改原文件。行号是某个文件版本中的位置；轮转、截断、插入或删除内容后，旧行号可能失效。

### 7.2 时间比较先声明格式

假设日志每条记录的首行都以固定 23 字符时间戳开头：

```text
2026-11-02 10:03:21.456 ERROR [http-8080-exec-7] traceId=abc123 request failed
java.lang.IllegalStateException: payment failed
    at com.example.OrderService.submit(OrderService.java:87)
Caused by: java.net.SocketTimeoutException: Read timed out
2026-11-02 10:03:22.101 INFO [http-8080-exec-8] traceId=def456 request completed
```

如果每行都是独立记录，可以进行字符串范围比较：

```bash
LC_ALL=C awk \
  -v start='2026-11-02 10:00:00.000' \
  -v stop='2026-11-02 10:10:00.000' '
  {
    ts = substr($0, 1, 23)
    if (ts >= start && ts < stop) print
  }
' /var/log/myapp/app.log
```

这里使用左闭右开区间 **`[10:00:00.000, 10:10:00.000)`**，便于相邻窗口衔接。它成立的条件是：字段定宽、日期从年到秒排列、同一时区且小数位数一致。该方法不会自动解析时间；对 `02/Nov/2026:...`、混用时区偏移或不定长日期的日志不能直接套用。

### 7.3 保留没有时间戳的堆栈续行

对于前面的多行异常，逐行比较会丢掉堆栈。可以在识别到记录首行时更新状态，续行沿用该状态：

```bash
LC_ALL=C awk \
  -v start='2026-11-02 10:00:00.000' \
  -v stop='2026-11-02 10:10:00.000' '
  /^[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2}\.[0-9]{3}[[:space:]]/ {
    ts = substr($0, 1, 23)
    selected = (ts >= start && ts < stop)
  }
  selected {print}
' /var/log/myapp/app.log > ./incident-window.log
```

这要求“时间戳首行 + 若干无时间戳续行”确实是应用的记录格式。混入其他来源的文本、被截断的记录或不同时间戳格式时，需要调整规则。输出文件从第一条被识别的合格首行开始保留，不会猜测文件开头孤立续行的归属。

脚本没有在遇到结束时间后直接 `exit`，因此能继续寻找文件后面乱序写入的合格记录。对于多实例、多线程或异步日志，不要未经验证便假设记录严格按时间排序。

### 7.4 为什么不直接使用 `sed '/开始时间/,/结束时间/p'`

`sed` 的地址范围匹配的是模式，不是时间运算。如果结束时间对应的那一秒没有任何日志，范围可能一直延伸到文件末尾；重复出现相同时间片段还可能生成多个范围。需要时间语义时，应选择 journal 的时间过滤、符合前提的字段比较，或专门的时间解析工具。

## 八、按 Trace ID 追踪请求，并提取完整多行记录

### 8.1 先建立请求关联

```bash
grep -nF -- 'traceId=abc123' /var/log/myapp/app.log

# 明确列出多个服务的日志，保留来源
grep -nH -F -- 'traceId=abc123' \
  /var/log/gateway/access.log \
  /var/log/order/app.log \
  /var/log/payment/app.log
```

请求标识比单独查询 `ERROR` 更有利于还原入口、下游调用、重试和返回状态。一个请求在多个服务里可能使用不同字段名；应确认网关是否透传标识、异步任务是否继承上下文，以及不同机器的时钟是否一致。

### 8.2 一次处理一个文件，按记录缓冲

下面的例子识别前述时间戳首行，先缓冲一条完整记录，再判断它是否包含目标字符串：

```bash
awk -v needle='traceId=abc123' '
  function emit_record() {
    if (index(record, needle)) printf "%s", record
  }
  /^[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2}\.[0-9]{3}[[:space:]]/ {
    emit_record()
    record = ""
  }
  {record = record $0 ORS}
  END {emit_record()}
' /var/log/myapp/app.log
```

这样能保留请求标识所在记录下方的 `Caused by`、`at ...` 等续行。它不会自动找出没有目标标识的其他独立记录，也不能解决并发输出导致的堆栈交错。单条记录极大或首行规则失配时，缓冲区也会持续增长，因此应先在少量真实日志上确认格式。

## 九、`awk`、`sort`、`uniq`：从日志提取统计信息

分析前先检查字段结构。以下 access 日志示例假设使用常见的 combined 布局：IP 为第 1 个空白字段，状态码为第 9 个字段；自定义格式需要重新定位。

```bash
# 请求量最多的前 20 个客户端地址
awk '{print $1}' /var/log/nginx/access.log \
  | LC_ALL=C sort | uniq -c | sort -nr | head -n 20

# 按 HTTP 状态码计数
awk '{count[$9]++} END {
  for (status in count) print status, count[status]
}' /var/log/nginx/access.log | sort -n

# 提取 5xx 响应
awk '$9 ~ /^5[0-9][0-9]$/ {print}' /var/log/nginx/access.log

# 使用双引号分隔字段，提取典型 combined 格式中的请求行
awk -F '"' '{print $2}' /var/log/nginx/access.log \
  | LC_ALL=C sort | uniq -c | sort -nr | head -n 20
```

`uniq -c` 只合并**相邻**的相同行，因此通常先排序。`sort` 处理大量数据时可能使用临时磁盘空间，应先限定日期和文件范围。

请求行统计会把不同查询参数分别计数；反向代理后的 `$1` 也可能只是代理地址。要统计真实用户、请求失败率或接口耗时，必须结合可信的客户端地址字段、日志格式及业务口径。

### 9.1 用固定字段统计慢请求

假设自定义日志的最后一个字段是**以秒为单位的纯数字耗时**：

```bash
awk '$NF ~ /^[0-9]+([.][0-9]+)?$/ && ($NF + 0) > 1 {
  print
}' /var/log/nginx/access-with-time.log
```

先检查字段是否确实为数字，避免把 `-`、`1.2ms` 或其他字段错误转换。`$request_time` 与 `$upstream_response_time` 的含义不同，后者还可能记录多次上游尝试；不能仅凭“最后一列看起来像数字”就使用这个规则。

## 十、结构化 JSON 日志使用 `jq`

如果日志采用 JSON Lines，即每行一个完整 JSON 对象：

```json
{"timestamp":"2026-11-02T10:03:21.456+08:00","level":"ERROR","traceId":"abc123","message":"request failed","durationMs":1280}
```

优先按字段查询，避免误匹配 `message` 中出现的级别或请求标识：

```bash
# 输出匹配对象，每条保持一行
jq -c 'select(.level == "ERROR")' /var/log/myapp/app.jsonl

# 同时筛选级别与请求标识
jq -c 'select(.level == "ERROR" and .traceId == "abc123")' \
  /var/log/myapp/app.jsonl

# 输出时间、级别和消息，使用制表符分隔
jq -r '[.timestamp, .level, .message] | @tsv' \
  /var/log/myapp/app.jsonl

# 缺失、非数字耗时不参与数值比较
jq -c 'select((.durationMs | type) == "number")
       | select(.durationMs > 1000)' /var/log/myapp/app.jsonl

# 实时查看，并让 jq 及时刷新输出
tail -n 0 -F -- /var/log/myapp/app.jsonl \
  | jq --unbuffered -c 'select(.level == "ERROR")'
```

`jq` 默认按 JSON 值流读取；JSON Lines 可直接处理。不要在超大日志上随意使用 `jq -s`，它会把全部输入收集进数组。若文件混有非 JSON 行，默认解析会报错，应先确认日志格式；`fromjson?` 一类静默跳过方式可能隐藏损坏数据。参数含义见 [jq 官方手册](https://jqlang.org/manual/)。

## 十一、systemd 日志：`journalctl`

```bash
# 最近 200 条，禁用分页器
journalctl -u myapp.service -n 200 --no-pager

# 持续追踪
journalctl -u myapp.service -n 100 -f

# 精确时间窗口；未写时区时按本机的时间解析规则处理
journalctl -u myapp.service \
  --since '2026-11-02 10:00:00' \
  --until '2026-11-02 10:10:00' \
  -o short-iso-precise --no-pager

# 最近 30 分钟，使用 UTC 输出
journalctl -u myapp.service --since '-30 min' --utc --no-pager

# 当前启动周期 / 上一次启动周期
journalctl -b -u myapp.service
journalctl -b -1 -u myapp.service

# 当前启动周期的内核日志
journalctl -k -b --no-pager

# 查询 journal 已记录的启动周期
journalctl --list-boots

# 当前用户的用户服务
journalctl --user -u myapp.service -n 100 --no-pager
```

这里的 `--until` 包含指定的边界时刻，与前面 awk 示例人为定义的右开区间不同。`-b -1` 需要上一次启动的 journal 仍然存在；若日志只存于运行时目录，重启后可能无法查询。

`journalctl -p warning` 查询的是 warning **及更高严重程度**的条目；应用把文本 `ERROR` 输出到 stdout，并不保证 journal 的 `PRIORITY` 就是 err。因此查询应用异常时，不应只依赖 `-p`。查看系统日志所需权限因发行版及用户组配置而异。上述语义以 [systemd journalctl 官方手册](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html)为准。

## 十二、Docker 与 Kubernetes 中查询应用日志

### 12.1 Docker

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Image}}'

# 最近 200 行，包含时间戳
docker logs --tail 200 --timestamps myapp

# 最近 30 分钟，并持续追踪
docker logs --since 30m --tail 200 --timestamps -f myapp

# 显式携带时区的时间窗口
docker logs \
  --since '2026-11-02T10:00:00+08:00' \
  --until '2026-11-02T10:10:00+08:00' \
  myapp 2>&1 | grep -F -- 'traceId=abc123'

# Compose 服务名与容器名不一定相同
docker compose logs --since 30m --tail 200 --timestamps -f myapp
```

`docker logs` 主要读取容器 stdout/stderr 经日志系统保存的内容；如果应用只写容器内部文件，该命令不一定能看到。可用历史还受日志驱动、轮转和容器生命周期影响。`--since` 与 `--tail` 同时使用时会共同限制结果，不代表完整的 30 分钟日志。参考 [Docker logs 官方文档](https://docs.docker.com/reference/cli/docker/container/logs/)。

### 12.2 Kubernetes

```bash
kubectl get pods -n production -o wide

# 指定命名空间、Pod 和容器
kubectl logs -n production myapp-7d9f-demo \
  -c app --tail=200 --timestamps=true

# 最近 30 分钟并跟踪
kubectl logs -n production myapp-7d9f-demo \
  -c app --since=30m --timestamps=true -f

# 同一 Pod 中该容器上一个实例的日志
kubectl logs -n production myapp-7d9f-demo -c app --previous

# 按标签查询多 Pod，标注来源并明确限制每个来源的行数
kubectl logs -n production -l app=myapp \
  --all-containers=true --prefix=true \
  --since=30m --tail=200
```

`--previous` 指向同一 Pod 内该容器的上一个实例，不会自动找回已删除 Pod 的日志。多 Pod 输出不等于全局按时间排序的事件流；若要覆盖所有副本，应核对标签是否完整命中。长期历史需要集中采集与存储。参数说明见 [kubectl logs 官方文档](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_logs/)。

## 十三、重定向、管道与 `tee`：理解日志如何产生和保存

### 13.1 三个标准文件描述符

| 编号 | 名称 | 默认连接 |
| --- | --- | --- |
| `0` | stdin，标准输入 | 终端输入 |
| `1` | stdout，标准输出 | 终端显示 |
| `2` | stderr，标准错误 | 终端显示 |

```bash
# 覆盖写入标准输出；错误仍显示在终端
./run-task.sh > ./task.log

# 追加写入，合并标准输出与标准错误
./run-task.sh >> ./task.log 2>&1

# 两种输出分别存储
./run-task.sh > ./task.out 2> ./task.err

# 屏幕查看的同时追加保存
./run-task.sh 2>&1 | tee -a ./task.log

# nohup 示例：明确写入位置，关闭终端输入
nohup java -jar /opt/myapp/app.jar \
  >> /var/log/myapp/console.log 2>&1 < /dev/null &
```

`>` 会在命令读取输入前打开并截断目标文件；`>>` 追加。`2>&1` 表示让 stderr 复制**此时** stdout 的目标。重定向从左到右处理，所以 `> file 2>&1` 与 `2>&1 > file` 不等价。参考 [Bash 重定向文档](https://www.gnu.org/s/bash/manual/html_node/Redirections.html)。

`nohup` 处理挂断信号及相关输入输出，不负责开机启动、自动重启和日志轮转。长期服务通常应交给服务管理器或容器编排系统。

### 13.2 `sudo` 不会自动提升 Shell 重定向权限

```bash
# tee 以 sudo 权限打开目标文件；不使用 -a 时会覆盖
printf '%s\n' 'enabled=true' \
  | sudo tee /etc/myapp/example.conf > /dev/null
```

这解释了为什么 `sudo echo ... > /etc/...` 仍可能报权限不足：`>` 是当前 Shell 执行的。上例会覆盖目标配置，只用于明确需要写入这一内容的场景；修改正式配置前先备份并验证格式。

### 13.3 管道的返回状态

默认情况下，Bash 管道通常返回最后一个命令的状态。若 `run-task.sh` 失败但 `tee` 成功，仅检查 `$?` 可能看不出上游失败。

```bash
# 放在独立 Bash 脚本中使用
set -o pipefail
./run-task.sh 2>&1 | tee ./task.log
rc=$?
printf 'pipeline exit status: %s\n' "$rc"
```

`pipefail` 让管道返回最右侧非零状态；它不会自动把所有失败变成异常。上游因下游 `head` 提前退出而收到 SIGPIPE、`grep` 没有匹配返回 1，都应结合场景判断。

## 十四、文件与目录的定位、列出和属性检查

```bash
pwd
cd /var/log/myapp
cd -

# -a 含隐藏项，-h 易读大小，-t 按修改时间排序
ls -lah -- /var/log/myapp
ls -lht -- /var/log/myapp

# 看 inode 与链接计数
ls -li -- /var/log/myapp/app.log

# GNU stat：查看大小、mtime、ctime 和权限
stat -c 'name=%n size=%s mtime=%y ctime=%z mode=%A owner=%U:%G' \
  -- /var/log/myapp/app.log

# 判断内容类型，不能只看扩展名
file -- /var/log/myapp/app.log

# 解析符号链接指向的实际路径
readlink -f -- /var/log/myapp/current.log
```

`ls -lh` 的大小一般是文件的逻辑长度，不等于实际占用块数；稀疏文件尤其明显。`ctime` 是 inode 状态变更时间，**不是创建时间**。创建时间是否可查询，取决于文件系统、内核和工具支持；不要用 `ctime` 冒充它。

## 十五、`find`：按名称、类型、时间、大小和权限查找

### 15.1 名称、类型与目录排除

```bash
find /var/log/myapp -type f -name '*.log' -print
find /opt/myapp -type f -iname '*config*' -print
find /opt/myapp -maxdepth 2 -type d -print
find /opt/myapp -type l -print

# 排除 archive 子树
find /var/log/myapp -path /var/log/myapp/archive -prune -o \
  -type f -name '*.log' -print

# 多个名称条件必须分组
find /var/log/myapp -type f \
  \( -name '*.log' -o -name '*.out' \) -print
```

`find` 中相邻条件通常表示“与”，`-o` 表示“或”，且“与”的优先级更高。缺少括号可能让 `-type f` 只约束一侧。括号需转义或引用，避免被 Shell 当成语法处理。

### 15.2 按修改时间查找

```bash
# 最近 30 分钟修改过的文件
find /var/log/myapp -type f -mmin -30 -print

# 修改时间在最近 24 小时以内
find /var/log/myapp -type f -mtime 0 -print

# GNU find：晚于起点，且不晚于终点
find /var/log/myapp -type f \
  -newermt '2026-11-02 10:00:00' \
  ! -newermt '2026-11-02 10:10:00' -print
```

`-mtime` 以 24 小时为单位取整：`-mtime 1` 大致表示距今 24 至 48 小时；`-mtime +7` 表示取整后大于 7，即至少约 8 个 24 小时。它不是直观的“超过 7 天整”。`-daystart` 可以改变部分时间测试的基准，且只影响出现在它后面的相应条件。详见 [GNU find 时间范围](https://www.gnu.org/software/findutils/manual/html_node/find_html/Age-Ranges.html)。

`-newermt` 比较文件 mtime；边界为 **`(起点, 终点]`**，与前面的日志内容窗口也不同。审计或精确清理时，要明确采用哪种边界。

### 15.3 按大小和属性查找

```bash
# 大于 500 MiB；GNU find 的 M 是 1024×1024 字节单位
find /var/log/myapp -type f -size +500M -print

# 空的普通文件与空目录
find /var/log/myapp -type f -empty -print
find /opt/myapp -type d -empty -print

# 其他用户可写的普通文件，只查看
find /opt/myapp -type f -perm -0002 -print

# 指定属主
find /opt/myapp -user myapp -type f -print
```

`-size` 使用指定单位时会对文件长度向上取整；需要精确字节阈值可使用 `c`，例如 `-size +524288000c`。空文件也可能是应用必需的标记或锁文件，不应一概删除。

## 十六、创建、复制、移动、链接和删除

### 16.1 创建文件与目录

```bash
mkdir -p -- ./myapp-work/backup ./myapp-work/export

# 文件不存在时创建；已经存在时更新时间戳，不清空内容
touch -- ./myapp-work/notes.txt

# 写入文本；目标已存在时会覆盖
printf '%s\n' '排障记录' > ./myapp-work/notes.txt

# 创建仅当前用户可访问的临时目录
work_dir=$(mktemp -d)
printf '%s\n' "$work_dir"
```

`mkdir -p` 不代表已有目录的权限会被调整。`touch` 也不等于“新建一个空白文件并覆盖原内容”。

### 16.2 复制与备份

```bash
# 修改前创建带时间后缀的配置副本
backup_file="/opt/myapp/config/app.properties.bak.$(date +%Y%m%d-%H%M%S)"
cp -a -- /opt/myapp/config/app.properties "$backup_file"

# 将源目录内容复制到已准备的目标目录，包含隐藏文件
mkdir -p -- ./myapp-backup
cp -a -- /opt/myapp/. ./myapp-backup/

# 交互确认是否覆盖已存在的目标文件
cp -i -- ./new.properties ./app.properties
```

GNU `cp -a` 用于递归复制并尽量保留属性和链接关系；保留属主、ACL、扩展属性等还受权限和目标文件系统能力限制。`目录/.` 可包含隐藏项，`目录/*` 通常不会匹配以点开头的名称。对于正在持续修改的数据，普通复制不提供应用级一致性快照。参考 [GNU cp 文档](https://www.gnu.org/s/coreutils/manual/html_node/cp-invocation.html)。

### 16.3 移动与符号链接

```bash
mv -i -- ./report.txt ./report-20261102.txt
ln -s -- /opt/myapp/releases/20261102 ./current-release
readlink -- ./current-release
```

同一文件系统内的重命名通常通过目录项变更完成；跨文件系统的 `mv` 需要复制和删除，不能把两者都当成原子操作。符号链接保存的是路径：目标移动或删除后可能成为悬空链接。

### 16.4 删除普通文件和目录

```bash
# 对单个文件先确认路径，再交互删除
ls -l -- ./obsolete.log
rm -i -- ./obsolete.log

# 只删除空目录
rmdir -- ./empty-dir

# GNU rm：递归删除前提示一次，不会逐个文件询问
rm -rI -- ./old-export
```

`rm` 通常不会把文件放进桌面回收站。`-f` 会减少提示，但不保证能绕过权限、只读文件系统或不可变属性。不要用别名是否带 `-i` 来判断脚本的安全性；脚本应显式写出需要的选项。

## 十七、特殊文件名与批量操作：`-exec`、`-print0`、`xargs -0`

文件名可能包含空格、制表符、引号，甚至换行。`for f in $(find ...)`、`ls | xargs ...` 会把文件名拆错，不适合可靠的批量处理。

```bash
# find 直接按参数传递文件名，自动分批
find /var/log/myapp/archive -type f -name '*.gz' \
  -exec ls -lh -- {} +

# 使用 NUL 分隔连接 find 和 xargs；-r 是 GNU 选项
find /var/log/myapp/archive -type f -name '*.gz' -print0 \
  | xargs -0 -r sha256sum --
```

`-exec ... {} +` 批量传递参数；`-exec ... {} \;` 每个匹配对象执行一次。NUL 分隔能保留特殊文件名的边界，但不能解决文件在扫描后被替换的竞态问题。在允许不可信用户修改的目录中，特权批处理还需进一步控制目录权限及执行方式。见 [GNU find 安全文件名处理](https://www.gnu.org/software/findutils/manual/html_node/find_html/Safe-File-Name-Handling.html)。

### 17.1 按保留时间清理已归档日志

只清理明确的归档目录，先展示候选文件：

```bash
# 预览：修改时间不晚于 30 天前的归档压缩日志
find /var/log/myapp/archive -xdev -type f -name '*.log.gz' \
  ! -newermt '30 days ago' -print
```

确认保留策略和候选范围后，再选择执行删除：

```bash
find /var/log/myapp/archive -xdev -type f -name '*.log.gz' \
  ! -newermt '30 days ago' -delete
```

`-xdev` 不跨入不同设备号的文件系统，不等于排除所有形式的挂载。两次运行之间文件和相对时间边界都会变化，预览不是对删除结果的锁定；严格流程可把边界固定为明确时间，并在受控目录执行。`-delete` 应放在完整筛选条件后，也不应与前面的 `-prune` 模式直接混用，因为它会启用深度优先遍历。

长期清理宜通过日志轮转策略管理，并区分业务保留期限、mtime 和日志实际发生时间。不要把正在写入的 `app.log` 当作普通归档文件删除。

## 十八、编辑配置与文本替换：`vim`、`sed`、`diff`

### 18.1 交互编辑

```bash
vim /opt/myapp/config/app.properties
```

| 操作 | Vim 按键 |
| --- | --- |
| 进入插入模式 | 普通模式下按 `i` |
| 返回普通模式 | `Esc` |
| 搜索 | `/关键字`，回车；`n` 找下一处 |
| 撤销 | 普通模式下按 `u` |
| 保存 | `:w`，回车 |
| 保存并退出 | `:wq`，回车 |
| 放弃未保存修改 | `:q!`，回车 |

编辑正式配置前先留备份，完成后运行应用自身的配置校验。能够打开文件并保存，并不意味着语法正确，也不意味着进程已加载新配置。

### 18.2 `sed` 先预览，再带备份替换

```bash
# 只预览，不修改原文件
sed 's/^server\.port=8080$/server.port=8081/' \
  /opt/myapp/config/app.properties

# GNU sed：修改原文件并生成 .bak 副本
sed -i.bak 's/^server\.port=8080$/server.port=8081/' \
  /opt/myapp/config/app.properties

# 比较修改前后内容
diff -u -- /opt/myapp/config/app.properties.bak \
  /opt/myapp/config/app.properties
```

该规则只适用于恰好存在 `server.port=8080` 的 properties 文本，不会处理任意空格、注释、重复定义或 YAML。复杂配置应使用对应格式的解析工具或应用提供的管理命令。

GNU `sed -i` 通常通过写临时文件再重命名实现，可能改变 inode 或影响链接关系；不应拿来修改正在追加的日志。反复用同一个 `.bak` 后缀还会覆盖上一份备份，重要改动应使用唯一备份名。详见 [GNU sed 原地编辑说明](https://www.gnu.org/software/sed/manual/sed.html)。

下面这种写法会先截断输入文件，必须避免：

```bash
# 错误示例：不要执行
sed 's/old/new/g' app.properties > app.properties
```

`diff` 返回 `0` 表示相同，`1` 表示存在差异，更大的状态通常表示错误；脚本也应区分这几种情况。

## 十九、权限、属主、目录访问与默认权限

```bash
id
ls -ld -- /opt /opt/myapp /opt/myapp/config
ls -l -- /opt/myapp/config/app.properties

# 查看整个路径各层的权限
namei -l -- /opt/myapp/config/app.properties

# 让属主读写、同组只读、其他用户无权限
chmod 640 -- /opt/myapp/config/app.properties

# 目录需要 x 权限才能穿越访问
chmod 750 -- /opt/myapp/config

# 明确修改一个对象的属主与属组
sudo chown myapp:myapp -- /opt/myapp/config/app.properties

# 查看默认创建权限的掩码
umask
```

| 对象 | `r` | `w` | `x` |
| --- | --- | --- | --- |
| 普通文件 | 读取内容 | 修改内容 | 作为程序执行，仍需有效格式等条件 |
| 目录 | 列出目录项名称 | 增删目录项，通常还需 `x` | 穿越目录、访问已知名称 |

删除文件通常取决于父目录的写入和执行权限，而不只看文件是否可写；sticky bit、ACL、只读挂载和安全模块也会影响结果。不要因为服务无法读取配置就直接执行 `chmod -R 777`。

当传统权限看起来正确但仍报拒绝访问时，可继续查看 ACL 与系统安全策略：

```bash
getfacl -- /opt/myapp/config/app.properties
ls -lZ -- /opt/myapp/config/app.properties
```

这些工具和 SELinux 选项不一定在所有系统中存在。应根据拒绝记录修复目录标签或策略，不要用关闭安全机制代替定位原因。

## 二十、压缩、归档、同步与完整性验证

### 20.1 `tar` 与 `gzip`

```bash
# 归档配置：输出放在当前目录，成员路径为相对路径 config/
tar -czf ./myapp-config-20261102.tar.gz -C /opt/myapp config

# 解压前先查看归档成员
tar -tzf ./myapp-config-20261102.tar.gz

# 解压到专用的新目录，便于核对结果
mkdir -- ./restore-preview-20261102
tar -xzf ./myapp-config-20261102.tar.gz -C ./restore-preview-20261102

# 压缩到另一个文件，保留原始日志
gzip -c -- ./incident-window.log > ./incident-window.log.gz

# 检查 gzip 数据流完整性
gzip -t -- ./incident-window.log.gz
```

`tar` 负责归档，`gzip` 负责压缩，二者可以组合。默认的 `gzip 文件` 通常会用压缩文件替换原文件，所以需要保留原件时采用 `-c`。不可信归档可能包含危险路径或链接，应在低权限、隔离的目标目录检查和解包。

正在写入的日志可能在归档过程中发生变化；数据库等有状态数据应使用应用一致性备份方法。不要把“命令返回成功”直接等同于“具备可恢复的一致性备份”。

### 20.2 `rsync` 同步先演练

```bash
# -n 不实际传输；-i 列出拟发生的变化
rsync -ani -- /opt/myapp/config/ ./config-backup/

# 核对后执行
rsync -ai -- /opt/myapp/config/ ./config-backup/

# 通过 SSH 复制到远端，非默认端口可显式指定
rsync -ani -e 'ssh -p 2222' -- \
  /opt/myapp/config/ backupuser@backup.example.com:/srv/backup/myapp-config/
```

源目录末尾的 `/` 通常表示复制目录内容，不带 `/` 则可能多出一层源目录名。`-a` 不自动包含硬链接、ACL 和扩展属性的全部保留需求；有这些要求时应核对 `-H`、`-A`、`-X` 及两端权限。`--delete` 会删除目标端多出的文件，只有明确需要镜像语义时才添加，并先演练。见 [rsync 官方手册](https://download.samba.org/pub/rsync/rsync.1)。

### 20.3 校验传输和备份文件

```bash
sha256sum -- ./myapp-config-20261102.tar.gz > ./myapp-config-20261102.sha256
sha256sum -c -- ./myapp-config-20261102.sha256
```

校验和适合检查文件内容是否一致，但不验证备份是否能被应用恢复，也不单独证明来源可信。应保留受信任的校验值，并定期做恢复验证。

## 二十一、磁盘占用、inode 与“删了日志却不释放空间”

### 21.1 先区分文件大小和文件系统容量

```bash
# 日志路径所在文件系统的容量与 inode 使用情况
df -h -- /var/log/myapp
df -i -- /var/log/myapp

# 统计日志目录及其一级子目录占用，不跨文件系统
du -x -h --max-depth=1 -- /var/log/myapp | sort -h

# 按逻辑长度查看最大的 20 个文件；NUL 分隔保留文件名边界
find /var/log/myapp -xdev -type f -printf '%s\t%p\0' \
  | sort -z -nr | head -z -n 20 | tr '\0' '\n'
```

`df` 查看文件系统整体分配情况，`du` 遍历可访问目录项估计文件占用，两者统计对象不同。稀疏文件、硬链接、快照、预留块、挂载覆盖和已删除但仍打开的文件都可能让结果难以直接对齐。最后一个命令按逻辑长度排序，且转为文本后含换行的文件名仍可能显示成多行，适合人工查看。

### 21.2 检查已删除但仍被进程打开的文件

```bash
sudo lsof +L1
```

删除路径不等于立即释放底层数据：如果进程仍持有打开的文件描述符，相关空间可能继续占用。应确认具体 PID、文件及所属服务，再按照应用支持的方式重新打开日志，或安排必要的服务重启。不要看到 `(deleted)` 就直接终止不明进程。

### 21.3 日志轮转与紧急截断

长期方案应是应用日志策略或 `logrotate`，包括轮转条件、压缩、保留份数、创建权限，以及通知进程重新打开日志的方式。

```bash
# 调试模式：查看轮转决策，不实际修改日志和状态文件
sudo logrotate -d /etc/logrotate.d/myapp
```

`copytruncate` 在复制与截断之间存在可能丢失日志的窗口；能否采用、是否需要重开信号，要结合应用行为判断。参见 [logrotate 手册](https://man7.org/linux/man-pages/man8/logrotate.8.html)。

只有在**已保存必要证据、明确接受内容丢失、确认目标是文本日志**的紧急场景，才考虑：

```bash
sudo truncate -s 0 -- /var/log/myapp/app.log
```

该命令保留文件但清空其内容，不能恢复原日志。若写入进程不使用追加模式，截断后继续从旧偏移写入还可能产生空洞；因此它不能替代正确的日志管理，更不能用于 journal、数据库或未知二进制文件。

## 二十二、完整案例：排查某接口在十分钟内大量超时

假设已知以下信息：应用是 `myapp.service`；日志为前述固定时间戳格式；用户在北京时间 2026 年 11 月 2 日 10:00 至 10:10 之间调用订单接口出现超时。

### 第一步：确认实例、时区与当前状态

```bash
date '+%Y-%m-%d %H:%M:%S %z %Z'
systemctl status myapp.service --no-pager -l
stat -- /var/log/myapp/app.log
tail -n 30 -- /var/log/myapp/app.log
df -h -- /var/log/myapp
```

确认用户所说的时间与日志时区一致，服务运行在预期主机和版本上；若当前文件不包含故障窗口，再查未压缩轮转文件、压缩归档或 journal。

### 第二步：把窗口导出到独立目录

```bash
incident_dir=$(mktemp -d)

LC_ALL=C awk \
  -v start='2026-11-02 10:00:00.000' \
  -v stop='2026-11-02 10:10:00.000' '
  /^[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2}\.[0-9]{3}[[:space:]]/ {
    ts = substr($0, 1, 23)
    selected = (ts >= start && ts < stop)
  }
  selected {print}
' /var/log/myapp/app.log > "$incident_dir/window.log"

wc -l -- "$incident_dir/window.log"
```

导出目录应有足够容量；临时目录不是长期证据存储，排查后按保留要求转存。原日志持续增长时，本次读取也不属于冻结快照。

### 第三步：定位首个异常并保留因果上下文

```bash
grep -nE -- 'ERROR|Exception|timed out|timeout' \
  "$incident_dir/window.log" | head -n 50

less -N -- "$incident_dir/window.log"
```

从异常记录找到请求标识，例如 `traceId=abc123`，再追踪相同请求在网关、订单服务和支付服务中的过程。不要只根据 `SocketTimeoutException` 就认定数据库故障；超时可能发生在连接建立、连接池等待、读响应、DNS 或重试预算等不同环节。

### 第四步：检查同一时间的系统与服务证据

```bash
journalctl -u myapp.service \
  --since '2026-11-02 10:00:00 +08:00' \
  --until '2026-11-02 10:10:00 +08:00' --no-pager

journalctl -k \
  --since '2026-11-02 10:00:00 +08:00' \
  --until '2026-11-02 10:10:00 +08:00' --no-pager

# 当前状态只能作为补充，不能倒推出故障窗口的资源状况
df -h -- /var/log/myapp
df -i -- /var/log/myapp
```

进一步对齐监控中的 CPU、内存、GC、连接池、请求量和下游延迟。当前 `top` 或 `df` 正常不能证明十分钟前也正常；日志中的相关性需要结合时间、请求标识和系统指标建立证据链。

### 第五步：验证修复并保留排查记录

修复后对相同接口进行受控验证，观察错误率、延迟及下游状态是否恢复，再持续追踪日志。记录故障窗口、影响实例、请求标识、原因、修复方式和验证结果。分享日志前应检查令牌、Cookie、个人信息和业务敏感字段，原始证据与可分享副本按实际需要分别保留。

## 二十三、一个可以在临时目录中练习的小实验

下面只创建临时目录和样本文件，便于理解“匹配行”与“完整记录”的差别：

```bash
demo_dir=$(mktemp -d)
cat > "$demo_dir/app.log" <<'LOG'
2026-11-02 09:59:59.900 INFO traceId=before ready
2026-11-02 10:00:00.000 INFO traceId=abc123 request start
2026-11-02 10:03:21.456 ERROR traceId=abc123 request failed
java.lang.IllegalStateException: payment failed
    at com.example.OrderService.submit(OrderService.java:87)
Caused by: java.net.SocketTimeoutException: Read timed out
2026-11-02 10:03:22.101 INFO traceId=def456 request completed
2026-11-02 10:10:00.000 INFO traceId=after next window
LOG

grep -nF -- 'traceId=abc123' "$demo_dir/app.log"
grep -n -A 3 -F -- 'request failed' "$demo_dir/app.log"
sed -n '3,6p;6q' "$demo_dir/app.log"

printf 'sample directory: %s\n' "$demo_dir"
```

第一条查询只返回带目标标识的第 2、3 行，第二条保留第 3 行及后三行堆栈，第三条输出第 3 至 6 行。把第七、八章的脚本用于这个文件，可以验证时间窗口是否排除右边界、堆栈续行是否保留，以及记录筛选与逐行筛选的区别。

## 二十四、常见误区与命令速查

### 24.1 查不到、查不全或判断错误时

| 现象或做法 | 原因或风险 | 改进方法 |
| --- | --- | --- |
| 当前日志没有故障记录 | 已轮转、实例不对、时区不一致 | 核对来源，查询归档和其他副本 |
| `tail -f` 突然不更新 | 仍追踪轮转前的旧文件 | 核对应用写入目标，按需用 `-F` |
| 实时过滤一阵一阵输出 | 管道或应用缓冲 | 检查各环节，按需启用行缓冲 |
| 搜 IP 命中不相关内容 | `.` 被当成正则通配符 | 使用 `grep -F` |
| 查询 ERROR 后堆栈不见了 | 堆栈续行没有关键字 | 查看上下文或按记录提取 |
| `grep -c` 被当作错误次数 | 统计的是匹配行 | 定义事件或请求级统计口径 |
| `grep -m 100` 被当作最新记录 | 它选择读取顺序靠前的匹配 | 明确方向，并限定时间窗口 |
| `find -mtime` 被当成业务时间 | 它读取文件元数据 | 对日志内容的时间字段筛选 |
| `sed` 重定向回原文件 | Shell 先截断了目标 | 使用备份、临时输出或合适的编辑方式 |
| `rm` 后磁盘仍满 | 可能有进程继续持有文件 | 查询 `lsof +L1` 并处理对应服务 |
| `chmod 777` 暂时“修好”问题 | 扩大权限并掩盖实际原因 | 检查运行账户、父目录、ACL 与标签 |
| `rsync` 后目录多了一层 | 源目录末尾 `/` 语义不同 | 先用 `-n -i` 查看结果 |
| 文件备份可校验就认为能恢复 | 内容完整不等于状态一致 | 验证配置、依赖和实际恢复流程 |

### 24.2 高频命令速查

| 任务 | 命令示例 |
| --- | --- |
| 看日志末尾 | `tail -n 200 -- app.log` |
| 按文件名持续追踪 | `tail -n 100 -F -- app.log` |
| 交互浏览大文件 | `less -N -S -- app.log` |
| 固定字符串检索 | `grep -nF -- 'traceId=abc123' app.log` |
| 多关键字任选其一 | `grep -nE -- 'ERROR\|WARN' app.log` |
| 查看前后文 | `grep -n -C 20 -F -- 'Exception' app.log` |
| 查看指定行区间 | `sed -n '100,150p;150q' app.log` |
| 查最近修改的文件 | `find ./logs -type f -mmin -30 -print` |
| 查压缩日志 | `zgrep -nF -- 'timeout' app.log.2.gz` |
| 查服务最近日志 | `journalctl -u myapp.service -n 200 --no-pager` |
| 查容器日志 | `docker logs --tail 200 --timestamps myapp` |
| 查看文件类型与属性 | `file -- app.log`；`stat -- app.log` |
| 复制配置并保留属性 | `cp -a -- app.properties app.properties.bak` |
| 比较文件 | `diff -u -- before.conf after.conf` |
| 查看文件系统容量 | `df -h -- /var/log/myapp` |

| 查看已删除但仍打开的文件 | `sudo lsof +L1` |
